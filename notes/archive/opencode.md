# OpenCode（开源 AI 编程 agent）

这个项目是 **OpenCode**——一个开源的 AI 编程助手，跟前面学的 Codex 是同一类东西（在终端里帮你写代码、改代码的 AI 助手），但它是社区开源、不绑定任何一家公司的，而且特别重视"开放"：你可以自由接入各种模型（OpenAI、Anthropic、DeepSeek、本地模型都行）、通过插件扩展能力。

它背后用的技术栈很有意思，值得单独提一下：

- **TypeScript**：带类型检查的 JavaScript（JavaScript 是网页语言，TypeScript 是它的"升级版"，写大项目更不容易出错）。
- **Bun**：一个比 Node.js 更快的 JavaScript 运行环境（可以理解为"加速版 Node"），这个项目里用 Bun 来跑代码、管理依赖（看到根目录有 `bun.lock` 文件）。
- **Effect**：一个让"异步操作"（比如等网络请求、读文件）更好管理的 TypeScript 库。项目里有 `effect-drizzle-sqlite` 这种包，说明它用 Effect + SQLite 存数据。
- **monorepo**（单仓库多包）：一个仓库里同时管着几十个"包"（可以理解成几十个相对独立的小项目），它们共享一份依赖、一起发版。

几个关键概念（大白话版）：

- **TUI**：终端里的图形界面（用文字画的界面），OpenCode 的主界面就是 TUI。
- **SDK**：Software Development Kit，软件开发工具包——把自己程序的功能封装好，让别人写几行代码就能调用。
- **协议（Protocol）**：两套程序之间"约定怎么说话"的规则。OpenCode 把自己的核心逻辑和外界（比如桌面端、网页端）隔开，靠一个明确的协议通信。

## 2026-09-11 学习记录

**当天版本**：commit `193de13` —— "fix(stats): normalize deepseek v4.1 flash"（修复统计功能：把 deepseek v4.1 flash 这个模型名统一格式）。

### 今天学到了什么

**1. 一个仓库里几十个包是怎么组织的？**

它的 `packages/` 目录下有几十个包，我挑几个关键的：

- `opencode`：核心，智能体循环（agent loop）就在它的 `src/agent/agent.ts` 里。
- `core`、`schema`、`protocol`、`server`：核心逻辑、数据定义、通信协议、服务器。
- `cli`：命令行入口；`tui`：终端界面；`web`、`app`、`desktop`：网页版、应用、桌面版。
- `client`、`sdk`、`sdk-next`：给开发者用的客户端库和 SDK。

这种"按职责切分成很多小包"的方式叫 **monorepo**，好处是：界面、核心、SDK 可以独立演进，但共享同一套代码和依赖管理。缺点是：几十个包之间的依赖关系要理清楚，否则会乱。

**2. 依赖方向是"单向"的——这是个好设计**

它的 `AGENTS.md` 里写了一条很严格的规定：依赖方向必须是 `Schema → Core → Protocol → Server`（数据定义被核心用，核心被协议用，协议被服务器用），而且 **Client 的代码可以依赖 Schema 和 Protocol，但绝对不能依赖 Core 和 Server**。

这句话对新手来说有点绕，我用例子解释：想象一座楼的图纸——"Schema"是"材料的规格书"（什么材料长什么样），"Core"是"承重结构"，"Protocol"是"楼内电梯和管线的规则"，"Server"是"给外部访客的前台"。规则要求：前台（Client）只能按"管线规则"和"规格书"来做事，不能直接伸手去改承重结构。这样外部客户怎么用你的功能都不会破坏内部结构，升级内部时也不用担心连累外部。**这种"分层 + 单向依赖"是大型项目的生存法则。**

**3. 它默认分支叫 `dev` 而不是 `main`**

这个仓库有个小特点：默认开发分支是 `dev`。它的 `AGENTS.md` 里专门提醒："默认分支是 dev，本地 main 可能不存在，用 dev 或 origin/dev 做对比。"这说明它的发布流程是：日常开发都在 `dev` 上，稳定了才合并发布。这也是很多开源项目（尤其是快速迭代的）会采用的节奏：**开发主干和稳定版本分开**。

**4. 今天这个提交在干什么？**

`193de13` 是统计模块（`packages/stats`）的一个小修复：模型名 `deepseek v4.1 flash` 在不同地方写法可能不一致（大小写、空格、版本号），统计时会把同一个模型算成好几个，所以要做 **normalize（归一化）**——把所有写法统一成一个标准名字。别小看这个改动，统计如果对不上账，做数据分析的人会被误导。**"归一化"是数据处理里很常见也很重要的一步：先把脏数据洗干净，再谈统计。**

### 一句话收获

OpenCode 教给我两件事：一是"单向依赖 + 明确分层"能让一个几十个包的大项目不乱套；二是它用 Bun、Effect、monorepo 这些偏"新锐"的技术栈，让我看到开源编程助手在工程实践上可以很前卫。

## 2026-09-12 学习记录

**当天版本**：commit `95daf90` —— "fix(acp): restore session options and reasoning boundaries"（修复 ACP：恢复会话选项和推理边界）。

### 今天学到了什么

**1. ACP 是什么？—— AI 智能体的"标准插座"**

今天这个提交的标题里有个缩写 **ACP**，全称是 **Agent Client Protocol（智能体客户端协议）**。这是今天最值得学的概念。

大白话解释：市面上有很多 AI 编程助手（Codex、OpenCode、Claude Code……），也有很多编辑器（VS Code、Cursor……）。如果每个助手和每个编辑器之间都要专门写一套对接代码，那就是"每家跟每家握手"，乱成一团。**ACP 就是一个大家约定好的标准协议**：任何编辑器只要按这个协议说话，就能接上任何支持这个协议的 AI 智能体——就像电器统一用同一个插座规格，什么电器都能插。

OpenCode 的 ACP 代码在 `packages/opencode/src/acp/` 下，它直接用官方的 `@agentclientprotocol/sdk`（ACP 官方提供的开发工具包），说明 ACP 已经是一个有正式标准的协议。

**2. 协议里定义了哪些"动作"？**

在 `service.ts` 里我读到协议定义的一整套操作，光看名字就能猜个大概：

- `initialize`（初始化）和 `authenticate`（登录验证）：握手阶段，确认身份和双方能力。
- `newSession`（新建会话）、`loadSession`（加载已有会话）、`listSessions`（列出所有会话）、`resumeSession`（继续之前的会话）、`closeSession`（关闭会话）、`forkSession`（复制出一个新会话，像 git 的分叉）。
- `prompt`（提问）：把用户的话发给智能体，这是核心动作。
- `cancel`（取消）：打断正在进行的任务。
- `setSessionConfigOption`（设置会话配置项）、`setSessionModel`（切换模型）、`setSessionMode`（切换模式）。

看到这里我明白了一个关键点：**协议的职责就是"把会话的生命周期管理好"**——从建立、提问、取消，到切换配置和模型。智能体内部怎么干活它不管，但它规定了"外面的人怎么跟你打交道"。

**3. 今天的修复：恢复"会话选项"和"推理边界"**

`95daf90` 修复了两样东西：

- **会话选项（session options）**：会话的配置项，比如让智能体以什么模式工作。这次修复是让这些选项在某种场景下被弄丢之后能恢复回来。
- **推理边界（reasoning boundaries）**：模型"思考"（reasoning）的边界设置。现在很多模型在回答问题前会先"想一会儿"（推理），有些场景要求它多想、有些要求它少想，这就是边界的意义。修复是让边界设置能正确生效。

有意思的是，这个修复还配了 290 多行新增的测试（`service-session.test.ts`）——**改一个 bug，把对应的场景用测试钉死，防止以后再犯**，这是很标准的工程习惯。

### 一句话收获

OpenCode 让我认识了 ACP 这个"智能体标准插座"：通过定义会话的完整生命周期（新建、加载、继续、提问、取消、复制、切换配置），不同的编辑器能和不同的 AI 智能体自由组合——标准化，是把生态做大的关键。

## 2026-09-13 学习记录

**当天版本**：commit `95daf90`（昨天那个 ACP 修复，今天官方没有新提交，保持最新）。

### 今天学到了什么

**1. 换个角度：AI 助手"什么事能做、什么事不能做"由谁说了算？**

昨天学了 ACP（智能体客户端协议），今天官方没更新，我换了个角度，去看了 opencode 的**权限系统**（`packages/opencode/src/permission/`）。这是每个 AI 助手都要回答的问题：AI 想"写文件"、"运行命令"、"访问网络"，到底允不允许？总不能什么都让它干，也不能什么都拦着。

**2. 核心函数：evaluate（评估一条请求）**

opencode 的权限核心是一个叫 `evaluate` 的函数，它的签名大概长这样：

```
evaluate(permission, pattern, ...rulesets) → 规则结果
```

三个输入，用大白话解释：

- **permission（权限）**：AI 想干什么。比如"允许写文件"、"允许执行命令"。
- **pattern（模式）**：在哪个范围上干。比如"只允许写 `/tmp/` 目录下的文件"。
- **rulesets（规则集）**：一份"规则清单"，每条规则写着：什么权限 + 什么模式 → 怎么处理（允许/禁止/询问）。

程序拿着"想干什么 + 在哪儿干"，去规则清单里找匹配的规则，然后决定：**allow（放行）、deny（拦截）、还是 ask（弹窗问用户）**。

**3. 两个值得注意的细节**

- **通配符匹配**：规则里的模式和权限都支持**通配符**（`*` 这种"匹配任意字符"的符号）。比如规则可以写"`write *`"表示"写任何文件都算这条规则管"。这样几条规则就能覆盖很多情况，不用一条条列。
- **"最后匹配的规则生效"**：代码里找规则时用的是 `findLast`——在规则列表里**从后往前找，找到最后一条匹配的就用它**。这意味着规则有优先级：**后面的规则可以覆盖前面的规则**。打个比方：先列一条宽松的默认规则（"可以读任何文件"），再在它后面列一条例外（"但不能读 `secrets/` 目录"）——因为后面的生效，例外就生效了。**这个"越靠后越优先"的设计，让规则的组合和覆盖非常灵活。**

**4. 这跟 openclaw 的"确定性策略"是同一个思路**

第二天学 openclaw 时讲到"确定性策略：安全决策不靠 AI 临时发挥，靠写死的规则"。opencode 的权限系统也是同一类设计：**用一套明确的规则表来决定"能/不能/要问"，而不是让模型自己拍脑袋。** 这几乎是所有成熟 AI 助手的共识——安全相关的决定，必须可预测、可审计。

### 一句话收获

OpenCode 的权限系统让我看懂了一个通用的授权模型：权限（干什么）+ 模式（在哪干）+ 规则集（怎么处理）→ 允许/拦截/询问，而且"后面的规则优先"让规则可以层层覆盖——安全决策用规则表，不用 AI 拍脑袋。

## 2026-09-14 学习记录

**当天版本**：commit `df23b7f` —— "feat(console): forward Go billing source"（新功能：控制台转发 Go 计费来源）。

### 今天学到了什么

**1. 背景：这个提交在改什么？**

今天 opencode 的提交很小（只改了 3 行），但里面有个有意思的知识点。先交代背景：opencode 有网页端控制台（console），用户在网页上跟 AI 对话时，请求会经过一个叫 **zen** 的中间层（可能是它的模型网关服务），再转给模型。

网页端发请求时会带上一些标记用的 HTTP 头（header，HTTP 请求的"信封信息"，用来传递额外的说明，比如"我是谁"、"要什么服务"）。其中一个头叫 `x-zen-model`（用的什么模型）。今天加了一个新头：`x-zen-billing-source`（计费来源）。

**2. 计费来源（billing source）：这笔账算到谁头上？**

新增的 3 行代码意思大致是：

- 当用户用的是 **lite（精简版）模型列表**时，设置 `x-zen-billing-source` 头，值根据用户当前的状态是 **`go`**（一种订阅/套餐模式）还是 **`credit`**（按点数/充值扣费）来定。
- 同时别忘了：在清理请求头的时候，这个新头也要跟着删掉，不能残留。

为什么要区分计费来源？因为同一个模型请求，成本从哪扣不一样：订阅用户走"套餐额度"，充值用户走"点数余额"。后端收到这个头，就知道该从哪个账本扣钱。**这教给我一个很实用的设计：把"业务信息"（这里是谁的账）通过请求头传给下游，让下游不需要自己猜。**

**3. 顺带学到的：HTTP 头的"生命周期管理"**

这个提交还有一个容易被忽略的细节：代码里加头的地方和删头的地方是**成对出现**的——设置 `x-zen-billing-source` 的同时，在"移除请求头"的逻辑里也补了删除它。为什么？因为这些头是发给模型服务商的，转发给别人的请求里不能残留你内部的标记（既是礼貌也是安全：别把内部信息漏给第三方）。**这个习惯值得学：往请求里加的每一个自定义头，都要想清楚"它在哪个环节该被删掉"，加头和删头要配对管理。**

### 一句话收获

OpenCode 的这个小提交让我看到计费系统的一角：同一个请求要按用户模式区分"从哪个账本扣钱"，通过 HTTP 头把业务信息传给下游——同时提醒我，往请求里加的每个自定义头都要管理好生命周期，加和删成对出现，别把内部标记漏给第三方。

## 2026-09-15 学习记录

**当天版本**：commit `e03db9b` —— "Merge branch 'dev'"（dev 分支的合并提交，没有具体新功能）。今天按设计思路，换个角度学它的"事件"设计。

### 今天学到了什么

**1. 背景：大系统里"事件"为什么要专门管理？**

还记得第一天学的吗？OpenCode 是一个 monorepo（一个仓库管几十个包）。一个这么大的系统里，各个包之间怎么通信？很常见的方式是**事件（event）**：某个包发生了什么事（"会话被创建了""模型回复了"），就广播一个事件，其他关心的包收到后做自己的事。

但这里有个大问题：**几十个包都会产生事件，如果每个包自己定义一套事件，名字可能撞车、格式可能不一致、改了这边忘了那边**。OpenCode 的解决办法是把所有事件集中管理。

**2. Event Manifest（事件清单）：所有事件的"户口本"**

在 `packages/opencode/src/event-manifest.ts` 里我看到：它把事件定义统一收在 **schema 包**里（`packages/schema/src/event-manifest.ts`），而且按领域分好了类，我读到的就有：

- `Event`：基础事件。
- `Durable`（`durable-event-manifest.ts`）：**持久化事件**——这类事件要落盘保存的（比如会话记录），跟"广播完就忘"的普通事件分开管理。
- `LspEvent`：跟代码编辑器智能提示（LSP，Language Server Protocol）相关的事件。
- `McpEvent`：跟 MCP（还记得 dsh 里也见过的那个"工具接入协议"吗）相关的事件。
- `ServerEvent`、`InstallationEvent`、`LegacyEvent`：服务器、安装、旧版本兼容的事件。

**3. 这个设计好在哪里？**

- **一份"户口本"，人人可查**：想知道系统里有哪些事件、长什么样，去 schema 包看清单就行，不用翻遍几十个包。
- **类型即文档**：所有事件都用 TypeScript 类型定义好，别的包引用时编译器能检查——写错字段立刻报错，不用等运行时才发现。
- **持久事件和普通事件分开**：`Durable` 单独一个文件，明确区分"要存起来的"和"广播完就忘的"。**这种区分很重要：该存的不存会丢数据，不该存的瞎存会撑爆存储。**

**4. 这跟 dsh 的"事件溯源"呼应起来了**

昨天学 dsh 时知道它把所有会话事件存成只追加日志；今天看到 OpenCode 也在 schema 层专门给**持久化事件**（Durable）划了领地。两个项目的设计不约而同：**事件是系统的"通用语言"，而"哪些事件值得存下来"是必须认真想清楚的事。** 事件清单集中管理，就是给这套语言立规矩。

### 一句话收获

OpenCode 的事件清单让我看到大系统的"通信秩序"：所有事件类型集中在一份清单里，按领域分类、类型严格、持久事件单独标注——先立好规矩，几十个包才能用同一种语言说话。

## 2026-09-16 学习记录

**当天版本**：commit `e03db9b`（dev 分支合并提交，无新功能）。今天按设计思路，学它的**插件系统**。

### 今天学到了什么

**1. 插件系统：OpenCode 怎么"接天下模型"？**

OpenCode 的卖点是"开放"——不绑定任何一家模型服务商。那它是怎么做到"随时换模型"的？答案在它的插件系统里。看 `packages/opencode/src/plugin/` 目录，一眼就能发现：**目录里几乎每个文件对应一家模型提供商**——`azure.ts`（微软 Azure）、`openai/`（OpenAI）、`github-copilot/`（GitHub Copilot）、`cloudflare.ts`、`digitalocean.ts`、`cerebras.ts`、`snowflake-cortex.ts`、`modal/`……每家一个插件。

**2. 每个插件管什么？**

从代码看，这些插件主要干两类活：

- **认证（authentication）**：每家服务商的登录方式都不一样（有的用 API 密钥，有的走 OAuth 登录，有的用账号密码），插件负责把"怎么登录这家"这件事封装好。比如 `CopilotAuthPlugin`（GitHub Copilot 的登录插件）、`CodexAuthPlugin`（Codex 的登录插件）。
- **配置接入**：把这家服务商的模型列表、默认设置接进 OpenCode，让用户能直接选。

**3. 插件的"标准接口"：怎么保证每家都能接进来？**

插件不是随便写写的，它要实现一个标准的 **PluginModule（插件模块）接口**——代码里能看到 `Hooks`（钩子，程序在特定时机让你插一脚的地方）、`PluginInput`（插件输入）、`WorkspaceAdapter`（工作区适配器）这些定义。**只要按这个标准接口写，就能被 OpenCode 的插件加载器（`loader.ts`）识别和启动。**

打个比方：这就像**国家电网的插头标准**——每家发电厂（模型服务商）发的电不一样，但只要都按国家标准的插座接口接入（实现 PluginModule），用户插上就能用。**OpenCode 自己不做发电，它做的是"电网"：定义标准接口，让所有发电厂都能接入。**

**4. 这跟我这几天学的知识连起来了**

OpenCode 的插件系统让我看到"开放"的落地方式：定义标准接口（PluginModule），让每家模型服务商各自实现接入，核心只做"电网"不做"发电"——开放生态的秘诀，就是让第三方都能按标准插进来。

**当天版本**：commit `88c6c7a` —— "fix(stats): preserve container dependency lock"（修复统计服务：保留容器里的依赖锁）。今天按设计思路，学它的 **LSP 集成**。

### 今天学到了什么

**1. LSP 是什么？—— 编辑器与语言工具的"标准插座"**

今天学 OpenCode 的 LSP（`packages/opencode/src/lsp/`）。**LSP 全称 Language Server Protocol（语言服务器协议）**，它解决一个很实际的问题：

以前，每个编辑器（VS Code、Emacs……）都要为每种编程语言专门写"代码智能"（自动补全、报错、跳转定义）。语言有几十种，编辑器有十几个——**每家都要写几百套**，累死个人。

LSP 的做法是解耦：**每种语言单独提供一个"语言服务器"（language server）**，专门懂这一种语言；**编辑器只要写一次 LSP 客户端**，就能接上所有语言服务器。像插座和电器：语言是电器（自己带插头），编辑器是插座（一个规格接所有）。微软带头搞了这个标准，现在几乎所有编辑器都支持。

**2. OpenCode 的 LSP 集成：AI 也能"看懂代码"**

OpenCode 是个 AI 编程助手，它接 LSP 不是为了给用户补全代码，而是**让 AI 拥有代码的"语义视野"**。我在它的 `lsp.ts` 里看到它调用的能力：

- `touchFile`：告诉语言服务器"这个文件变了"，触发重新分析。
- `diagnostics`：**获取诊断**——就是"哪一行有语法错误、类型错误"这类红波浪线信息。AI 拿到这个，就能先自查代码有没有问题，再动手改。
- `hover`：**悬停提示**——把鼠标放在某个符号上显示的说明，AI 可以问"这个函数是干什么的"。
- `definition`：**跳转到定义**——AI 想知道"这个函数在哪定义的"，就问语言服务器。

**3. 这个设计教给我什么？**

- **AI 不该靠"猜"理解代码，而该用标准工具**：OpenCode 没有自己实现"解析所有语言"，而是站在 LSP 这个标准肩膀上——**每种语言的专业理解，交给最懂它的语言服务器；AI 只负责用。** 这跟它做"电网不做发电"（插件系统）的思路一脉相承：**不重复造轮子，用标准接口集成最强的东西。**
- 注意它的事件设计：LSP 相关的事件走的是 `LspEvent`（还记得事件清单里专门有一类 LspEvent 吗？昨天学的知识在这里对上了）——**每一个新领域的能力，都会在事件清单里有一席之地。**

### 一句话收获

OpenCode 的 LSP 集成让我看懂"标准协议"的威力：编辑器写一次客户端就能接所有语言服务器，而 AI 助手站在这套标准上，就能拿到诊断、悬停、跳转这些"代码语义"——不自己造轮子，用标准接口集成最强的东西。

## 2026-09-18 学习记录

**当天版本**：commit `5a83358` —— "fix(console): show migrated workspaces in selector"（修复：在切换器里显示已迁移的工作区）。今天按设计思路，学它的**会话上下文管理**。

### 今天学到了什么

**1. 背景：会话"太长了"怎么办？**

第二天学 codex 时讲过"上下文窗口"（模型一次能看的内容有限）。OpenCode 作为 AI 编程助手，同样要面对这个问题：**对话越长，越接近窗口上限，最后放不下**。它在 `session/` 目录里专门放了两个文件管这件事：`overflow.ts`（溢出）和 `compaction.ts`（压缩）。

**2. 核心函数：usable（还能用多少空间？）**

`overflow.ts` 里有个 `usable` 函数，计算"现在还能塞多少内容"。它的算法很有意思：

```
可用空间 = 模型上下文上限 − 预留量（reserved）
```

关键在**预留量（reserved）**怎么算：默认取一个 **20000 token 的缓冲区**（COMPACTION_BUFFER），或者跟模型的"最大输出长度"取较小值。

**为什么要预留 2 万 token？** 因为模型回答时还要输出内容！如果上下文被历史记录塞得满满当当，模型连"写回答"的空间都没有了。所以 opencode 的做法是：**永远给"输出"留出位置**——就像一张桌子，不能摆满东西，得留一块地方给你写字。

**3. 溢出 → 压缩（compaction）**

`compaction.ts` 里引用了一个 `isOverflow`（是否溢出）函数：当"已用空间 + 新增内容"超过可用空间时，就判定溢出，触发**压缩**——把旧对话浓缩成摘要，腾出空间（第二天在 codex 学的压缩，在这里以另一个形式出现了）。

**4. 这个设计教给我什么？**

- **不要把资源用满，要留余量**：`usable` 里的预留缓冲区，是最典型的"**提前量**"设计——不是等窗口满了才慌，而是永远留出输出需要的空间。这跟人做事一样：**安排别排到 100%，留出缓冲，才不会被意外卡死。**
- 注意它的计算细节：`usable` 里还有个判断"模型有没有单独标 input 上限"，有就用 input 上限算，没有才用总上下文减输出——**不同模型的限制不一样，计算要按模型的实际能力来**，不能一刀切。

### 一句话收获

OpenCode 的会话上下文管理让我记住一个设计：永远给模型留出"输出空间"——可用空间 = 上下文上限 − 预留缓冲，对话快满时触发压缩（把旧内容浓缩成摘要）；做事和算资源一样，留余量才不会卡死。

## 2026-09-19 学习记录

**当天版本**：commit `5f9d918` —— "chore: generate"（自动生成的代码提交，无新功能）。今天按设计思路，学它的**配置系统**。

### 今天学到了什么

**1. 背景：一个 AI 编程助手的配置有多复杂？**

OpenCode 作为一个"开放"的工具（还记得插件系统吗），需要让用户配置很多东西：用哪个模型、什么权限、哪些工具、给 AI 什么指令……这些配置散在**好几个地方**：全局配置文件（所有项目通用）、项目配置文件（每个项目自己的）、命令行参数（一次性的）。今天看它的 `config/` 目录，学它怎么管理这套配置。

**2. 配置的"多层合并"**

它用了一个函数叫 `mergeDeep`（深合并）——这是配置系统的核心操作。**深合并**的意思是：把多份配置**按层级合并**成一份，而且合并是"深层的"——不是简单地把 A 盖在 B 上面，而是**一层一层地合并**：如果全局配置里有 `模型.提供商 = A`，项目配置里有 `模型.温度 = 0.7`，合并结果就是 `模型.提供商 = A + 模型.温度 = 0.7`——两家的设置都保留，互不覆盖。

打个比方：合并配置像"**叠被子**"——不是把第二床被子整个扔第一床上面（把下面的细节全盖住），而是把两个被子的每层都对齐铺好，你补充我的空缺，我保留你的细节。**深合并的价值：不同层级的配置可以各管一摊，互不打架。**

**3. 解析的宽容度：支持 JSONC**

它用了一个叫 `jsonc-parser` 的库来读配置文件。**JSONC** 是 JSON 的"宽容版"——JSON 是严格的文本格式（不许注释、不许尾逗号），而 JSONC 允许写**注释**和**多余的逗号**。为什么要支持？因为配置文件是给人写的，人写配置时很想加注释解释"这一项是干嘛的"，JSON 不让写，JSONC 让写。**工具要体贴"写配置的人"：允许注释、允许多一点宽容，配置体验完全不同。**

**4. 这个设计教给我什么？**

- **配置系统的本质是"解决冲突"**：多个来源的配置（默认值、全局、项目、命令行）总有冲突，深合并 + 层级优先级就是解决冲突的机制。**越开放的工具，配置来源越多，越需要一套清晰的合并规则。**
- **配置要"好写"**：支持注释、宽容解析、友好的报错（这目录里还有 `parse.ts` 专门管解析和报错）——这些细节决定了用户是"愿意配置"还是"被配置劝退"。**工具的用户体验，一半藏在配置体验里。**

### 一句话收获

OpenCode 的配置系统让我看到"多层配置怎么不打架"：靠深合并把全局、项目、命令行各层配置逐层对齐（各管一摊、互不覆盖），再靠 JSONC 这种宽容格式让写配置的人能加注释——配置系统的本质是解决冲突，体验的一半藏在解析的宽容度里。

## 2026-09-20 学习记录

**当天版本**：commit `83abc64` —— "chore(ci): refresh v2 models.dev snapshot on a schedule"（用一个定时任务，定时刷新内置的"AI 模型清单"）。

### 今天学到了什么

**1. 背景：OpenCode 需要一份"常新"的模型清单**

OpenCode 要用各种 AI 模型（还记得吗？它是给 AI 编程助手用的终端工具）。它内置了一份**模型清单（models snapshot）**——一个文件，记录了"现在市面上有哪些模型、每个模型有什么能力、怎么收费"（文件在 `packages/core/src/models-dev/snapshot.txt`）。AI 模型这个圈子更新极快：今天新出个模型、明天某个模型改价、后天又下架一个。**如果这份清单不更新，OpenCode 就会"不认识"新模型，或者按过期的价格/能力来用。**

**2. 做法：让 GitHub 的定时任务（cron）来"养"这份清单**

人工更新清单显然不现实（谁能天天盯着模型圈）。OpenCode 的做法是：**写一个 GitHub Actions 定时任务，每 30 分钟自动跑一次**（配置文件在 `.github/workflows/models-snapshot.yml`）。这个任务的流程是：

1. **自动触发**：通过 `schedule` 里的 cron 表达式 `*/30 * * * *`（每 30 分钟执行一次），也支持手动触发（`workflow_dispatch`）。
2. **自动刷新**：跑一个脚本，从模型的权威来源拉最新数据，重新生成清单文件。
3. **有变化才提交**：检查清单文件有没有变化——**没有变化就安静退出**（输出一句"没有变化要提交"就结束）；**有变化才提交并推送**回仓库。

这跟你现在用的"每日定时学习任务"是同一个思路：**把"定期要做、但内容不固定"的维护工作，交给机器按固定节奏去做**，人不用记着，也不用天天手动来一遍。

**3. 三个值得学的细节**

- **先检查再提交，避免"空提交"噪音**：每 30 分钟跑一次，绝大多数时候清单根本没变。任务先 `git status` 看文件有没有变，没变就退出——**频繁检查、按需动作**，不制造一堆"什么都没改"的提交，也不浪费别人看历史的时间。
- **防"撞车"的并发控制**：定时任务每 30 分钟一次，万一上一次还没跑完（仓库慢、网络卡），下一次又开始了，两个任务同时提交、推送就会打架。它用 `concurrency` 把同一个任务的任务归成一组，并且**不取消正在跑的那次**（`cancel-in-progress: false`），让它们排队；推送前还先 `git pull --rebase`（拉取同步再推送），避免"我推的时候仓库已经被别人改了"的冲突。**定时任务要防"重复跑"和"互相打架"。**
- **用机器人身份提交，不用个人账号**：提交用的不是某个开发者的私人账号，而是一个专门的"机器人"身份（GitHub App，通过 `OPENCODE_APP_ID`/`OPENCODE_APP_SECRET` 配置）。这样以后翻历史，一眼能看出"这类提交是自动维护的"，跟人类开发者的提交分开。**自动化的"署名"要独立、可区分。**

**4. 这个提交教给我什么？**

- **"常新数据"要交给自动化维护**：凡是"外部世界总在变、而程序需要跟得上"的数据（模型清单、价格表、汇率、组件版本），靠人手动更新必然过期，**写一个定时任务让它自己刷新、自己提交，是治本的方案。**
- **定时任务也要讲究"克制"**：不是每次跑都要有产出——没变化就安静，有变化才动作；还要防并发撞车、用独立身份署名。**一个"懂分寸"的定时任务，比一个"勤快但毛躁"的定时任务可靠得多。**

### 一句话收获

OpenCode 的定时刷新让我看到"自动化维护一份常新数据"的完整套路：用 cron 每 30 分钟自动跑、有变化才提交（没有就安静退出）、用并发控制防两个任务撞车、用机器人身份署名——**把"跟着世界变化走"这种琐事交给机器，人类只管设定好节奏和规则。**

## 2026-09-21 学习记录

**当天版本**：commit `d870e22` —— "fix(stats): retry transient query failures"（查询遇到"瞬时故障"时自动重试）。

### 今天学到了什么

**1. 背景：查数据库偶尔会"卡一下"，但这不是代码的错**

OpenCode 有一个统计（stats）功能，会去查数据库拿数据。这里有个很现实的工程问题：**网络查询偶尔会失败，但失败的"原因"并不一样**。

- 有的是**永久性错误**：比如 SQL 写错了（语法错误）、登录凭证不对（认证失败）、查询的行数超了限制——**这种错误，重试一万次也是同样的结果**，因为错在请求本身。
- 有的是**瞬时故障（transient failure）**：比如网络超时、服务端临时过载、接口暂时抽风（返回"太多请求"429 或"服务器错误"5xx）——**这种错误，过一会儿自己就好了**，重试一下很可能就成功了。

问题在于：如果代码一遇到失败就放弃，那些"明明过一秒就能成功"的查询就白白失败了，用户看到的统计数据就会缺一块。但如果见错就盲目重试，又会把"永久性错误"也反复重试，浪费时间。

**2. 做法：给查询加上"挑着重试"的逻辑**

这个提交给 SQL 查询加了一个重试逻辑，我把它拆开看，每一处都值得学：

- **只重试"当前这一页"**：代码注释写得很清楚——"只重试这一页；一个瞬时超时不应该丢掉整个显示窗口的回填"。OpenCode 的数据是分页加载的，一次查一页。**如果重试就把整个分页流程从头再来，代价太大；只重试失败的那一页，别的地方都不受影响。** 这是"重试的粒度"问题：**重试要尽量小，小到只覆盖失败的那一步。**
- **最多重试 2 次，用"指数退避"**：`times: 2`（最多重试 2 次），退避（两次重试之间的等待）用 `Schedule.exponential("5 seconds")`——**第一次失败等 5 秒再试，再失败等更久**（指数退避：间隔按 5 秒、10 秒、20 秒……往上翻）。为什么退避要越来越慢？因为"瞬时故障"常常是服务端过载，**如果大家失败后都立刻疯狂重试，反而把服务压得更垮**；越退越慢，是给服务留喘气的机会。
- **重试条件写得明明白白**：只有这三种情况才重试——错误码是 `40005`（R2 服务特有的临时错误码）、状态码是 `429`（太多请求）、状态码大于等于 `500`（服务器错误）。**其余的错误（语法错、认证错、行数超限）一律不重试，直接失败。**

**3. 这个提交教给我什么？**

- **重试之前先问："这个错，重试有用吗？"** 把错误分成两类：**瞬时故障值得重试（网络抖一下、服务打了个盹），永久性错误不值得（请求本身有问题，重试只会重复浪费时间）**。判断标准就是错误码和状态码——代码里把"该重试的"和"不该重试的"用条件明明白白地列出来，一眼能看懂。
- **重试的"粒度"越小越好**：只重试失败的那一步（那一页），而不是把整个大操作推倒重来。**重试是"补考"，不是"重读一遍书"。**
- **重试要有限度、要退避**：设次数上限（2 次），间隔越来越长（指数退避）。**无限重试和拼命重试，都会把"瞬时故障"变成"持久故障"。**

### 一句话收获

OpenCode 的重试修复让我看到"怎么优雅地跟不稳定的网络打交道"：把错误分成"瞬时故障"（超时、429、5xx，值得重试）和"永久性错误"（语法错、认证错，重试无用），只对前者重试；而且只重试失败的那一页、最多 2 次、间隔指数退避越来越慢——**重试不是无脑再来一次，而是"挑对的错、用对的节奏、止于该止处"。**

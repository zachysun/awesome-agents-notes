# Hermes Agent（Nous Research 的"会自我改进"的 AI 智能体）

这个项目是 Nous Research 做的 **Hermes Agent**，它的卖点一句话概括：**它是唯一内置了"学习闭环"的智能体**。普通 AI 助手用一次忘一次，Hermes 却会在干活的过程中积累经验：遇到复杂任务，它会自己总结出一套方法存下来（叫 **skill**，技能），下次再遇到类似任务就用得更好；它还会记住关于你的事（记忆），跨会话持续了解你。

它不绑定在你的笔记本上：同一个核心可以跑在 CLI（命令行）、桌面应用、或者一个常驻的 **gateway**（网关，一个负责接各聊天平台的程序）里。你可以通过 Telegram、Discord、Slack、WhatsApp 等约 20 个平台跟它对话，它却是在云服务器上干活的。它还能用任何模型（OpenAI 的、DeepSeek 的、自己搭的），随时切换，不锁死在一家。

几个关键概念（大白话版）：

- **记忆（memory）**：AI 跨会话记住的关于你的信息。Hermes 有一整套记忆管理机制，还不止一种"记法"。
- **技能（skill）**：一段写好的"工作方法说明书"，告诉 AI 某类任务该怎么干。普通助手靠系统自带的技能，Hermes 的厉害之处是它能**自己从经验里创造新技能**。
- **学习闭环**：指"干活 → 总结 → 下次干得更好"这个循环。这是 Hermes 区别于其他助手最核心的东西。
- **网关（gateway）**：一个中间程序，把 Telegram、Discord 这些平台的聊天消息接进来，转给 AI 核心处理，再把回复送回去。

## 2026-09-11 学习记录

**当天版本**：commit `6c3d4a4af7` —— "fix(desktop): resolve plugin SDK namespaces lazily, not at module scope"（修复桌面端：插件 SDK 的命名空间改为"用到时才解析"，而不是在模块加载时就解析）。

### 今天学到了什么

**1. 记忆是怎么管理的？（memory_manager.py）**

我读了它的 `agent/memory_manager.py`，发现记忆管理器的设计思路很清晰：它自己不存记忆，而是把"记忆动作"**分发给注册好的记忆提供者（provider）**。打个比方：它像一个"记忆总台"，各家记忆服务（比如一个本地数据库、一个云服务）都可以来登记"我能记东西"，总台负责把该记的都广播给它们。

有个细节很有意思：内置的记忆提供者永远被允许，但**外部插件记忆提供者只能同时注册一个**。为什么？因为每个提供者都会往模型发送的工具清单（tool schema，告诉模型"你可以调用哪些能力"）里塞内容，塞多了会撑大每次请求的开销、还可能互相打架。所以设计者宁可限制"只准一个"，也不让记忆能力无限膨胀。**这体现了一种克制：不是能加就加，而是考虑每次调用的代价。**

**2. 技能目录是"会成长的"（skill_utils.py）**

`skill_utils.py` 里管理技能目录。注意它有几个"不看"的目录（`.git`、`.venv`、`node_modules` 这些），避免把无关文件夹误认成技能。它还支持"渐进式展开"（progressive disclosure）：一个技能包可以把参考资料、模板这些辅助文件放在 `references/`、`templates/` 子目录里，平时不加载，只有 AI 明确要看某个文件时才去读——这样不浪费每次对话的上下文空间。**这个思路对新手很有启发：信息不是一股脑全塞给 AI，而是"按需取用"。**

**3. 项目 AGENTS.md 里两条"神圣不可侵犯"的原则**

- **每个会话的提示词缓存（prompt caching）是神圣的**。大白话解释：跟 AI 长聊时，每次请求都会带上"系统提示词"（一段很长的背景说明），模型服务商会把这段开头缓存起来、重复使用，这样用户省钱。一旦你在对话中途改了提示词或工具列表，缓存就作废，费用成倍增加。所以 Hermes 规定：能不改就不改，只有"压缩上下文"这一个例外，而且有些修改默认延迟到下次会话才生效（除非用户明确说"立刻生效"）。
- **核心要窄（narrow waist），能力在边缘**。意思是：AI 每次调用都要把"所有核心工具"发一遍，所以往核心加一个工具，代价是每次调用都变贵。因此新能力优先做成命令行 + 技能、插件、MCP 服务器（一种标准的工具接入协议），核心只保留最通用的骨架。

**4. 今天这个修复在讲什么？**

`6c3d4a4af7` 修复的是桌面端的插件加载性能问题：以前插件模块一加载就把所有 SDK 命名空间都解析好（浪费启动时间），现在改成"哪个命名空间真被用到了才解析"。这种"延迟加载"（lazy loading）是性能优化的常见手法：**别一口气把所有东西都准备好，用到什么准备什么**。

### 一句话收获

Hermes 让我看到"AI 助手"和"AI 同事"的区别：记忆 + 技能 + 跨会话的学习闭环，让 AI 从"每次从零开始"变成"越用越懂你"——但它的代价管理（缓存、核心宽度）同样值得敬畏。

## 2026-09-12 学习记录

**当天版本**：commit `bf51fee548` —— "docs(multiplex): make the multiplexed-gateway page match what the code does"（修正文档：让"多路复用网关"的说明和代码实际行为一致）。

### 今天学到了什么

**1. 多路复用（multiplex）：一个网关，服务多套独立配置**

昨天提到 Hermes 有网关（gateway，负责接通各聊天平台的常驻程序）。今天这个提交讲的是网关的一个高级用法：**multiplex（多路复用）**。大白话解释：平时一个网关服务一套配置；多路复用让**一个网关进程同时服务好几套完全独立的配置**。

在代码里我读到，每套配置有自己的 **profile home**（配置主目录，通过 `HERMES_HOME` 环境变量指定）。多路复用模式下，网关同时加载多个 profile，比如：

- 一个默认 profile：你自己日常用的。
- 另一个 profile：给公司/团队的 Slack 机器人用的，模型预算、频道设置全都不一样。

关键点在于**隔离**：代码里专门写了逻辑，保证"第二个 Slack 机器人"不会继承默认 profile 的设置（比如默认 profile 忽略的频道列表、模型最大轮数）。每套配置独立读取、独立生效，互不串味。

**2. 为什么要有这种设计？**

想一想场景：你想让一个 AI 助手同时服务"个人私聊"和"团队频道"，但两边的规则完全不同——个人那边可以放手让它干，团队那边要限制它每轮最多干多少步（代码里叫 `agent.max_turns`，一次任务最多执行的轮数）。如果共用一套配置，就得在两边来回切换设置，非常容易出错。

多路复用就是为这种"一个程序、多套规则"的场景准备的：**不是复制几份程序，而是让一个程序按 profile 区分对待。** 这里我还注意到代码里有个细节：`max_turns` 这种"一次进程只装得下一个值"的设置，在复用模式下必须从各自的 profile 里单独读，否则所有 profile 都会共享第一个 profile 的值——这种"全局变量陷阱"在多路复用里要特别小心。

**3. 今天的提交为什么是"文档修正"？**

`bf51fee548` 是个文档提交，内容是"让文档和代码实际行为一致"。这提醒我一个观念：**文档不是写完就完事的，代码改了文档就得跟上**。很多项目里"文档和代码不一致"比"没有文档"更坑人——照着文档操作会得到错误结果。所以定期校正文档、让说明和现实对齐，是很实在的维护工作，不丢人。

### 一句话收获

Hermes 的多路复用让我看到"一个程序服务多套配置"背后的坑与解法：配置要按 profile 隔离、全局变量要小心、文档要和代码同步——越灵活的能力，越需要明确的边界。

## 2026-09-13 学习记录

**当天版本**：commit `d595e636c8` —— "fix(model): a selected model id is never rewritten to a catalog neighbour"（修复：用户选定的模型 ID 永远不会被改写成目录里的"邻居"）。

### 今天学到了什么

**1. 背景：Hermes 支持很多模型，它是怎么管理的？**

Hermes 可以接很多家的模型（OpenAI、DeepSeek、自己搭的等等），所以它维护了一个**模型目录（model catalog）**——一张预置的"模型清单"，里面记录着各家的模型：ID 叫什么、能干什么、有什么限制。用户通过 `hermes model` 命令选模型时，就是在跟这个目录打交道。

**2. 这个 bug 是什么？—— 好心办坏事的"自动纠错"**

`d595e636c8` 修的是个很有意思的 bug。场景是这样的：

除了目录里的预置模型，Hermes 也允许用户**自定义模型**（比如你自己搭了一个服务，给它起个 ID 叫 `my-llama`）。但旧代码在切换模型时，会做一层"自动修正"：如果发现用户选的 ID 在目录里找不到，就自作主张把它替换成目录里**名字相近的另一个模型**（代码里叫"邻居"，neighbour）。

后果很坑：用户明明选的是 `my-llama`，实际跑起来的却是目录里的 `llama-3-8b` 之类"看起来差不多"的模型。模型不对，回答风格、能力全都不对，用户还不知道怎么回事。

**3. 修复原则：用户明确指定的，就原样保留（verbatim）**

修复的核心原则在测试名里写得很清楚：**"unlisted id on user provider is kept verbatim"**——不在目录里的自定义 ID，必须**原样保留**，一个字都不许改。代码里还专门删掉了给用户配置里写"哨兵键"（sentinel keys，程序内部使用的标记字段）的行为，让用户的配置干干净净。

**4. 这个 bug 教给我什么？**

- **自动化要尊重用户的明确意图**：当用户手动指定了一个值，系统就不该再"聪明地"改写它。自动纠错只应该用在"用户没明确说"的地方，否则纠错就是添乱。
- **每个修复都要有测试钉死**：这个提交专门新增了测试文件（`test_model_switch_user_provider_slug_verbatim.py`）锁死"ID 原样保留"这个行为，防止以后有人又把它"修"回去。**没有测试保护的修复，等于没修。**

### 一句话收获

Hermes 的这个修复让我记住：系统可以给用户建议，但用户明确指定过的值必须原样执行——"自动纠错"一旦盖过用户的明确选择，就是好心办坏事。

## 2026-09-14 学习记录

**当天版本**：commit `a7254e2d4c` —— "fix(profiles): unroute a renamed profile whenever a live default multiplexer exists"（修复：只要有活跃的默认多路复用器存在，重命名过的 profile 就要被取消路由）。

### 今天学到了什么

**1. 背景：profile 和"路由"是什么关系？**

第三天学了 Hermes 的多路复用（一个网关服务多套 profile）。今天这个修复接着这个话题，但主角变成了**路由（routing）**。

先解释概念：多路复用模式下，一个网关同时服务好几个 profile（每套独立配置）。**路由**就是"决定这条消息该交给哪套 profile 处理"的动作——你从 Telegram 发消息，网关要判断这属于默认 profile 还是团队的 profile，然后送对地方。

**2. 今天的 bug：profile 被重命名之后，路由乱了**

场景是这样：你有一个 profile 叫 `work`，网关正在服务它。然后你把它重命名为 `personal-work`。如果系统没处理好，会发生什么？

- 旧名字 `work` 可能还残留在某些配置或网关的路由表里。
- 消息来了，网关按旧名字去找 `work`，发现找不到了，路由就出问题——消息可能送错 profile，或者直接被丢弃。

**3. 修复思路：重命名后要"取消路由"（unroute）**

代码里我看到修复的关键逻辑：

- 有个检查函数 `_served_by_running_multiplexer`（"这个 profile 是不是正被运行中的多路复用器服务"）。
- 当一个 profile 被重命名时，只要它正被活跃的多路复用器服务，就执行 **unroute（取消路由）**——把旧名字从服务名单里摘掉，不再让它接收消息。

这里其实藏着一个通用的工程原则：**"改名"不是简单改个字，凡是系统里"按名字找东西"的地方，改名都要同步更新，否则就会留下指着旧名字的"断头路"。** 就像公司里一个人改名了，工牌、门禁、通讯录都要跟着改，漏一个就进不了门。

**4. 顺带学到的：创建 profile 时的"通知机制"**

代码里还有个 `_notify_multiplexer`（通知多路复用器）函数：新建一个 profile 时，不能光把目录建好就完事，还要**通知正在运行的多路复用器重新扫描**，让它马上开始服务新 profile。**这教给我：配置文件改了，运行中的程序不会自己知道——要么轮询、要么主动通知，动静要传到"正在干活的人"那里才算数。**

### 一句话收获

Hermes 的这个修复让我看到"重命名"在运行系统里的连锁反应：名字一旦被路由表引用，改名就必须同步"取消旧路由"，否则就是断头路——改名字永远不只是改一个字的事。

## 2026-09-15 学习记录

**当天版本**：commit `40f2702b22` —— "feat(desktop): chat/UI font picker (desktop.font_family) for readability faces"（桌面端新增字体选择器）。今天按设计思路，重点学它的内置定时任务系统。

### 今天学到了什么

**1. 背景：AI 助手也能"定时干活"**

Hermes 有个很实用的内置能力：**定时任务（cron）**。还记得第一天 README 里提到的吗？"每天的报告、每晚的备份、每周的审查——用自然语言说一声，它就会定时自动跑。" 今天我就去看了它定时任务的实现（`cron/` 目录），发现里面藏了不少讲究的工程设计。

**2. 任务存在哪、结果输出到哪？**

代码开头的注释就把存储结构说清楚了：

- 任务清单存在 `~/.hermes/cron/jobs.json`（一个 JSON 文件，记录所有定时任务）。
- 每次执行的输出存在 `~/.hermes/cron/output/{任务ID}/{时间戳}.md`（每个任务一个文件夹，每次执行一个带时间戳的文件）。

**这个设计简单但很清晰：任务定义（jobs.json）和任务产物（output/）分开存放，每次执行的结果都留档，可以回看。** 它还用了 **croniter** 这个库来解析 cron 表达式（比如 `0 9 * * *` 这种"每天 9 点"的写法），这说明它用的是标准的定时表达式语法，不是自己发明一套。

**3. 两个"小而关键"的可靠性设计**

- **跨进程文件锁**：`jobs.json` 是多个程序进程可能同时读写的文件（定时器、CLI、网关都可能动它）。代码里用了**文件锁**（Unix 上用 `fcntl`，Windows 上用 `msvcrt`）来防止两个进程同时改它导致文件损坏；如果平台两个都不支持，就退化成进程内锁，而不是直接报错。**这教给我：共享文件被多进程读写时，要加锁；而且锁的实现要"降级可用"，不能因为没有锁就整个功能瘫痪。**
- **原子写入（atomic write）**：它用 `atomic_replace`、`atomic_write_text` 这些工具写文件。**原子写**的意思是：先写到一个临时文件，再一次性"替换"到目标位置——这样即使写一半断电，也不会留下一个写坏的半成品文件（要么是旧完整文件，要么是新完整文件，绝不会是中间状态）。**写重要文件用"先写临时再替换"，是防止文件损坏的标准手法。**

**4. 跟今天的字体选择器提交有什么关系？**

顺带提一句今天的提交（桌面端字体选择器）：它让用户可以在设置里指定聊天界面的字体（`desktop.font_family`）。这个功能本身不复杂，但它说明 Hermes 的桌面端在不断打磨"可读性"这类体验细节——功能都稳定后，优化的是眼睛舒服不舒服这种小事。**好产品在功能做全之后，开始抠体验细节。**

### 一句话收获

Hermes 的定时任务系统让我看到"让 AI 定时干活"背后的可靠性设计：任务定义和输出分开存、跨进程文件锁防止写坏、原子写防止半成品——定时任务听起来简单，做可靠了全是细节。

## 2026-09-16 学习记录

**当天版本**：commit `416a8177c2` —— "perf(plugins): scan each plugin's source for removed imports once per process, not once per profile"（性能优化：每个进程只扫描一次插件源码，而不是每个配置档都扫一次）。

### 今天学到了什么

**1. 背景：Hermes 启动时要"扫描插件"**

还记得第三天学的吗？Hermes 有很多插件，还会检查插件的兼容性。这个提交涉及的场景是：启动时，Hermes 要**扫描每个插件的源码**，检查有没有"被移除的导入"（removed imports，插件代码里引用了某些已经不存在的东西），这是插件兼容性检查的一部分。

**2. 问题：同一个扫描，被重复执行了很多遍**

先看它为什么慢。还记得多路复用网关吗？一个网关同时服务好几个 profile（配置档），而**每个 profile 启动时都会"发现"一次插件**。也就是说：如果网关服务 5 个 profile，同一个插件的源码就要被完整解析 **5 遍**。代码注释里算了笔账：**每个 profile 重新解析全部插件源码，大约慢 0.4 秒 × profile 数量**——profile 一多，启动就要多等好几秒。

**3. 解法：签名缓存（signature cache）——"文件没变就用缓存"**

它加了一个进程级的缓存（`_scan_cache`），思路非常经典：

- 给插件目录算一个**签名**：把里面每个 `.py` 文件的 `(相对路径, 修改时间纳秒, 文件大小)` 汇总起来，得到一个唯一的"指纹"。
- 扫描之前先看签名：**如果签名没变，说明文件没动过，直接用缓存里的结果，不重新解析**；签名变了（说明有人改过插件），才重新扫描并更新缓存。
- 注释里还量化了收益："一次 stat 遍历（查文件属性）大约 1 毫秒，而它替代的 AST 扫描（把源码拆成语法树来理解）每个文件大约要 10 毫秒"——**查属性比解析源码便宜 10 倍**，所以用便宜的检查代替贵的解析。

**4. 这个设计教给我什么？**

- **缓存的关键是"怎么知道缓存有没有过期"**：这里用"文件指纹"（路径 + 修改时间 + 大小）判断，文件没变就复用，不重算。这是所有缓存系统的核心问题——**不是"什么时候缓存"，而是"怎么安全地判断缓存还新鲜"**。
- **用便宜的检查代替贵的计算**：与其每次真刀真枪解析源码（10ms/文件），不如先看一眼文件属性（1ms）来判断要不要解析。**性能优化的常见套路：用低成本的"指纹判断"挡住大部分高成本的重复计算。**
- 这个优化同样发生在"多路复用"的场景里——**多个 profile 共用一个进程，正好可以把跨 profile 的重复工作合并到进程级只做一次。**

### 一句话收获

Hermes 的插件扫描优化让我看到缓存的标准姿势：给文件算个指纹（路径+修改时间+大小），没变就用缓存、变了才重扫——用 1ms 的便宜检查挡住 10ms 的昂贵解析，而且"多 profile 共用进程"正好让缓存一次生效多处受益。

## 2026-09-17 学习记录

**当天版本**：commit `260da4ef62` —— "fix: catalog installs no longer block on caution; admission runs the same scanner"（修复：插件目录的安装不再被"谨慎检查"阻塞；正式接纳时才运行同一个扫描器）。

### 今天学到了什么

**1. 背景：插件的"目录"和"安装"**

Hermes 有一个**插件目录（catalog）**——一个收录了各种可用插件的"商店"（还记得第二天学的"技能目录"吗？类似的思路）。用户可以从目录里安装插件。安装之前，系统自然要做一些**安全检查**，看看这个插件干不干净、有没有引用已经不存在的东西（还记得昨天学的"移除导入扫描"吗？就是它）。

**2. 问题：安全检查卡住了安装流程**

旧的行为是：安装插件时，安全检查（这个提交里叫 **caution，谨慎检查**）不过关，**安装就被阻塞**。听起来挺合理？但实际会带来麻烦：

- "谨慎检查"可能因为**网络、签名、环境**等原因迟迟没结果或误报——用户只是想装个插件，却被一道"可能还没准备好的检查"卡住，体验很差。
- 而且，用户从目录装插件这件事，本身已经过了目录的初步筛选，不该被一道"全量深度检查"在门口拦死。

**3. 解法：把"安装"和"准入"分开**

修复的思路是把**两个时机**分开：

- **安装时（catalog installs）**：不再被谨慎检查阻塞。安装先顺利进行——用户能拿到插件、能用起来。
- **正式接纳时（admission）**：等插件真正要"准入"（正式进入运行环境、被系统承认）时，才运行**同一个扫描器**做全面检查。检查不过就不准入，但已经安装的插件不会被"删掉"或阻塞。

这个设计教给我一个通用原则：**"先让你能用"和"正式承认你"可以是两步。** 就像你搬进新公寓：可以先进屋住（安装），但正式"入住登记、录入业主系统"（准入）时要过完整审核。**把"轻量的放行"和"严格的验收"放在不同时机，用户不被卡，安全也不丢。**

**4. 顺带学到的："同一个扫描器"**

注意提交里说"准入运行**同一个**扫描器"——不是准入时另写一套检查逻辑，而是复用安装流程里那套扫描器。**同一份检查逻辑，在不同时机被调用**：不写两套"检查"，避免两套逻辑悄悄不一致（还记得 openclaw 学的"测试契约共享"吗？同一个道理——重复的逻辑副本迟早会分叉）。

### 一句话收获

Hermes 的"安装不再被谨慎阻塞"让我看到时机设计的分寸：先轻量放行（安装不卡），后严格验收（准入时跑同一个扫描器全面检查）——用户不被阻塞，安全不放松，检查逻辑也只写一份。

## 2026-09-18 学习记录

**当天版本**：commit `d04f6f7913` —— "fix(env): import dotenv internals lazily so stubbed dotenv modules still import env_loader"（修复：延迟导入 dotenv 的内部模块，让被打桩的 dotenv 模块仍能导入 env_loader）。

### 今天学到了什么

**1. 背景：dotenv 和 env_loader 是什么？**

先解释两个词：

- **dotenv**：一个流行的工具库，作用是**从 `.env` 文件里读配置**（`.env` 是放密钥、环境变量的文件，还记得之前说过 `.env` 只放秘密吗）。
- **env_loader**：Hermes 自己的"环境加载器"模块，负责启动时把各种环境配置加载进来。它依赖 dotenv 来读 `.env`。

**2. 问题：顶层导入把"测试打桩"搞坏了**

这个修复的标题有点绕，拆开看。**导入（import）**是 Python 里"引用另一个模块"的动作。Python 代码常在文件**开头**就导入所有依赖，这叫**顶层导入**——文件一加载，依赖就全部跟着加载。

麻烦出在测试场景：测试时，程序员经常用 **stub（打桩）**——用一个假的模块替换掉真的 dotenv，来控制它的行为（比如假装读到了某些配置）。但如果 env_loader 在**顶层就导入 dotenv**，那么"文件一加载就导入 dotenv"这个动作会发生**在打桩之前**——结果：真 dotenv 已经被加载了，打桩的假 dotenv 没机会顶上去，测试就失效了。

**3. 解法：延迟导入（lazy import）——用到才导入**

修复很简单：把 dotenv 的导入从"文件开头"挪到"真正用到 dotenv 的代码里"。这样：

- 文件加载时**不会**立刻导入 dotenv。
- 测试可以先打完桩，再到代码真正用 dotenv 时，导入的就是那个"假的"。
- **打桩能生效，测试变可控。**

**4. 这个修复教给我什么？**

- **顶层导入不只是"风格问题"，它影响行为的时机**：什么时候导入，决定了"打桩/替换"能不能生效。所以依赖注入、模拟测试这类技术，都对"导入时机"很敏感。
- 这已经是这周第二次遇到"延迟加载"了（第六天 dsh 的启动加速也靠它），但用途完全不同：dsh 用延迟加载**省性能**，hermes 用延迟导入**保测试可控**。**同一个手段，在不同场景解决不同问题**——"用到才加载"既是性能优化，也是让外部依赖可被替换的设计。

### 一句话收获

Hermes 的 dotenv 修复让我看到"导入时机"的讲究：顶层导入会让测试打桩失效（真模块先加载了，假的没机会顶上），改成"用到才导入"后打桩才能生效——延迟加载既是性能优化，也是让依赖可被替换的关键。

## 2026-09-19 学习记录

**当天版本**：commit `a51143fbbe` —— "fix(bedrock): resolve application-inference-profile ARNs before the prompt-cache allowlist match"（修复 AWS Bedrock：在提示词缓存白名单匹配之前，先解析应用推理配置的 ARN）。

### 今天学到了什么

**1. 背景：AWS Bedrock、ARN、提示词缓存**

这个提交的标题里全是缩写，先逐个拆开（正好练练"术语第一次出现必须解释"）：

- **AWS Bedrock**：亚马逊云的一个服务，让你能调用各种 AI 模型（Anthropic、Meta 等的模型都在上面）。Hermes 支持通过它用模型。
- **ARN**：Amazon Resource Name，亚马逊云里每个资源的**唯一身份证号**，长这样：`arn:aws:bedrock:us-east-1:123456789012:inference-profile/xxx`。云服务靠 ARN 区分"你说的到底是哪个资源"。
- **提示词缓存（prompt cache）**：还记得第二天学的吗？对话每次请求都带上很长的系统提示词，服务商把开头缓存起来重复用，能省钱。**白名单（allowlist）**就是"哪些内容可以走缓存"的名单。

**2. 问题：拿"没解析的 ARN"去匹配白名单，匹配不上**

Bedrock 的配置里，用户可能写一个**简写**（比如只写资源名 `my-profile`），而不是完整的 ARN。旧代码直接把简写拿去跟缓存白名单匹配——结果当然对不上（白名单里存的是完整 ARN 格式）。**修法：先解析（把简写补全成完整 ARN），再拿完整 ARN 去匹配白名单。**

**3. 这个修复教给我什么？**

- **匹配之前先归一化（normalize）**：这是数据处理里最常见的坑之一——**两个值长得很像但不是同一种格式，直接比较必然失败**。正确做法是先把两边都统一成同一种"标准格式"，再比较。就像比较日期："2026年9月19日"和"09/19/2026"看着差不多，不归一化就是比不出相等。
- **顺序很重要**："先解析、后匹配"——步骤的顺序错了，后面全错。代码注释里专门强调这个顺序，说明这是出过真实事故的地方。**修 bug 时，"步骤顺序"往往是最后被怀疑、却又最致命的因素。**

### 一句话收获

Hermes 的 Bedrock 修复让我记住"先归一化再匹配"：拿没解析的 ARN 去比对缓存白名单必然失败，得先把简写补全成标准格式再比较——两个值格式不统一，看着再像也匹配不上。

## 2026-09-20 学习记录

**当天版本**：commit `8a92051f20`（今天是一个合并提交，没有实质代码改动）。既然没有新代码，今天换个角度：学 hermes 的**离线评估脚本（offline eval）**——一个专门用来检验"审批拦截"有没有失效的测试（文件在 `evals/approval_deny_dispatch.py`）。

### 今天学到了什么

**1. 背景：hermes 的"审批"和它的"拒绝名单"**

回忆一下之前学的：hermes 在让 AI 执行命令前，会走**审批（approval）**流程——有些危险命令必须经过人同意。审批配置里可以写**拒绝名单（deny）**，比如：

```yaml
approvals:
  deny: ["sudo *", "printf SAFE", "git status"]
```

意思是：凡是匹配这些规则的命令，**一律拦下，不许执行**。比如 `sudo -n id -u`（用最高权限运行一个查询命令）应该被直接拒绝。

但问题来了：**"拦命令"这件事，真的拦得住吗？** 一个老练的攻击者（或者只是 AI 不小心）可以用各种花招绕过拦截——比如用 `env` 包一层、用 `bash -c` 转一道、把命令藏进 `printf` 的参数里。hermes 的开发者显然很担心这一点，所以专门写了一个评估脚本，把几十种"绕过姿势"挨个试一遍，看拦截到底牢不牢。

**2. 方法一：拿"假靶子"代替真命令，测试绝不碰真的**

这个脚本开头第一句话就声明："绝不调用特权命令"（never invokes a privileged binary）。那它怎么测？它**自己做了一个假的 `sudo` 脚本**：一个极小的 shell 脚本，内容就是打印一行"OWNED_EXECUTABLE_REACHED"（"我的假命令被触发了"）。然后它把环境变量全部清空，把 `PATH`（命令搜索路径）指向放假 sudo 的那个临时目录。

这招太聪明了：如果某个"绕过姿势"真的骗过了拦截，系统就会执行到那个假 sudo，输出"OWNED_EXECUTABLE_REACHED"——**测试立刻就能看见"拦截被击穿了"**。全程没有碰过真正的 sudo，零风险。**在沙箱里用"诱饵"做危险测试，是安全测试的标准姿势：测试要验证的只是"拦截在不在"，没必要真的引爆危险。**

**3. 方法二：列一张"绕过清单"，把所有伪装姿势都试一遍**

脚本里有一个长长的列表，全是试图骗过拦截的命令，我数了数有几十条，大致分成几类：

- **套壳类**：`env -i sudo ...`（用 env 包一层）、`command sudo ...`（用 command 转一道）、`true && sudo ...`（前面加个真值）、`bash -c "sudo ..."`（塞进 bash 里）。
- **藏字类**：`printf '%s\n' 'sudo -n id -u'`（把命令拼进 printf 的字符串里，让系统看到的是 printf 而不是 sudo）。
- **env -S 变体**：`env -S 'printf %s; sudo -n id'`（用 env -S 的字符串解析功能偷偷拼接）。
- **注释绕道类**：`echo ok # ; bash -c "sudo ..."`（利用 `#` 注释符，让前半句看似无害）。
- **伪造身份类**：`env --argv0 marker sudo ...`（伪造程序名，让系统以为这个程序叫别的名字）。
- **转义类**：`printf\_SAFE`、`printf\c ignored`（利用转义字符让名字"看起来"不匹配规则）。

然后**挨个把这些命令交给审批系统去分发执行**，记录每个命令的结果。**安全测试的要点就在这：不能只测"正经调用会被拦"，还得假设对方是狡猾的，把所有能想到的伪装路径都铺开试一遍。**

**4. 方法三：用断言代替人眼，还要能对比"改前改后"**

脚本有个 `--verify`（验证）模式：对每条命令，**用断言（assert）机器自动检查**——该拦的必须返回"被拦"状态（status 是 blocked、没有输出、错误信息里提到拒绝规则）；少数设计上允许放行的（比如 `printf SAFE` 规则本身想放行的良性命令）必须正常执行并输出预期内容。人眼扫 JSON 会累会漏，断言一次跑完全查。

更妙的是文件开头注释说的：**同一个脚本可以分别跑在"改动前"和"改动后"两个版本上，输出两份 JSON 对比**，作为这次改动没有把护栏改坏的"验收凭证"。这就像医院做手术前后的检查报告——**改动安全性的证据，是"前后对比"而不是"我检查过了"**。

**5. 这个脚本教给我什么？**

- **安全功能要专门测试"绕过"，而不是只测"正常拦截"**：拦命令、拦请求、拦访问，这类功能的天敌是"伪装"。测试时把各种套壳、藏字、转义、伪造姿势列成清单逐个击破，才算真的验过。
- **危险测试用假靶子**：想验证"会不会误触发危险操作"，就造一个无害的替身放在那里，看它有没有被碰到——零风险，证据还清清楚楚。
- **测试要可对比、可留档**：同一套测试跑在改动前后，输出对比凭证，改坏了能一眼看出，没改坏也能让人放心。**"可复现的测试"是工程自信的来源。**

### 一句话收获

Hermes 的离线评估脚本让我看到"怎么认真验证一道拦截"：不用真命令，摆一个假靶子；不只测正常拦截，把几十种绕过姿势（套壳、藏字、转义、伪造名字）挨个试一遍；再用断言自动检查该拦的拦了、该放的放了，还能前后对比留凭证——**对"拦得住吗"这个问题，答案不是"我觉得可以"，而是"我试过了这几十种绕法"**。

## 2026-09-21 学习记录

**当天版本**：commit `1df1904e45` —— "test(skills): real-Windows quarantine hash parity check"（在真实的 Windows 上，验证"隔离区"处理后的技能文件哈希不变）。

### 今天学到了什么

**1. 背景：hermes 下载技能包时，要经过"隔离区"**

回忆一下 hermes 的技能系统（前几天学过）：hermes 会从网上下载技能包（bundle，一个打包的技能压缩包）。下载的东西不能直接信任，hermes 会先把它放进一个**隔离区（quarantine）**——一个专门存放"还没验明正身"的文件的目录，检查没问题了才放行使用。

检查的手段之一是**内容哈希（content hash）**。**大白话解释哈希**：给一份文件的内容算一个"指纹"——同样的内容算出来永远是同一个数，内容只要改一个字节，指纹就完全变样。所以用哈希就能验证"这份文件跟我下载时一模一样，没被改过"。hermes 用 `content_hash`（内容指纹）来核对下载的包和处理后的文件是不是同一份内容。

**2. 问题：Windows 会在你不知不觉中，把文件的换行符"变个样"**

今天的提交要守的一个"不变量"是：**技能包经过隔离区处理后，内容的哈希必须和原始包一致**（`content_hash` 等于 `bundle_content_hash`）。这个不变量在一个地方特别容易破——**Windows**。

原因很冷门但很经典：**Windows 上的程序在"文本模式"下写文件时，会自动把换行符从 LF（`\n`，Unix 系的标准）转换成 CRLF（`\r\n`，Windows 的老标准）**。也就是说，一个内容为"第一行\n第二行"的文件，如果在 Windows 上用文本模式写入，存到磁盘上可能变成"第一行\r\n第二行"。注意：**从人眼看去完全一样的文件，字节数却不同了**——而哈希是对每一个字节敏感的，换行符一变，哈希就变了，等于"内容被修改了"。

**3. 修法：在"真实的 Windows 上"加一个测试，把这个不变量钉死**

hermes 的开发者写了一个专门的测试（`test_quarantine_bundle_hash_matches_bundle_on_windows`），并且给它打了一个 **`windows_only` 的标记**（只在 Windows 上跑的标记）。这个测试做三件事：

1. 构造一个技能包，里面有一个 `SKILL.md`，内容是标准的 LF 换行；
2. 走一遍真实的 `quarantine_bundle`（隔离区处理）流程；
3. **断言处理后的内容哈希必须等于原始包的哈希**——只要哪天有人改代码时不小心用了文本模式写文件，这个测试在 Windows 上就会立刻失败。

有意思的是提交说明里提到：之前已经有一个**模拟（emulated）换行的测试**了——在别的平台上模拟 Windows 的行为来测。但模拟终归是模拟，**这次专门在真实的 Windows 主机上跑一遍**，让不变量被真实环境守护。

**4. 这个提交教给我什么？**

- **"看着一样"的文件，字节可能不一样**：哈希验证的是字节，不是人眼。换行符、编码、末尾的空行、BOM（文件开头的隐藏标记）这些"看不见的差别"，都会让哈希判若两人。**凡是靠哈希验证一致性的系统，都要警惕"同一份内容在不同环境下被悄悄改写"。**
- **跨平台的坑，要用"真实环境"的测试来守护**：模拟测试有用，但**真实环境会给你模拟想象不到的意外**。像"Windows 自动转 CRLF"这种系统级行为，模拟得再像也不如真的跑一遍。**跟环境强相关的行为，值得为它专门开一个"只在那个环境跑的测试"。**
- **测试也要有"平台标签"**：`windows_only` 标记让测试在别的平台上自动跳过——**同一个测试文件，不同平台跑不同子集，各平台守护自己特有的坑**，互不干扰。

### 一句话收获

Hermes 的 Windows 哈希测试让我看清一个隐蔽的坑：Windows 写文件时会悄悄把换行符 LF 变成 CRLF，人眼看着没变，哈希却变了——所以"内容一致性"要防的不是明着改，而是**各平台在暗地里给文件"整容"**；而守住它的办法，就是在真实 Windows 上跑一个专属测试，让不变量被真实环境钉死。

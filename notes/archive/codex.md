# Codex（OpenAI 的本地编程助手）

这个项目是 OpenAI 出的 **Codex CLI**——一个跑在你自己电脑上的 AI 编程助手。你不用打开网页，直接在终端（就是那个黑底白字的命令行窗口）里敲 `codex`，它就能帮你改代码、跑测试、查问题。它跟你日常用的聊天机器人最大的区别是：它不只是"聊天"，而是真的会读你项目里的文件、帮你执行命令、把改好的代码写回文件。

和后面要学的 deepseek-harness、opencode 相比，它更像一个"工具"而不是一个"框架"：装好就能用，重点是体验，而不是让你自己拼装。

几个关键概念（大白话版）：

- **终端（Terminal）**：电脑上的命令行窗口，所有程序员最早的入口。
- **TUI**：Text User Interface 的缩写，翻译过来是"文本用户界面"。就是不开图形窗口，用文字和方框在终端里画出一个带菜单、输入框的界面。Codex 的对话界面就是 TUI。
- **Agent loop（智能体循环）**：AI 助手干活的基本套路，像一条流水线：把"你要干什么"交给模型 → 模型说"我要先看看代码" → 程序帮它执行（读文件、跑命令）→ 把结果喂回去 → 模型再决定下一步 → 直到活干完。Codex 内部就是靠这个循环转起来的。

## 2026-09-11 学习记录

**当天版本**：commit `78600239` —— "Honor system reduced-motion preferences in the TUI"（让终端界面尊重系统的"减少动态效果"设置）。

### 今天学到了什么

**1. Codex 用什么语言写的？**

这个仓库主目录下有 `codex-rs/`（Rust 写的主体）和 `codex-cli/`（命令行入口）。Rust 是一种以"安全、快"出名的系统编程语言。选 Rust 写一个终端工具很合理：启动快、占内存小、不容易崩溃。如果你想自己看懂 Codex 的内部，重点看 `codex-rs/`，里面按功能拆成了好几个 crate（可以理解成"模块"或"零件"），核心的 `core` 负责主流程，`tui` 负责界面。

**2. 今天这个提交在干什么？**

`78600239` 这个改动是：在 TUI 里支持"系统减少动态效果"（reduced motion）设置。这是个无障碍（accessibility）功能——有些人对屏幕上的动画、闪烁很敏感甚至头晕，操作系统提供了"减少动态效果"的开关。Codex 学会了检测这个开关，开了就少放动画。顺带一提，它为此新增了 `codex-rs/tui/src/system_motion.rs` 这个文件，还配了快照测试（snapshot test，就是预先记录好"界面长什么样"，改动后自动比对有没有意外变化）。从这里能学到：**正经项目连"动画"这种小事都会考虑用户体验和可访问性。**

**3. 沙箱（sandbox）是什么？为什么重要？**

在 `AGENTS.md` 里我读到 Codex 用了一个叫 **沙箱** 的机制：让 AI 执行的命令都关在一个"隔离房间"里，房间里的 AI 碰不到你电脑上别的东西（除非你放行）。这很重要——AI 会执行命令，如果没限制，它误操作删了你的重要文件就糟了。沙箱就像给 AI 戴了个"安全围栏"，能挡住大部分闯祸。Codex 在 macOS 上用的沙箱工具叫 **Seatbelt**（`/usr/bin/sandbox-exec`），这是苹果系统自带的一个安全功能。

### 一句话收获

Codex 让我看到了一个"生产级"AI 编程助手应该长什么样：Rust 写的底层、TUI 界面、agent 循环、沙箱保护、连动画这种细节都照顾到——好的工程不是堆功能，是把小事也做扎实。

## 2026-09-12 学习记录

**当天版本**：commit `202d61c6` —— "Unify context snapshots and group requests into windows"（统一上下文快照，并把请求分组进"窗口"）。

### 今天学到了什么

**1. 上下文窗口（context window）：AI 的"临时工作台"是有限的**

今天的提交主题是"上下文管理"，这是所有 AI 助手都要面对的难题。大白话解释：模型每次能"看到"的内容是有限度的，这个限度叫**上下文窗口（context window）**——就像一张大小固定的工作台，你摆上去的东西越多，剩下的地方越小，摆不下就得收拾。

对话长了以后，历史记录会占满整张桌子。这时候有两个办法：

- **压缩（compaction）**：把旧对话浓缩成一段摘要，腾出空间放新内容。codex 的 `codex-rs/core/src/compact.rs` 就是干这个的，它还有配套的 `compact_token_budget.rs`（压缩时的"字数预算"管理——先算好压缩成多长最划算）。
- **分组请求（group requests into windows）**：把"模型需要看到的内容"按批次打包成窗口，而不是零散地一条条发。今天的提交就是在统一这套打包逻辑，让所有请求走同一套"快照 → 分组 → 归一化"流程。

**2. 快照测试和归一化（normalize）：让"会变的测试"变得稳定**

这次提交改动最大的一块在测试代码（`context_snapshot.rs` 改了 1400 多行，还新增了 `normalize.rs`）。它教给我一个很实用的测试技巧：

AI 助手的测试经常要对比"发给模型的内容长什么样"，这叫**快照测试**（把某次输出的样子原样记录下来，以后跑就对比有没有变化）。但有个麻烦：输出里经常带着每次都不一样的值，比如 **UUID**（一串随机生成的编号）、**工作目录路径**、**prompt 缓存键**（标记提示词缓存用的编号）。如果直接对比，每次跑都不同，测试永远失败。

解决办法就是**归一化**：把所有随机值替换成稳定标签，比如 `<UUID 1>`、`<PROMPT_CACHE_KEY 2>`。测试对比的是"结构"，而不是"每次都在变的随机数"。**这个思路在写任何需要对比文本的测试时都通用：先把不稳定的部分"打码"，再比较。**

### 一句话收获

Codex 让我理解了"上下文管理"是 AI 助手的核心工程难题——窗口有上限，所以要压缩、要分组、要归一化；而测试里"先归一化再对比"这个小技巧，能让随机值不再成为测试的敌人。

## 2026-09-13 学习记录

**当天版本**：commit `b979d4f1` —— "Add a feature flag for asynchronous user messages"（给"异步用户消息"功能加一个开关）。

### 今天学到了什么

**1. 功能开关（feature flag）：给功能装一个"电灯开关"**

今天的提交主题是 **feature flag（功能开关）**。大白话解释：一个功能开发完了，不一定立刻对所有人开放——先把它装在一个"开关"后面，默认关着。想试的人可以打开，出了问题时随时关掉，不用重新发布版本。

Codex 把这件事做得很正规：它有专门的 `codex-rs/features` 代码库（crate），管着一个**集中式的功能开关注册表**——所有新功能都在这里登记，每个功能还标注了生命周期阶段（`Stage`），比如"UnderDevelopment（还在开发中，不对外）"。用户通过配置文件（TOML 格式，一种简洁的文本配置格式）就能打开或关闭某个功能。

**2. 今天加开关的"异步用户消息"是什么？**

`b979d4f1` 给"异步用户消息"这个功能加了开关。什么意思呢？正常情况下，AI 助手是"一问一答"：你发消息，它回复，你们俩轮流来。而**异步消息**的意思是：用户可以不等 AI 回复完，直接再发一条新消息（或者用代码在后台注入消息），AI 会把这些消息排队处理。

为什么这种功能要加开关？因为它改变的是"对话的基本节奏"，属于行为大变样，直接默认开启可能让很多用户不适应。先藏着，等稳定了再逐步放开——**这就是功能开关最大的价值：把"发布功能"和"让所有人用上功能"拆成两件事。**

**3. 顺带学到的：老功能开关的"退役"**

代码里还有个 `legacy.rs` 文件，管"老功能开关"。这说明功能开关不是只进不出的：一个功能稳定后，开关会逐步移除（叫"退役"），把行为固定下来，避免开关越积越多变成垃圾。**管理开关和管理功能一样，都要有进有出。**

### 一句话收获

Codex 让我认识了"功能开关"这个工程利器：新功能先藏在开关后面，灰度、回滚、试错都从容——发布不等于全量上线，开关是给发布留的"后悔药"。

## 2026-09-14 学习记录

**当天版本**：commit `6f39a47b` —— "Add worktree session creation to the agents overview"（在 agents 总览界面里支持用工作树创建会话）。

### 今天学到了什么

**1. 工作树（worktree）：一个仓库，多个"工位"**

今天的提交主题是 **worktree（工作树）**，这是 git 的一个功能。先解释 git 基础：git 是管理代码版本的软件，一个项目通常在一个"工作目录"里干活。而 **worktree 允许同一个仓库同时存在多个工作目录**。

打个比方：普通情况是一个项目一张桌子，大家轮流用；worktree 是同一个项目开了好几张桌子，每张桌上都能独立干活、互不干扰，改的东西最后还是汇总到同一个仓库里。

**2. Codex 用工作树做什么？—— 并行会话**

Codex 的界面里有个"agents 总览"（可以同时管理多个 AI 助手会话的地方）。今天这个提交让它可以**用工作树创建新会话**：每个会话分配一个独立的工作树，AI 在那个工作树里改代码、跑测试，不影响你主目录里正在干的事。

代码里我看到它用的是 `WorktreeManager`（工作树管理器）这个专门的组件来创建和管理工作树。注意文件开头还写了句注释：**"工作树从仓库的默认分支开始，并且只绑定这个新会话"**——意思是新会话从干净的分支起点开始，不会把你改到一半的代码卷进去。

**3. 值得学的细节：工作树的"善后"处理**

代码里有个 `PendingWorktree`（挂起的工作树）结构，它做了一件很讲究的事：如果会话创建了一半、最终没人认领这个工作树，它会在销毁时**自动把这个工作树清理掉**（代码里叫 Drop 时移除），不留下垃圾目录。如果实在清理不掉，它会提示用户手动执行 `git worktree remove <路径>` 来删除。

**这个设计教给我：创建了临时资源，就要考虑"如果没用上怎么办"——临时工位用完要收拾，收拾不了也要告诉主人怎么收拾，不能甩手不管。**

### 一句话收获

Codex 用 git worktree 让我看到"并行干活"在 AI 编程里的样子：每个会话一张独立的桌子，互不干扰；同时学会了一个好习惯——创建临时资源时必须想好它的善后（自动清理 + 清理不了就明确提示）。

## 2026-09-15 学习记录

**当天版本**：commit `18d7ace2` —— "Move Guardian reviewer lifecycle into the extension"（把 Guardian 评审者的生命周期管理移入扩展层）。

### 今天学到了什么

**1. Guardian（守护者）：AI 的"监护人"**

今天的提交涉及 Codex 里一个很重要的机制叫 **Guardian**（守护者）。从代码注释看，它的定位是："承载审批决策，以及一个独立的同步评审者"。翻译成人话：**它是给 AI 干活把关的监护人**——AI 想干一些敏感的事（访问网络、调用外部工具）时，由 Guardian 决定要不要批准；AI 干完活，Guardian 还会评审干得怎么样。

我翻它的模块清单，发现 Guardian 管的事还真不少：

- **approval（审批）**：AI 要访问网络、调用 MCP 工具（外部服务接口）时，判断该不该放行。
- **review（评审）**：对 AI 的工作做独立评审（有专门的 `review_session`、`reviewer_config`）。
- **budget（预算管理）**：`input_budget`（输入预算）和 `request_budget`（请求预算）——防止一次任务把上下文窗口或请求次数用爆（还记得第二天学的"上下文窗口有限"吗？Guardian 会管这个预算）。
- **decision / feedback**：做出决策、收集反馈。

**2. 最有价值的架构分工："扩展定策略，核心管执行"**

`guardian/mod.rs` 里有一句非常凝练的设计说明：

> "The extension chooses policy and evidence; core enforces permissions and mandatory review requirements."
> （扩展层负责选择策略和证据；核心层负责强制执行权限和强制性的评审要求。）

拆开看：**策略（什么算敏感、什么时候要审、预算给多少）是灵活的，放在扩展里可以随时换；但"必须遵守权限、必须过评审"这条底线，是核心层强制执行的，谁都绕不过去。**

这就像机场安检：安检标准和设备（策略）可以升级换代，但"每个乘客都必须过安检"这件事是制度底线，不能因为任何理由跳过。**这种"灵活的归扩展、强制的归核心"的分工，是安全系统的经典设计——灵活性不会削弱底线。**

**3. 今天的提交在做什么？**

`18d7ace2` 把"评审者的生命周期管理"（什么时候启动评审者、什么时候销毁）从核心挪到了扩展层。方向跟上面的原则一致：**把更多"怎么管"的细节下放到扩展，核心只保留"必须执行"的部分。** 核心越薄、越稳定，扩展越灵活、越好改。

### 一句话收获

Codex 的 Guardian 让我看懂一个安全系统的分工智慧：策略可以灵活（扩展负责选策略、管证据），但底线必须强硬（核心强制权限与评审）——"灵活的部分可以松，强制的部分必须硬"。

## 2026-09-16 学习记录

**当天版本**：commit `b71af39fe` —— "Preserve MCP App UI metadata in tool-call events and history"（在工具调用事件和历史中保留 MCP App 的界面元数据）。

### 今天学到了什么

**1. 背景：MCP 是什么？**

还记得 dsh 笔记里出现过好几次 **MCP** 吗？今天终于可以正式讲它了。MCP 全称 **Model Context Protocol（模型上下文协议）**——一个开放标准，作用是让 AI 助手能统一地接入外部工具和数据。打个比方：USB 是"外部设备的标准插头"，MCP 就是"AI 工具的标准插头"——不管工具是谁家的，只要实现 MCP 接口，AI 助手就能直接调用。

Codex 支持 MCP 服务器（提供工具的第三方程序）。当 AI 调用 MCP 工具时，会产生一条"工具调用事件"，并且会进入历史记录。

**2. 今天的提交：保留"UI 元数据"

先说**元数据（metadata）**是什么——"关于数据的数据"，也就是描述信息的附带信息。比如一张照片的拍摄时间、地点，就是照片的元数据。这里说的是 **MCP App 的 UI 元数据**：工具的展示信息，比如图标、显示样式、按钮文案等，用于在界面里把工具"打扮"得好看。

今天的提交做的事情是：**这些 UI 元数据，在工具调用事件和历史记录里都要保留下来。** 为什么值得专门做？因为：一个 MCP 工具可能今天还能用，明天被卸载了。但**历史记录里曾经用过这个工具的记录，依然要能正确展示**——如果元数据只在工具活着的时候才有，等工具卸载了，历史里那条记录就"破相"了（图标没了、样式乱了）。

**3. 这个提交教给我什么？**

- **展示信息和"当下可用性"要分开**：界面展示工具需要元数据，但元数据不能依赖"工具此刻还连着"。**历史记录要"自包含"**——它该带的信息，在事件发生时就要完整存下来，而不是等到展示时再去外面找。
- 这跟昨天 opencode 学的"持久事件"是同一个思路的体现：**该跟着记录一起存下来的元数据，就要在记录时存好**，否则将来一定丢。

### 一句话收获

Codex 的这个小提交让我明白"历史记录要自包含"：工具调用事件的展示信息（UI 元数据）要在事件发生时就完整存下来，不能等展示时再去外面找——记录时刻省事，将来展示就破相。

## 2026-09-17 学习记录

**当天版本**：commit `c56dda711` —— "Track WebSocket continuation modes and full-input send reasons"（跟踪 WebSocket 的继续模式，以及完整输入发送的原因）。

### 今天学到了什么

**1. 背景：WebSocket 是什么？**

今天的提交涉及 **WebSocket**——一种让客户端和服务器之间保持"一条长期打开的双向通道"的通信协议。平时我们上网是"一问一答"（你发请求，服务器回响应，然后断开）；WebSocket 不同，**通道一直开着，两边随时都能说话**，就像打电话而不是寄信。

Codex 的 TUI（终端界面）和它的后端之间就用 WebSocket 通信——你打字给 AI，AI 的回话实时流过来，靠的就是这条常开的通道。

**2. 今天这个提交在做什么？—— 记录"原因"**

提交标题里两个关键词：

- **continuation modes（继续模式）**：对话"继续"时走的模式。之前学过 turn/step（回合/步），"继续"是对话推进的重要动作，可能有多种方式，这里要把用的哪种记下来。
- **full-input send reasons（完整输入发送的原因）**：把"完整的一整段输入"发给服务器的原因——可能是用户按了回车、可能是粘了一段长文本、可能是某个快捷键。**每种原因都记录下来。**

**3. 为什么要记录"原因"？—— 可观测性（observability）**

这引出一个重要的工程概念：**可观测性**——让系统的内部状态和决策过程"看得见"，出了问题能查清楚"为什么"。

打个比方：你修车，最怕听到"反正就是坏了"。可观测性就是给系统装"行车记录仪"：每一步动作、为什么做这个动作，都记下来。Codex 记录"这条消息是用什么模式、什么原因发出去的"，就是为了：以后界面出现诡异行为（比如消息重复发、发送时机不对），工程师能翻记录，定位到"哦，是这种原因触发的那条路径"。

**4. 这个提交教给我什么？**

- **调试困难往往不是缺日志，而是缺"为什么"**：很多日志只记"发生了什么"（消息发了），不记"为什么发生"（用什么模式、什么原因发的）。补上"原因"维度，排查问题的效率完全不同。**记录动作时，顺手把"上下文和原因"一起记下来，是最便宜的调试投资。**
- 它还呼应了之前学的"事件溯源"思想：**把"发生的事 + 当时的背景"都留痕**，将来随时能复盘。

### 一句话收获

Codex 的"发送原因追踪"让我理解可观测性的精髓：光记"发生了什么"不够，还要记"为什么发生"——用哪种模式、什么原因触发的，都留痕，出了问题才能像看行车记录仪一样回放定位。

## 2026-09-18 学习记录

**当天版本**：commit `c775dd3c3` —— "Defer environment selection changes until the next turn"（把环境选择更改推迟到下一回合生效）。

### 今天学到了什么

**1. 背景：环境选择（environment selection）是什么？**

先解释 **环境选择**：AI 干活时在哪个"环境"里跑？比如在本地直接操作、还是在一个隔离的沙箱里、或者在一个 Docker 容器里（还记得第一天学的沙箱吗？）。这个选择决定 AI 能看到什么、能碰什么。

**2. 问题：如果中途突然换环境会怎样？**

提交的标题已经给出了答案："**推迟到下一回合（next turn）**"。也就是说，用户想切换环境的请求，**不会立刻生效，而是要等当前这个回合（turn，还记得 turn/step 吗？）全部结束，才应用**。

为什么不能立刻生效？因为环境是"AI 正在干活的那个房间"：如果干到一半，房间突然换了——文件变了、能用的工具变了、上下文也变了——正在进行的对话就会**前后不一致**，AI 可能"精神分裂"：上半段以为自己在沙箱里，下半段突然在本地了。

**3. 这让我联想到一个老朋友：hermes 的"缓存神圣"原则**

第二天学 hermes 时，它有一条"神圣不可侵犯"的原则：**提示词缓存（prompt caching）是神圣的，对话中途改动上下文会作废缓存、翻倍费用**，所以修改默认延迟到下次会话生效。

codex 这里的做法和它如出一辙：**"中途改大环境"这件事太伤，所以干脆排队，等当前工作收尾了再换。** 两个项目不约而同地选择了"延迟生效"——这背后是个通用规律：**对话进行中的系统状态，能不改就不改；真要改，就等到一个自然的边界（回合结束/会话结束）再改。**

**4. 顺带学到的：代码结构**

这个提交改了很多地方，其中 `session/environment.rs` 动了 125 行——专门管"环境配置怎么在会话里生效"的模块。可见"环境"在 codex 里是一个正经的会话级概念，有专门的代码管它的生命周期（验证、排队、生效）。**一个概念一旦重要到成为系统的"一等公民"，就该有自己独立的模块管它。**

### 一句话收获

Codex 的"环境更改推迟到下一回合"让我记住一个工程规律：对话进行中的系统状态，能不改就不改，真要改就排队到自然的边界再改——中途换环境就像干到一半换房间，上下文会前后不一致。

## 2026-09-19 学习记录

**当天版本**：commit `c0e1b7825` —— "Preserve the provisioned macOS CLI's code-signing identity"（保留已配置的 macOS 命令行的代码签名身份）。

### 今天学到了什么

**1. 背景：代码签名（code signing）是什么？**

今天的提交讲的是 **代码签名（code signing）**。大白话解释：**给软件盖一个"防伪数字章"**——用开发者持有的数字证书，给程序文件算一个"指纹"并签上名。谁拿到这个程序，都能验证：这确实是官方发布的、没有被任何人篡改过（哪怕改一个字节，章就失效了）。

在 macOS 上，这是安全体系的一部分：系统（通过 Gatekeeper，苹果的软件安全检查机制）会检查下载的程序有没有合法的签名。**没有签名或签名无效的程序，系统会警告"无法验证开发者"，甚至拒绝运行。** 这就像买酒看防伪标：没有防伪标或者标是假的，心里就要打鼓。

**2. 今天的提交在做什么？**

Codex 的 macOS 版本发布前，要经过一个签名流程（代码在 `.github/scripts/macos-signing/` 里）。这个提交修复了一个具体问题：**"已配置好的" macOS 命令行包（provisioned CLI package），在签名过程中要保留它的签名身份（code-signing identity）**——不要因为流程里的某个步骤，把之前已经签好的身份弄丢。

**3. 这个提交教给我什么？**

- **签名是一次性、不可逆的"盖章"**：程序签了名，之后的任何改动都会破坏签名。所以"先改完再签名"是铁律——签名之后就不能再动程序内容了。这也解释了为什么"保留签名身份"这么重要：弄丢了，整个包就要重新来一遍签名流程。
- **发布流程里的"身份"要小心保管**：代码签名身份（证书+私钥）是发布方的"命根子"，泄露了别人就能冒充发布方。所以这类脚本里有专门的测试（这次新增了 70 行测试）确保流程不会弄丢身份。**安全相关的资产，要当作"钥匙"一样对待：不丢失、不泄露、有测试守护。**

### 一句话收获

Codex 的代码签名提交让我看懂软件发行的一环：给程序盖"防伪数字章"让用户能验证官方身份和完整性——而签名身份就像发布方的钥匙，流程里要小心保管，丢了就要全部重来。

## 2026-09-20 学习记录

**当天版本**：commit `392f56a61` —— "Cancel pending transcript Home jumps on subsequent navigation"（用户做出新的导航后，取消挂起的"跳回开头"动作）。

### 今天学到了什么

**1. 背景：这个提交在修一个什么样的问题？**

Codex 的终端界面（TUI，还记得吗？就是在黑底终端里运行的那个交互界面）里，有一个"只读对话记录查看器"——你可以往回翻看以前跟 AI 的整个对话过程。对话历史可能非常长，所以它采用了**分批加载**：一开始只加载最近的一段，你往下翻的时候，它再继续加载更老的记录。

问题出在按 `Home` 键（跳回对话最开头）这个操作上：如果你按下 Home 时，更老的记录**还在加载中**，那"跳回开头"这个动作就会变成一个**挂起的跳转（pending jump）**——先记着"等加载完要跳回去"，等加载完成后再执行。

这本来没问题，但有个漏洞：如果用户在等加载的时候**又改变了主意**，比如滚到了别的位置、按 `End` 跳回最新消息、或者用方向键浏览别的记录——此时用户已经换了一个新的阅读位置。可是那个"挂起的跳回开头"还记在账上，等历史加载完成后，它会**强行把视图拉回开头，把用户的新位置覆盖掉**。用户会看到屏幕"啪"地跳走，非常恼火。

**2. 修复的思路：让新的操作"取消"过期的操作**

这个提交做的事，用一句话说就是：**用户一旦做出新的导航动作，就把之前挂起的"跳回开头"取消掉**（代码里叫 `cancel_pending_jump` / `cancel_beginning`）。具体细节很有意思：

- **已开始的加载不浪费**：本来在加载的是"开头的历史"（状态叫 `LoadingBeginning`），用户既然不想回开头了，就把这个状态改成 `LoadingOlder`（加载更老的内容）——已经加载到一半的数据接着用，不白干。
- **覆盖各种时机**：不只是渲染完成之后的导航要取消，连**第一次绘制之前**就发生的导航也要处理（因为历史加载可能很快，用户在界面还没画出来时就按了键）。
- **有例外**：有一种场景**不取消**挂起跳转——"被动的"高亮恢复（passive highlight restoration，比如终端窗口大小改变后，界面重新计算高亮位置）。因为这种动作不是用户主动导航，是系统自己的重绘，不应该打断用户原本的"跳回开头"意图。

**3. 这个提交教给我什么？**

- **"过期的异步结果"必须能被取消**：凡是"用户操作之后才完成的旧操作"，都可能覆盖用户的最新意图。成熟的界面和程序都会给这类操作留"取消"的出口，而不是让它们自顾自地执行完再覆盖新状态。想想抢票软件：你点了两次"查询"，只有最后一次的结果应该显示——前面的查询结果如果晚到，就该被丢弃。
- **取消要分清"用户主动"和"系统被动"**：不是所有情况都取消。用户主动导航 → 取消旧跳转；系统被动重绘 → 保留旧跳转。**区分"人的意图"和"机器的内部动作"，是设计这类逻辑时最见功夫的地方。**
- **在途的工作尽量复用**：把 `LoadingBeginning` 改成 `LoadingOlder`，说明设计者没有简单地"扔了重来"，而是让已经加载一半的数据继续发挥价值。**能接住半成品的工作，就不必推倒重来。**

### 一句话收获

Codex 的导航取消让我看到异步世界的一个基本功：用户一旦做出了新动作，那些"还没执行完的旧动作"就该被取消，否则晚到的旧结果会覆盖用户的最新意图——就像打游戏时按了新招，旧招的收尾动作就不该再跳出来打断。

## 2026-09-21 学习记录

**当天版本**：commit `4ca8e7aff` —— "Make transcript list spacing uniform after streaming"（让对话记录列表在流式输出之后间距统一）。

### 今天学到了什么

**1. 背景：对话记录列表在"流式输出"时的排版问题**

Codex 的终端界面里有一个**对话记录查看器（transcript viewer）**——用来回看跟 AI 的整场对话。里面的内容常常以**列表**呈现：一条 AI 回复、一条用户消息、一条计划，都是列表里的一项。

关键背景是**流式输出（streaming）**：AI 的回答不是一次性蹦出来的，而是一个字一个字、一行一行"流"出来的，界面要跟着实时刷新。问题就出在"内容还在长"和"排版"之间：**AI 的回答可能很长、要折成好几行（跨多行），也可能很短只有一行**。如果排版时只给"跨多行的项"后面加空白行，那列表的间距就会忽大忽小——有的项下面有空行、有的没有，看起来歪歪扭扭。

**2. 修复的思路：流式时和完成时，用两套不同的排版规则**

这个提交的核心是**区分"流式进行中"和"流式结束"两个状态，分别处理**：

- **流式进行中（中间态）**：让列表保持**紧凑**——正在变长的内容不急着摆整齐，别让还在增长的文字把布局顶得来回跳。但已经完成的行**不拦着**（不让它们被"还没写完的行"卡住排队）。
- **流式结束（终态）**：这时候内容不再变了，可以做"收尾排版"——**只要有任何一项跨了多行，就给所有相邻项之间都加上统一的空白**，间距整齐划一；如果所有项都是单行，就保持紧凑不瞎加空行。窗口大小改变（resize）时，重新计算一次。

这跟我昨天学的"导航取消"是一对思路：**界面既要管"进行中"的临时样貌，也要管"尘埃落定"后的最终样貌**。流式输出时屏幕一直在变，不可能也不需要在每一毫秒都保持完美——但**内容稳定下来的那一刻，一定要收敛成一致的、好看的布局**。

**3. 三个值得学习的细节**

- **"跨多行"是触发重新排版的条件**：判断要不要加空行，不是看"项多不多"，而是看"有没有任何一项跨了多行"——因为只有跨多行的项会让相邻项"贴得太近"难以分辨。**排版规则要由"内容的形状"决定，而不是拍脑袋。**
- **间距策略要进渲染缓存的 key**：Codex 用渲染缓存（把渲染好的 Markdown 结果缓存起来省性能），这次特意把"间距策略"加进缓存 key——因为同样的内容，用不同的间距策略渲染出来是不同的样子，**缓存要知道"我用什么规则渲染的"，否则会返回过期的排版**。
- **合并流式单元格时，保留读者正在看的内容**：流式输出会有很多"单元格"（一小段一小段的输出），完成后要合并。合并时**不能让读者眼睛盯着的位置突然跳掉**——用户正读到一半的内容要保持原位。

**4. 这个提交教给我什么？**

- **"正在变"和"已经定"要分开管**：任何实时更新的界面（流式输出、进度条、加载列表）都有"中间态"和"终态"。中间态要**稳定、不打扰**（别跳来跳去），终态要**整齐、收尾**。把这两个状态分开设计，比在一个状态里两头兼顾清晰得多。
- **排版规则要听"内容的形状"**：空行加不加、间距大不大，依据应该是"内容长什么样"（有没有跨多行），而不是固定的格式参数。
- **缓存必须记得"自己是按什么规则算出来的"**：缓存 key 要包含影响结果的决策，否则缓存就是"过期的记忆"。

### 一句话收获

Codex 的间距修复让我看到流式界面的排版智慧：内容还在长的时候保持紧凑不打扰（中间态求稳），内容定下来之后统一间距做收尾（终态求齐），还让"间距策略"进缓存 key 防止排版过期——**"正在变"和"已经定"用两套规则，是实时界面不乱的秘诀。**

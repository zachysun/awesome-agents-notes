# DeepSeek Harness（dsh）

| 源仓库 | [deepseek-ai/deepseek-harness](https://github.com/deepseek-ai/deepseek-harness) |
|---|---|
| 协议 | MIT |
| 主语言 | TypeScript |
| 笔记基准 | commit `22ddee3792`（2026-10-24） |

DeepSeek Harness（简称 dsh）是 DeepSeek 官方开源的 agent harness：一套让 AI 智能体（agent）真正"跑起来"的完整支撑系统，管的是模型怎么被调用、工具怎么被执行、对话怎么被记录、危险动作怎么被拦截。它用 TypeScript 写成，是一个 monorepo（一个仓库里装很多独立发布的小包），`packages/` 目录下有近 300 个功能包、几十万行代码，底层构建在自带的插件框架 Cordis 之上。它目前处于 developer preview 阶段（跟进到 0.2.1-rc 版本线），官方明说会有破坏性变更。它最大的标签是 **everything-is-a-plugin（一切皆插件）**：框架里没有写死的核心，连模型适配、工具注册、对话记录、智能体循环本身都是插件，理论上每一个都能被配置换掉。

这份笔记按问题组织，不按 dsh 的开发时间线：每个问题讲清它现在是怎么解的、为什么这么解、代价是什么。项目演进过程放在文末修订记录里。笔记起于官方 0.1.6-alpha.2（commit `ddefc45fbc`，2026-09-21），跟进到 commit `22ddee3792`（2026-10-24）。

## 它要解决什么问题

先解释 harness 这个词。原意是"马具"，也就是套在马身上让人能驾驭马的那套皮带和挽具。放到 AI 领域，模型是那匹马：它只会根据输入生成文字，本身不会读文件、不会执行命令、不会记住上次的对话。harness 就是套在模型外面的那套"挽具"——把模型的一句话输出变成"调用工具、观察结果、再决定下一步"的完整循环，并把安全、记录、界面这些支撑设施补齐。

这个领域的多数框架有一个共同麻烦：核心是写死的。循环怎么跑、提示词怎么拼、工具怎么注册，都埋在框架代码里；想换个行为，只能去改框架源码，改完还要跟着上游版本维护补丁。框架作者预想的扩展点就那么几个，预想之外的需求很难塞进去。

dsh 对这个问题的回答很彻底：把"核心"取消掉。它的架构文档有一句纲领——模型适配器、工具注册表、会话日志、agent 循环本身，全都是插件，全部可以从配置替换。没有一处是"改不了的黑盒"，想扩展就是把一个新插件挂到其他插件旁边，而不是去修补某个特权核心。

它落地的形态有五种，对应五种运行方式（官方叫 profile，后面细讲）：`web`（浏览器界面）、`headless`（无界面的一次性运行）、`sdk`（给开发者程序调用的库）、`acp`（只跑自动化的协议服务端）、外加一个 Electron 桌面应用。同一个内核，套不同的外壳。桌面版的做法也能看出这套架构的省力程度：Electron 里跑一个私有的 Desktop Host，Host 调用的就是同一个 `dsh` CLI 启动器和同一套网页界面，桌面进程只负责把本地页面和 Host 连起来——没有第二个"桌面版内核"要维护。

## 插件树是怎么拼起来的

### Cordis：底下的插件框架

dsh 的插件机制不是自己发明的，它建立在一个 vendored（把外部项目源码收进仓库统一维护）的开源框架 Cordis 之上。理解 Cordis 只需要五个概念：

1. **插件（plugin）**：一个实现 `Service` 接口的对象，往系统里装一段功能，也能拆下来。
2. **上下文（context）和服务**：context 是一个"服务仓库"，每个服务认领一个固定的 key，比如 `ctx.tools`、`ctx.llm`、`ctx.sessions`。别的插件按 key 找服务，而不是直接 import 某个具体实现——这是"可替换"能在类型层面成立的关键。
3. **`inject` 声明依赖**：插件写明自己需要哪些服务，框架等这些服务就绪后再装载它。装载顺序由依赖关系决定，不需要手工排启动清单。
4. **类型化事件**：插件之间不直接调用，而是声明事件、监听事件。事件有五种派发模式（见下表），派发模式是事件公开契约的一部分。
5. **注册即效果，可撤销**：插件做的每件事（注册一个提示词分节、一个工具、一个监听器）都登记成"效果"，插件卸载时这些事自动撤销，不留残留。

| 派发模式 | 是否等待 | 顺序 | 有返回值 | 典型用途 |
|---|---|---|---|---|
| `emit` | 否 | 按注册顺序 | 无 | 广播通知，听众多半只观察 |
| `waterfall` | 否 | 按注册顺序 | 有 | 拦截和改写，见下文 |
| `parallel` | 是 | 并行 | 无 | 互不相关的收尾动作 |
| `serial` | 是 | 按注册顺序 | 有 | 需要按顺序执行的步骤 |
| `bail` | 否 | 按注册顺序，有人出手即停 | 有 | "谁能答谁答"，答了就不再问别人 |

其中 waterfall（瀑布）最常用。一个 waterfall 事件的每个监听器会拿到一个 `next()` 函数：调用 `next()` 表示"我改完了（或我只是看看），请传给下一站"；不调用 `next()` 直接返回，表示"这个决定我接管了"，后面的监听器根本不会执行。像流水线上每个质检台拿到产品，可以盖个章放行（改一改再 `next()`），也可以直接拦下（不调 `next()`）。审批、请求拦截、提示词组装用的都是这个模式。

### 能力挂载点：三段式拆分

dsh 组织功能的基本单元叫 capability seam（官方用词，可以理解成"能力的挂载点"）。一个可替换的能力要拆成三个角色：

- **Service Definition（服务定义）**：声明接口和 `ctx.<key>`，只说"这里能干什么"，不带实现。
- **Service Provider（服务提供方）**：真正干活的实现，可以随时换一个。
- **Consumer（使用方）**：用这个能力的代码，常常是一个模型能调用的工具。

举例：文件读写能力是"定义（`ctx.fs`）+ 本地实现 + `read`/`write` 工具"三件套；压缩能力是"定义（`ctx.compaction`）+ 具体压缩后端 + `/compact` 命令"；技能系统是"定义（`ctx.skills`）+ 本地目录/打包内置/远程等提供方 + `skill` 工具"。官方文档明确要求：新增一个能力就要把三个角色都设计出来，只写其中一个不算数。

这样拆的回报是"换一处、动全身"：文件系统和子进程共享同一个"执行世界"，把它们的提供方指向一台远程沙箱，Bash、PTY、代码导航（LSP）就全部跟着搬到沙箱里跑了，不需要为每个功能单独写远程版。

### Profile 与 Bundle：组合的层叠规则

一个运行中的 dsh，就是启动时按层叠规则组装出来的一棵插件树。三个概念：

- **Bundle（插件包）**：一批插件和配置打包成的分发单位，类似"安装包"。`dsh-base` 是最基础的包，提供模型适配、工具、持久化、沙箱与审批策略、设置、凭据、遥测这些几乎所有运行方式都要的东西；`dsh-web-app` 在它之上加浏览器界面，`dsh-headless` 加无界面运行器，以此类推。有个刻意留下的例外：`sdk-minimal` 是一个自足的最小包，不叠加 `dsh-base`，专门给想要极简依赖树的 SDK 用户。
- **Profile（运行配置）**：一个有名字的组合方案，写明叠加哪些 bundle、额外装哪些插件，还可以带自己的补丁文件。官方自带 `web`、`headless`、`sdk`、`sdk-minimal`、`acp` 五个。
- **Patch（补丁）**：以 id 为目标，整行替换某个插件的配置，或者插入新行。叠加顺序是：先按 profile 列出的顺序应用各 bundle，然后是 profile 自带的 `cordis.patch.yml`，再是用户主目录级的补丁，最后是命令行 `--patch` 传入的。越靠后优先级越高。

插件装上之后由 `plugin-manager` 服务管理运行期的增删改：装一个 bundle（底层走 pnpm，失败会自动还原 `package.json` 和锁文件）、启用停用某个插件、热重载（HMR）配置和模块。面对多个可用的公共插件注册表时，它选择第一个能正常响应的——装插件"从哪拿"不写死，哪个源活着就用哪个，一个源挂了不会卡住整个安装。

装插件还有一道**兼容性检查**：安装插件和 profile 启动时，对照插件声明支持的 dsh 版本范围（peer 依赖）检查运行时版本，范围不匹配的插件**拒绝加载**，除非用户显式确认精确版本豁免——豁免用 `version-exemptions` / `allow-version` / `revoke-version` 管理并持久化。拒绝时给出的是类型化的理由（typed refusal，"为什么不让装"是明确的原因而不是一句笼统的报错），而且不兼容提示里不暗示"可以让 agent 自行开豁免"——豁免是用户自己的决定，不甩给模型。

这套机制的回报是**可观测**：运行 `dsh --profile web --dump-config`，你机器上实际启动的整棵插件树会被完整打印出来，每一行都能被你自己的补丁替换。系统没有隐藏的组合过程，所见即所得。

插件树的周边还有两块。**插件市场**：Discover 标签页读取配置里声明的插件市场索引（format-1 校验、内联图标上限 32 KiB），宿主抓取 http(s) 索引后在 worker 线程解析并缓存，搜索用模糊的多语言匹配，安装时选定版本并检查 `engines.dsh` 兼容性；Creator 模式有 `plugin_market` 工具列索引、插件与版本；整包是显式的 opt-in 实验（提交 3de3a977e0）。**宿主版本门控**：浏览器页面只应用"启动自己所处版本"的宿主图与重建帧——宿主升级到另一个 release 后，页面收到的一切热替换都被忽略，弹一次"重新加载以使用新版本"的对话框；用户拒绝后停在旧版本，宿主再换 release 才会再次询问，页面只在内存里记住上次拒绝的 release（提交 f52abc04fa；release 是宿主的版本身份，由版本号加可选的源码提交号组成）。

### scope 与分层注册表

那么多插件往共享的 `ctx` 里注册东西，名字撞了怎么办？dsh 的答案是**按作用域（scope）分层**，而不是全局一刀切。

每个注册（一个工具、一个提示词分节、一个技能提供方）都会落到某一"层"：宿主和仓库自带的插件落在**全局层**；由某个 agent 预设（preset，一种"给特定智能体预置一组插件和配置"的机制）挂载的插件，落在**那个预设自己的层**。规则是：名字只在同一层内保证唯一，不要求全进程唯一。读取时，系统把全局层和当前作用域的层按链条合并，**离得近的那层直接赢**——当前层注册了同名工具，全局那个就被盖住。

好比公司总部有个规章叫"报销流程"，销售部自己也有一个"报销流程"。员工在销售部办公，按部门的走；名字重复没关系，因为裁决发生在具体的语境里。这让"特定场景特事特办"成为常态机制，而不是需要绕过的冲突。实现上这是 `packages/core/scope` 里的一个纯库（不依赖框架）：`ScopeKey` 是一个只比较身份的不透明对象，运行中的 dsh 直接拿活的 Agent 对象当 key；全局层始终存在，每个作用域的层按需创建，读取时按插入序合并、按作用域遮蔽。

### 事件的三类分工

官方架构文档说："事件就是扩展点，改大多数东西之前，第一个要决定的就是选哪类事件。"事件分三类：

- **会话事件（session events）**：持久的事实，追加到会话日志里，重启后还在。比如"用户说了什么""工具返回了什么"。
- **智能体事件（`agent/*`）**：携带活着的 Agent 对象，用来观察或拦截正在进行的工作。比如 `agent/pre-step`（某一步开始前）、`agent/request`（即将请求模型）。这些是活的、短暂的。
- **能力事件（`fs/*`、`tools/*`、`telemetry/*`）**：给某个具体能力挂策略和适配器。比如 `tools/pre-execute` 在每个工具执行前给安全策略一个放行或拦截的机会。

隐含的原则是：**"要留给以后查的"和"正在发生、要实时响应的"必须分开存储、分开传播**。混在一起，系统很快就分不清哪些是账、哪些是现场。

## 主轴：没有写死的核心，一切皆插件

上面这些机制拼起来，就是 dsh 对"框架写死"这个问题的完整回答，值得把因果链串一遍。

Cordis 让"可替换"在类型层面成立：服务按 `ctx.<key>` 查找而不是直接 import，换实现不用改调用方。三段式拆分（定义/提供方/使用方）把每个能力切成可独立替换的三瓣，换来"换一处、动全身"——把文件系统和子进程的提供方指向远程沙箱，整批能力跟着搬家。Profile/Bundle/Patch 让"怎么组合"本身成为可配置、可复现、可审计的对象，`--dump-config` 把组合结果完整打印。scope 分层让重名不冲突，特定场景可以特事特办。事件三类分工把扩展点标清楚，waterfall 模式给每个扩展点标准的拦截协议。

这条主轴的极致演示是 **Claude Code mods 兼容层**（实验性）：把 Claude Code（Anthropic 的编码 agent）的 mods（mod，Claude Code 生态里对 agent 行为的修改包）以 DSH 插件的形态跑起来。一个 mod 用 `defineMod()` 构建成标准 DSH 插件，围绕 `register(on, options)` 组织；桥接层是 ClaudeCodeMods 服务（`ctx.claudeCodeMods`），保管已加载的 mods 并转发它们的事件。设计上有几处克制：`prompt.submit` 的上下文改为追加在用户自己的 prompt 消息后面的文本块，桥接层不新增消息来源类型，持久化记录和重新生成的 schema 都因此省掉；mod 画的界面（Web band，用 Claude Code 的 Box/Text/Button 组件词汇画在 DSH 的主题 token 上）经 watchBand/pressBand 往返，按钮点击带着绘制时的代次号回去，防止点了上一个画面的按钮算到这一代的头上；官方兼容文档逐条列出 mod 经桥接与在原生环境里行为的差异（打包、事件、链、`$` 成员、绘制、测试），覆盖通读源码评估过的四个官方 mods。此前的 plugin.json/hooks.json 专用加载器、插件目录检测和动态 import 全部废弃——"修改包"就是插件，不再有第二套装载机制。用插件框架兼容竞品生态，等于把"扩展从哪来"的选择权交给用户。

代价也要说清：没有特权核心，就没有"改一行就好"的中心。任何功能都要走"定义、提供方、使用方"的完整拆分，简单改动的路径变长了。dsh 用配套设施补偿：`--dump-config` 让组合可见，文档和类型同源校验让约定不漂移（见"可复用的做法"）。

## Agent 循环

dsh 把 agent 的一次工作过程切成两级：

- **step（步）**：一次"问模型 + 执行模型要的工具"的完整往返。
- **turn（回合）**：零个或多个 step 的集合，从输入被认领开始，到没有任何欠着的事为止。

一个回合内部的顺序大致是：认领输入 → 组装系统提示词和工具清单 → `agent/pre-step` 决定放行哪些消息 → 请求模型 → 流式接收回复 → 逐个执行工具调用（`tools/pre-execute` → `tools/execute` → `tools/post-execute`）→ 如果工具结果需要再问模型，就开下一步 → 直到无事可做，`agent/turn-stopping` 之后关闭回合。

分两级的理由是**拦截点可以精确到步**。"工具执行前先过审批"插在 `tools/pre-execute` 就行，不用碰循环本身；"模型请求出错后决定要不要重试"有专门的 `agent/request-error`。粒度切细了，扩展点才能又多又稳。模型请求经 `llm-pi-ai` 包走 pi 项目的统一模型 API（pi-ai）发出，适配层支持 pi-ai 的会话级提示词更新与工具更新——会话中途的提示词与工具变更按 pi-ai 的语义传下去；借标准适配层的实际好处在这：上游协议演进，下游跟着升级就行。

### Agent 句柄与收件箱

插件（界面、钩子、编排器）编程时面对的是 `Agent` 句柄，它身上挂着会话、选项、状态和最关键的**收件箱（inbox）**。收件箱是两条有序的待处理消息队列，语义不同：

- `next-turn`：排队的普通输入，每条会在**自己的新回合**里被处理（`followup()` 投到这里）。
- `next-step`：急件，会在**当前回合最近的 step 边界**插进去（`steer()` 投到这里），像开车时乘客喊一句"前面路口右转"，不用等这趟到了再说。

还有第三种投递 `inject()`：只注入模型可见的上下文（文件变更通知、技能内容之类），**不唤醒**驱动器——agent 空闲时就先放着，下次被别的事情唤醒时捎上。取消（`cancel`）则带一个原因（用户取消、父级取消、钩子取消、销毁），这个原因会作为回合结束原因记进日志的 `turn/end` 事件，事后能查清"这回合为什么停"。

## 工具系统

工具是 AI 的手脚：读文件、跑命令、查网页，都是工具。dsh 里每个工具注册成一个 `ToolDefinition`，它有两副面孔，而且这两副面孔被硬性隔开：

- **给模型看的**只有名字、描述、参数说明三样（`ToolSchema`）。注册表在生成这份"说明书"时用显式白名单，只放行 `name`/`description`/`parameters` 三个字段。
- **程序内部用的**——真正干活的 `execute` 函数、输出声明 `output`、超时 `timeoutMs`、并发分类器、界面展示回调——一个字都不许混进发给模型的内容。

为什么这么严？发给模型的每个字都占用它的注意力，内部细节漏出去轻则带偏模型，重则被恶意构造的内容利用。超时时间跟模型毫无关系，模型知道了只会分心。

工具执行不是"直接跑"，而是一条带检查环节的 pipeline：`tools/pre-execute`（可重排的放行/拒绝/询问瀑布，审批就挂在这里）→ 注册的单向守卫 → `tools/execute`（工具在此执行，超时策略作为包装器挂在这里）→ `tools/post-execute`（检查或替换结果）→ 工具自带的收尾回调 → 不可变的最终结果。想给所有工具统一加一道检查，写一个插件挂上事件即可，不用逐个改工具。

两个实用设计。其一，工具可以声明自己是"并发安全"的：模型一次发出多个工具调用时，声明安全的调用可以并行跑，没声明的独占执行。其二，`ToolRestriction` 允许一个作用域对自己继承来的工具做 allow/deny 过滤（给 subagent 裁剪工具时用），而被作用域自己注册的工具不受过滤影响——裁剪别人的，不裁自己的。

dsh 还支持 PTC 模式（programmatic tool calling，程序化工具调用）：让一段代码在运行环境里直接编排多个工具调用，而不是每个工具都绕模型一圈。安全上有个收紧：PTC 模式下只有"带父调用的子派发"允许执行真正的工具名，模型直接发起的调用会被拒绝——编排权收进沙箱里，模型只能递任务单，不能直接下手。

联网能力走 DeepSeek 自家的 Search 与 Fetch API（两组 web 工具，0.2.1-rc 线），整套放在设置开关后面、默认关闭，由用户显式打开（提交 fda98dadd2）。实现里有个省 token 的细节：搜索分出的辅助 Messages 请求（给搜索接口做准备的内部请求）**显式关闭了 thinking**——这些辅助回合的生成正文会被 provider 丢弃，推理 token 根本没有读者；DeepSeek 模型默认开思考，不关的话每次搜索都白付一份延迟和输出 token（配套提交针对 #6099）。"谁会读这段输出"决定"要不要生成它"，这个判断对一切辅助请求都适用。

模型与界面的交互还有一条结构化通道：`propose_action` 工具（`packages/experimental/action-cards`，2026-10 下旬，提交 9980af2d48）。一个实验包想在回答下方提供"要不要顺手创建一个个性化页面"这类可选动作，不需要自己加工具：模型先加载该实验的技能，再调 `propose_action` 提出提案；卡片在回合结束后出现在回答下方（浏览器半边在 `packages/experimental/client-ui-action-cards`），用户不点它就什么都不跑，用户的每次选择会被记录、在下一次请求时报告给模型。卡片类型（card kind）是可注册的——登记动作名、技能、详情 schema、动词与处理器，个性化页面与插件推荐都已改成这种类型（提交 9b04d772b9、fcb7340be1），两者现已合并为实验插件「个性化推荐」（提交 d6d51be4cb）。成本上有一条硬约束：会话里没有任何卡片技能加载之前，这个工具不出现——不占提示词，也不给模型空转的机会。

## 系统提示词

系统提示词是每次对话前程序悄悄发给模型的那段"公司规章"：你是谁、能用什么工具、要遵守什么规则。多数程序把这段话写死在代码里，dsh 把它做成了一套拼装系统：

- **分节注册**。每个插件可以贡献一段提示词（`PromptSection`），带名字和排序号 `order`。组装时按排序号从小到大拼接。一本员工手册不是一个人写的，HR 写考勤、技术部写规范、安全部写守则，最后按章节装订。
- **固定槽位**。"人设前缀"（`deployment:persona-prefix`）和"人设后缀"两个位置是预留的，全局配置和各插件都可以往里填，保证身份设定总出现在固定位置。
- **`complete` 节**。某个插件可以声明"我的这段就是完整提示词"。组装流程照常跑完（工具、变量还要解析），但最终只保留这一节。声明了两个以上就会报错——"谁说了算"必须唯一。
- **拼装结果也是事件**。拼好的提示词不是塞进请求字段，而是作为 `system/message` 事件记入日志（它排在表面的第 0 位），提示词变了就替换这个节点。于是"模型当时看到的规章是什么"也能从日志重放出来，和事件溯源体系完全一致。
- **`knownNames`：报错要能分清两种情况**。每个工具提供方除了交出本次可见的工具清单，还要交出"限制之前的全部工具名"。这样配置里写错工具名时，系统能区分"你拼错了"和"这个工具被故意藏起来了"——排查问题时这两种情况的处理方向完全不同。

## 审批与安全

审批子系统只回答一个问题：这个具体动作，现在能不能做？模型想跑一条命令、写一个文件，先问一遍。

它的答案有几条硬规则：

- **结果是一个闭集**，只有四种：`allowed-once`（只放行这一次，下次再问）、`rejected`（明确拒绝）、`cancelled`（请求方撤回了）、`unavailable`（无人应答）。
- **fail-closed（失败即关闭）**：只要没有拿到明确的 `allowed-once`，一律按拒绝处理。应答的人不在岗、应答者不是这个 agent 的属主、应答过程抛了异常，统统归为 `unavailable` 然后拒绝。门卫不在岗，结果是"不许进"，绝不会因为"联系不上门卫"就放行。**没有明确的允许，就是不允许**——这是安全系统的铁律。
- **策略按场景切**。每个会话可配 `ask`（默认，去问人）或 `never`（不问任何人，所有请求直接拒绝）。后者给 CI、定时任务这类无人值守场景用：同一个框架，陪人用的时候问一下，全自动跑的时候一律拒绝。
- **审批过程本身也进日志**。`approval/asked`（问了）和 `approval/decided`（批了什么）作为一对审计事件记入会话日志（仅日志、不进模型上下文），还有独立的 ID 类型防止和工具调用的 ID 混淆。谁在什么时候批了什么，永久可查。
- **审批请求里故意不放工具参数**，而是带一个 `callId` 指回已经流式展示给用户的那个工具调用。界面把审批弹窗挂在那条调用上就行，不用再渲染一份参数副本——两份副本迟早改得不一样。

### 远程访问与调用身份

dsh 可以从别的设备连进来用（远程访问），权限与身份有两块设计。

**非所有者的调用与事件按资源放行（RBAC）。** 远程调用不是"连上就能用一切"：每个远程方法可以在 Typert（dsh 的类型化远程协议层）里声明自己触碰的资源（比如某个会话、某个文件夹），网关在实际查找发生之前，就从已经过类型验证的参数里解析出这次调用涉及的资源（packages/api/gateway/src/access.ts 的 `callResources`，模块注释自述 "Resource resolution for non-owner access decisions"）；策略据此放行或拒绝非所有者的调用与转发事件（提交 d7bd68ee7a，配套 767 行的网关访问测试）。资源来源有优先级：方法的 `resources` 读取器优先，其次各查找参数的声明与 Context 身份适配，最后落到默认字段；解析不出合法资源就按无效处理。

**连接的两端都带身份。** API 连接的握手按操作者（operator）作用域隔离：不同 API 操作者各有自己的连接语义，浏览器身份本身不受影响（提交 0f7ac58213）；显式对端连接携带调用者主体，用户消息来源记录非所有者主体（peer-principal 设计记录）。

## 持久化与恢复

**事件溯源（event sourcing）**是一个值得先讲清的通用模式：记录"发生过的每一件事"（流水），而不是只记录"当前状态"（余额）。存流水的好处是细节永不丢失，随时可以重放、审计，算法改进后还能用新逻辑重算历史。

dsh 的会话（Session）就是这样一条**只追加的日志（append-only log）**：只能往末尾加事件，已有的记录不许改。它是整个对话唯一的正式记录。最反直觉也最关键的一条设计是：**发给模型的消息历史不是单独存一份的，而是每次需要时从日志重新推导**（`deriveMessages()`）。日志里有 `turn/start`、`step/start`、`user/message`、`assistant/message`、`tool/call`、`tool/result` 等十几种核心事件类型，按序重放就得到当前该发给模型的完整上下文。

几个关键细节：

- **四种"表面事件"与"仅日志事件"**。只有四种事件会产生模型可见的消息：`system/message`、`user/message`、`assistant/message`、`tool/result`。其余事件（比如回合边界标记 `turn/start`/`turn/end`、记录请求配置的 `request/header`）只进日志、不进模型上下文。这条边界在类型层面强制：仅日志事件想带表面元数据，编译都过不了。
- **失败尝试也不丢**。模型一次输出如果失败、被重试或中途取消，dsh 把它记成 `assistant/attempt`（附带原始流），不进模型上下文，但审计时能看到"当时模型实际输出了什么"；成功的那条 `assistant/message` 则把产生它的完整带时间戳的流嵌入事件本身。派生历史、界面增量、失败排查各取所需，互不污染。
- **派生历史的周边设施**。围绕这条日志还有一小组配套服务：会话查询（`session-query`）提供有边界的精确读取、关系追踪和全文搜索；会话投影（`session-projection`）让各功能把"已提交事件"增量折叠成自己要的内存状态（subagent 列表、任务板都靠它）；令牌计量（`token-meter`）负责估算和重放。它们全都只读日志、不做第二份存储。
- **`ignorable` 标记**。每个事件可以声明"读者如果不认识我这个类型，可以安全跳过"；没声明的，旧版程序读到不认识的事件必须拒绝重建会话，而不是悄悄扔掉——因为一个不认识的事件可能改变对后续日志的解释。宁可麻烦，不可读错。
- **"进了模型的就是记了日志"**。这是一条运行时不变量（程序自己反复断言的规则）：任何到达模型的输入都必须能从日志重建。想给模型塞一段新内容？必须先发明一种会话事件。这条规则把"日志是唯一正式记录"从口号变成了机器强制。

**存储格式与崩溃安全。** 日志可以落成 JSONL 文件（每行一个 JSON 事件，可选 zstd 压缩），带版本号（`session.v1.jsonl`）。已提交的文件永不重命名、永不改写；升级格式时，新文件在旧文件旁边"独占式"发布，读写两端各走一条相邻版本的迁移链。崩溃后重启，程序能认出"写了一半的尾巴"并按规则修复。原子写入配的**锁**也做了崩溃安全：锁记录里存持有进程的 PID、主机名和一个随机串（nonce，一次性随机标识），进程异常退出（Ctrl-C、崩溃、收尾时取消的安装）往往来不及删锁，后来的写入者不再无限等下去——发现"本主机的锁记录 + 进程探针确认持有者已不存在"，就通过一个专门的接管标记文件认领锁、重读确认后接管，旧版本留下的只有 PID 的锁记录也照样接管；空记录、不完整记录、别的主机的记录、持有者还活着的记录则继续等待。崩溃留下的锁，从"要人工删"变成了"自动交给活着的写入者"。

**迁移是显式可见的。** 会话的存储格式状态可以查询：查一个还没加载的会话，能得知它是否 `migration-required`（需要先迁移才能用）。读取投影时，遇到这种旧格式会话不当场迁移，而是返回"需要迁移"的标记，附一份缓存的历史投影提示，让调用方自己决定下一步；分叉请求有 `allowMigration` 预检开关（默认 true）——设为 false 时，源会话尚未迁移就明确报 `session/migration-required`（"先打开源会话完成迁移再分叉"），而不是悄悄迁完再分。界面在展开会话前显示头部的迁移状态，客户端对需要迁移的分叉和 subagent 发现给出引导。老格式会话"看得见、可拒绝、受引导"，迁移不藏在读取路径里顺手发生。

## 上下文压缩

对话太长时，把旧内容浓缩成一份摘要腾地方，这就是上下文压缩（compaction）。dsh 的压缩是一个可选能力（三段式拆分，换摘要算法不用动核心），它的可靠性设计围绕一件事：**系统要能诚实地区分"没做完"和"做完了"**。

压缩过程用三个事件做标记：`compaction/start`（记日志即获得锁）、`compaction/summary`（记录摘要内容、覆盖范围、token 数等）、`compaction/end`（释放锁）。锁保证同一个会话不会两处同时压缩。关键的细节在于**锁的释放放在整个操作的最后**：先记 `start`，再做摘要、写摘要、替换表面历史，全部完成后才记 `end`。这样如果程序中途崩溃，日志里留下的是"有一个 `start` 但没有配对的 `end`"——一眼就能看出这次压缩没做完。反过来，如果把 `end` 提前写，崩溃时就会留下"压缩已完成"的假记录，而摘要其实没写完整。宁可留下清晰的半途记录，也不要伪造完成。

摘要怎么进对话？它不是单独存一份，而是作为一条 `user/message` 事件写入，附带一个"替换历史"的操作（`surfaceOp: { op: 'replace', startSeq, endSeq }`），把摘要顶替掉选定的旧内容。压缩后的摘要依然以事件的形式存在于日志里，和事件溯源体系一致——原始内容也没丢，还在日志深处，只是不再进入模型上下文。

压缩还有一道"前置减负"：在挑范围之前，可以先跑一个工具结果剪枝器（tool-result pruner），把过长的工具输出做头/中/尾截断替换（按 Unicode 码点切，避免切坏代理对字符），通常这一步就不用动整段历史了。

## 技能系统

技能（skill）是给 AI 准备的说明书：一个 Markdown 文件，教它"遇到这类事按这个章法办"，比如"周报的格式是这三段"。dsh 的技能系统值得学的是它管理"来源各异的技能"的章法：

- **来源可插拔**。`ctx.skills` 是服务定义；提供方可以是本地目录（官方本地提供方）、随程序打包的内置技能、也可以是远程技能库；使用方（`skill` 工具）负责把技能喂给模型。想加一种新来源，写一个新提供方挂进去即可。
- **本地目录有优先级**。项目根的 `.dsh/skills` 优先级最高（rank 100），然后是 `.agents/skills`、自定义目录、用户主目录，最后是打包内置（rank 600）。项目里的技能盖过用户级的——离你的代码越近的话越可信、越具体。
- **发现结果要诚实**。列出技能时，如果某个提供方查询失败了，系统记条日志，然后**从结果里省略它**，而不是整个崩掉；提供方还可以显式声明 `complete: false`——"我这次没查全，但这些先用着"。声明不完整的结果可以用，但**不会被缓存**，下次重新查。发现进行到一半、技能目录又变了，系统重试一次；再变就返回手头最新的候选并标记"不完整、不缓存"。系统不怕不完整，只怕假装完整。
- **变更通知只喊"变了"**。技能目录变化时发一个 `skills/change` 事件，这个事件不带任何 diff（不带"具体哪里变了"）。收到通知的使用方自己按需重查全量目录。附带 diff 的通知在多处变化交错时几乎必然出错；"收到通知就重查一遍"笨一点，但永远正确。
- **谁能调用也分层**。每个技能有两个独立开关：模型可调用（`modelInvocable`）和用户可调用（`userInvocable`）。会话开始时给模型注入一份技能目录（只有名字和描述，不带正文），模型想用某个技能时调 `skill` 工具加载完整内容——正文按需取，目录保持精简。

## 并发与多任务

### subagent

subagent 是一个 agent 把部分工作派给另一个更小的 agent 的机制。dsh 把它也做成一个可选能力，而且和 Bash 那种"只能有一个执行者"的能力不同——**subagent 允许多个提供方按名字共存**。官方自带六个后端：进程内派生（spawn）、进程内 fork（subagent 继承父对话历史的副本）、ACP 协议、以及对接 Codex、Claude Code、DSH SDK 三个外部产品。同一个程序里可以同时挂"自己引擎派生"和"调用外部工具"两种后端，按名字选用。

这个子系统有三条突出设计：

- **能力提前宣告，接不了就明确拒绝**。每个后端在干活前用一份静态描述符宣告自己支持什么：能不能自定义模型参数（`agentOptions`）、能不能约定输出格式（`outputSchema`）、能不能限制派发深度（`depthLimit`）、能不能裁剪工具（`toolFilter`）、能不能设人设（`persona`）。请求需要的功能如果选中的后端没宣告支持，立即抛出类型明确的错误（`UNSUPPORTED_CAPABILITY`），绝不"接了活然后悄悄跳过你不支持的部分"。官方原话叫 fail loud, no silent degradation——承接任务时当场说明干不了，比假装接下、交付时才发现缺一块可靠得多。
- **派发深度有绝对上限**。subagent 自己还能再派 subagent，dsh 给"套娃层数"设了上限：每个 subagent 启动时计算自己的深度，超过上限直接拒绝。凡是"自己能生成自己"的机制，都要有深度或数量上限，否则 A 派 B、B 派 C 无限套下去耗尽资源。
- **可延续的 subagent（continuable）**。除了"一次性派活收结果"，还有一种 subagent：任务做完后会话留着，可以继续跟它对话。为此有一套"激活（Activation）"管理：subagent 的持久会话不常驻内存，要用时才重建一个活动实例；空闲、队列清空、子孙全部收尾后，实例才被释放，持久会话仍在。配套的纪律是**发消息只许发给直系亲属**——`send_message` 只能发给直接父代理或直接 subagent，不能越级给"叔叔"或"孙子"发。谁是你的上下级、谁能给谁下指令，关系必须清楚。中断（interrupt）subagent 同样要验明正身：要么是人拿着直系父会话的地址，要么是调用方确实在目标的祖先链上，否则拒绝。

### agent-team 协作

一个 AI 干大任务容易顾此失彼，dsh（实验性功能）让多个 AI 组队：一个组长（Lead Session）带若干组员（teammates），大家并行干活、经组长汇总。它的工程内核是把协作建立在可靠的消息与任务机制上：

- **组员有确定的状态机**。每个组员有一份快照记录（名字、描述、模型、所处阶段），从 `provisioning`（准备中）出发，最终一定到达 `active`（活跃）或 `failed`（失败），没有第三种含糊状态。而"此刻忙不忙"（running/idle/inactive）是运行时另行推导出来的观察值，**绝不改写正式记录**——把"事实"和"观察"分开，恢复和判断才有依据。
- **持久化邮箱（durable mailbox）**。组员之间传消息走"先存后送，确认才删"：组长先把消息完整存下来，目标组员真正收到并确认后才算送达；公式是**已排队 − 已送达 = 待恢复邮箱**，中途崩溃后没送达的消息重启接着送，不会丢。投递方式看对方状态：忙的在下个 step 边界收，闲的收到就开新回合，长期不活跃的冷启动恢复。这是消息队列的经典做法（类比挂号信：先登记，签收后才销号）。
- **重试必然带来重复，重复靠去重消化**。既然"没送达就重发"，同一条消息就可能到两次。dsh 在收件箱和历史消息里都保留消息 ID 和发送者，作为去重键：同一条消息到第二遍时能被认出"已处理过"。支持重试的系统，幂等（同一操作做多次结果不变）是必备的配套。
- **共享任务板是一张有向无环图（DAG）**。任务之间可以声明"被谁阻塞"（`blockedBy`），系统保证不会成环；每次修改带版本号做 compare-and-set（比较后再写入，防止两人基于旧版本互相覆盖）；另外有"写入范围"（`writeScopes`）字段标注每个任务大概会动哪些路径——它是建议性的标注而非强制锁，用来提醒"这两个任务的改动范围有重叠，注意协调"。

## 启动流程与启动加速

启动分两层看。**流程层**：`app-boot` 包从 Harness 主目录读 profile 配置（`cordis.yml`），先加载 `.env` 环境变量，再按前文说的层叠顺序（bundle 依次、profile 补丁、主目录补丁、命令行补丁）组装插件树，启动失败时报清晰错误而不是甩一屏堆栈。**性能层**：0.1.6 版本线花了大量力气做启动提速，思路统一是**延迟加载**——不是所有东西都在启动时备好，而是用到的才加载。具体例子：类型系统（typert）生成的结构改成"第一次用到才构建"；可选的原生依赖（用 C/C++ 编写、导入很慢的组件）推迟到确认需要才导入；网页端的客户端组装也推迟了。判断标准不是"能延就延"，而是：启动路径上马上要用的必须提前备好，冷门和可选的才延。而且"延迟"本身有统一实现（一个相对调用方的延迟加载工具），不是各处自己造。

这条线上还有两个"崩溃/失败"场景的处理。一是**批量脚本失败要能恢复**：一个应用批次就是一个脚本，按顺序注册所有包，启动时只请求一次；如果这一下请求瞬时失败，整个批次的每一行都会跟着失败，还会通过依赖等待连累所有引用这些包的行。现在会从失败的批次脚本中恢复，并把导入错误记录下来。二是**致命错误要留下报告**：桌面端弹出"致命恢复"对话框之前，会先写一份崩溃报告文件——此前对话框只显示错误最后几行、并承诺"完整诊断在控制台里"，可打包安装的应用根本没有控制台。"报错要能被人真正看到"被当成一个要解决的问题来修，而不是想当然。异常收尾也补齐了：启动过程把**未捕获异常**（程序运行中没被任何代码接住的意外错误）统一按致命处理走 fail-loud 路径——此前只给"未处理的 Promise 拒绝"装了处理，从流式数据监听器里**同步抛出**的异常会掉进运行时的默认路径，只打印一下就退出，连释放钩子都不走。补上这个洞之后，"任何异常都走 fail-loud 收尾"才没有例外。

## 设计原则

- **没有特权核心，代价是没有"改一行就好"的中心**。一切皆插件换来极致的可替换性，但任何功能都要走"定义、提供方、使用方"的完整拆分，简单改动的路径变长了。dsh 用配套设施补偿：`--dump-config` 让组合可见，文档和类型同源校验让约定不漂移。
- **日志优先**。"进了模型的就是记了日志"这条不变量，让 fork（从某个回合分叉）、resume（恢复会话）、转写、遥测全部变成"从同一份日志做不同投影"，不用各存一份。代价是日志比"只存当前状态"大，dsh 用压缩、剪枝和"仅日志事件不进模型"的区分来控制。
- **两类失败，两种答案**。安全边界（审批）用 fail-closed：不明确允许即拒绝；能力边界（subagent 后端）用 fail loud：不支持就明确报错。两者的共同点是绝不静默：悄悄放行和悄悄降级是系统里最贵的两种 bug。
- **诚实暴露未完成**。压缩的锁最后释放，崩溃留下"有 start 没 end"的可检测痕迹；技能发现可以声明"不完整"且不缓存。系统不假装完成、不硬撑完整，把"未完成"做成一种可识别的正常状态。
- **冲突交给语境，细节留给需要的人**。重名工具和技能靠 scope 层"就近遮蔽"裁决，不搞全局唯一；变更通知只喊"变了"，diff 让使用方自己查。中心不做它做不好的裁决，只维护裁决规则。
- **事实与观察分离**。组员快照只存确定的生命周期事实，忙闲是推导值；会话日志是事实，投影（session projection）是观察。改观察不改事实，重放才永远对得上。

## 可复用的做法

- **对外接口白名单化**。工具"说明书"只放行三个字段，内部实现靠类型系统禁止泄漏。对外暴露最小够用的信息，是性能考虑也是安全考虑。
- **branded ID + 判别联合**。跨包传递的 ID 全部加"品牌"（`SessionId` 不能传给要 `ToolCallId` 的地方，虽然都是字符串）；可扩展的类型用"Map 接口 + `keyof` 派生联合"的模式，插件用声明合并（declaration merging，TypeScript 允许在别的模块里给已有接口补字段的语法）加新变体，不用改原包。类型层面的这些纪律，换来的是重构时的编译器护航。
- **文档与代码同源校验**。子系统文档里的类型声明用特殊代码块从源码粘贴，`pnpm run verify-type-equiv` 校验没有漂移；服务与事件参考由脚本从源码生成（`gen-cordis-catalog`），CI 校验新鲜度。文档烂掉的根源是"文档和代码是两份工"，让文档变成代码的另一种视图就断了这个根。
- **崩溃安全的时序设计**。"先记开始、最后记结束"这种顺序安排，成本为零，却决定了崩溃后系统分不分得清"没做完"和"做完了"。写任何有中间状态的操作（上传、迁移、构建）时都值得先想这一层。
- **版本化文件格式 + 只增不改**。会话文件带版本号，已提交文件永不改写，升级靠"旁边发布新版本 + 相邻迁移链"。这让任何时刻的磁盘数据都有明确的解释规则，回滚和排错都有据可依。
- **把"可观测性"做成产品功能**。`dsh --profile web --dump-config` 打印实际生效的插件树、审计事件记录每次审批、日志可完整重放对话——排错需要的信息不是靠翻日志碰运气，而是一等公民的输出。
- **约定式提交 + 按范围统计**。dsh 的提交信息全部遵循"类型(范围): 描述"格式（如 `fix(web)`、`feat(desktop)`），想看一个大版本的重心，按类型和范围分组统计提交即可。

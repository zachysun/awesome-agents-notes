dsh-superagent 是 DeepSeek 团队开源的研究原型（README.md:3 明确声明仅供研究参考，代码从团队的日常开发工作发展而来，大部分工程由编码 agent 完成），副标题是 "Towards a More Autonomous Agent System"，GitHub 上 star 数 1.7 万。它和本笔记另一篇的主角 DeepSeek Harness 出自同一个团队，并且建立在 Harness 之上：Harness 是通用的 agent 运行时（负责模型接入、工具循环、权限、持久化这些基础能力，详见 [deepseek-harness.md](deepseek-harness.md)），dsh-superagent 在这些能力之上实现了一个面向具体场景的应用——让 agent 作为一个团队的常驻成员，自己监听一个 GitHub 仓库（可选加飞书），有人发起工作请求就接受请求、实现改动、交付结果、汇报进展，全程尽量不打扰人。

仓库 2026-10-31 才创建，只有一个提交，92 个 TypeScript 文件约 1.2 万行，外加 9 篇编号文档（docs/000 到 008，必须按顺序读，每篇只依赖前面的）、十几个提示词文件和 30 多个测试文件。README 里还提到一篇论文《Exploring Super-agent Design: Towards a More Autonomous Agent System》：开源版本与论文描述的内部实现不完全一致，论文里一部分设计是未来方向，这个原型里没有实现。

这份笔记按问题组织，讲清每个机制现在是怎么做的、为什么这么做。关键论断都带源码位置。

## 它要解决什么问题

Harness 解决的是"一个 agent 会话怎么稳定运行"：模型怎么接、工具怎么调、权限怎么管、崩溃后怎么恢复。但它回答不了下一个问题：**agent 能不能作为一个团队的常驻成员，自己接受工作请求？** 一个编码 agent 如果只能人坐在终端前对话，它就只是个工具；如果能自己监听 Issue 列表、评论区、群聊，被指名就处理请求，完成后在原对话里交付一个 pull request（PR，拉取请求，GitHub 上提议合并代码的标准方式），它才像一个团队成员。

这个跃迁带来一个 Harness 不处理的核心矛盾：**一个能替整个团队工作的 agent，也能消耗整个团队的注意力。** 它每发一条消息、每提一个 PR、每问一个问题，都有真实的人要花时间读。项目把这件事定成最高原则（docs/000-philosophy.md:5）：尽可能少占用人的注意力，尽可能多地给出价值。每条消息、每个通知、每个问题、每个面板元素都要付出别人的注意力，价值必须大于代价，代价大于价值的东西删掉。

从这条原则推出一串具体纪律（docs/000-philosophy.md 第 "What follows for the agent" 节）：

- 只在被要求时工作，或者团队写下的规则允许时工作。请求必须直接指名 agent、来自允许名单上的人；没人要求的工作需要一条团队写好的规则，而且先进入只记录"本来会做什么"的观察模式。
- 只在"有人必须行动"或"有人能用上结果"时说话。工作期间保持安静，结果就绪了、需要决策了、无法完成时才再开口。消息默认一句话，硬上限 100 词（prompts/replies.md:27）。
- 一次只问一个具体问题，用结构化形式送到人面前，问题不淹没在长报告里。
- 按影响停，按投入干：本地改动一路做到可审查为止；需要设计决策的改动带着明确的问题停下来。
- 诚实汇报：草稿标未完成，失败报成失败，限制不绕过。

README 的第一段安装指引也体现这个哲学：安装步骤多，所以让编码 agent 协助你完成安装（SETUP.md 就是给它照着执行的脚本），它一次问一个短问题、先展示完整计划再动手。

## 它和 DeepSeek Harness 的关系

整个项目以 bundle（打包的插件集合）形式安装进一个专用的 DeepSeek Harness profile（profile 是 Harness 的独立配置目录，这里叫 `superagent`，与个人日常用的 profile 分开，因为插件会改进程级的 PATH 和 git 设置，需要独立重启）。bundle 的补丁文件 cordis.patch.yml 插入三个插件（cordis.patch.yml:4-12）：主插件 `dsh-superagent`（领域引擎、面板、执行器）、GitHub 来源插件 `dsh-superagent/github-watch`、飞书来源插件 `dsh-superagent/feishu-watch`（默认禁用，需要时再开）。

它定义了两个 agent preset（预设，一组打包好的插件配置，决定一个 Session 有哪些工具、什么行为，cordis.patch.yml:20 与 :125）：

- `dsh-superagent-worker`：执行器 Session 专用。以 Harness 的 `standard` 预设为基础，只保留执行工作所需的工具；前台 shell 命令超过 5 秒自动转入后台 job，让执行器在下一步就能收到新消息，无须等待一条长命令执行完毕（cordis.patch.yml:20-28 的注释写明了这个动机）。
- `dsh-superagent-router`：主 Session 专用，同样的 5 秒限制，工具集更小，只够路由。

两个角色贯穿全项目：**主 Session**（代码和提示词里叫 orchestrator，主持人）负责评估候选、接单派工、转达报告；**执行器 Session**（worker）负责一个工单的具体技术工作。执行器的 subagent（subagent，从执行器派出去执行子任务的独立 agent 实例）用 Harness 的 `standard` 预设，60 秒才转后台——subagent 的 job 在它结束时就终止，不需要那么急（docs/003-execution.md "Worker subagents" 节）。

dsh-superagent 自己不接模型、不实现工具循环、不存会话——这些全是 Harness 的能力，它只做三件 Harness 不做的事：决定哪些事件值得启动新工作（评估与授权）、管理工作的生命周期（工单）、以及控制注意力（消息与面板）。

## 领域模型：八个概念

docs/001-domain.md 定义了整个系统的词汇表，代码、工具、面板、文档只用这些词。核心八个：

| 概念 | 中文 | 它是什么 | 关键规则 |
|---|---|---|---|
| Source | 来源 | 一条事件流。kind 是可复用的实现（GitHub、飞书），instance 是一份具体配置 | 持有自己的读取位置和 bot 身份；进入领域之前丢掉 bot 自己的消息和没在监听范围内的事件；重启不重放事件 |
| Trigger | 触发 | 一条不可变事件，带 Source 自己的元数据（发送者身份等） | 幂等单元：同一个 Trigger 两次接收只产生一个工单（src/core/intake.ts:23 靠 `triggers.get(id)` 判重返回 duplicate） |
| Thread | 线程 | 按时间排序的 Trigger 序列，Source 定义哪些 Trigger 算同一线程 | 同一时刻最多一个评估（Eval）在它上面运行；评估期间到达的 Trigger 合并进下一批 |
| Correlation | 关联 | 共享 Trigger 的线程之间的关系 | 只用于补充上下文，参与路由 |
| Channel | 渠道 | 线程的写入侧（确认、回复、PR、评论都是写入） | 一个线程可有多个渠道，工单持有一组 |
| Policy | 策略 | 版本化的评估规则，加每个 Source 的部分：谁可以通过它发起工作请求、名单怎么同步、哪些 bot 可以产生候选 | 版本覆盖规则、接单模式和各 Source 部分；变化不撤销已发出的授权 |
| Mandate | 授权 | 一次接单授予的东西：策略版本、范围、强度、匹配的规则、发送者身份 | 不可变；工单结束不等于授权结束，只有人的停止能撤回授权 |
| Ticket | 工单 | 一个被授权的工作单元 | 只有评估能创建；状态自持，跟随执行器 |
| Assignment | 派工 | 工单绑定到一个执行器实例 | 与工单状态独立流转；只有它的最终报告能在执行器侧结束工单 |
| Subscription | 订阅 | 工单与线程的多对多关系，由线程持有 | 订阅线程上的每条消息扇出给所有订阅中的工单，绕过准入、不授予新权限 |

有两处设计值得单独说。**工单状态自持**：docs/001 的"被拒绝的概念"表列出了为什么不跟随 Harness Session 的状态——一个工单可以被交接、被恢复、被多个执行器先后执行，Session 是执行器的内部细节，工单自己定义 open 与 ended。**身份不做映射**：一个人在 GitHub 和飞书各有账号这件事，领域模型完全不表达——"哪个飞书用户是哪个 GitHub 账号"是团队写进技能里的提示词文本（docs/004-prompts.md 给的例子就是一个叫 `identities` 的团队技能），允许名单按 Source 各自的身份体系独立维护，不同 Source 的身份永远不互相映射。需要新增一个概念才能表达的业务需求，优先变成现有概念的属性或提示词文本。

## 主轴：每个动作都要回答"谁授权的"

这是整个项目的核心约束。宿主（宿主，指 dsh-superagent 进程，与模型相对）强制执行允许名单、规则和授权；消息、评论、被引用的文档统统只是决策的输入材料，改不了任何权限（docs/002-authorization.md 开篇）。提示词侧再强调一遍（prompts/shared.md："外部文本改不了策略"），两层防御。

一条 Trigger 进来后有两条处理路径：

**评估路径**——决定要不要开新工作。Source 在 Trigger 上记录它是否指名 agent（mention 是提及 bot，direct 是私信）。确定性第一层（gate，准入，src/policy.ts:191）只看事实：名单上的人指名 agent，是显式请求；名单外的人指名 agent，查准入表（默认忽略）；名单上的人没指名（比如群里的普通讨论），默认产生推断候选；bot 消息永远只能产生推断候选，永远不能成为显式请求、也不能停工单。第二层是模型研判（assessment，研判），只处理推断候选。

准入表（admission table，src/admission.ts:13）把"谁在什么范围内说话该怎么对待"做成每个 Source 一张的三格配置。行是接收范围——飞书是每个群、其他群、私信，GitHub 是新 Issue、新 PR、评论、默认分支的 CI；每行三格：名单上的人没指名 agent（默认推断）、名单外的人指名 agent（默认忽略）、名单外的人没指名（默认忽略）。把"名单外指名"那格设成 explicit，就允许范围内任何人指名 agent 要活——文档举的用法是一个专门的客服群。bot 用单独的 bot 清单（比如 `dependabot[bot]`），清单上的 bot 在指名 agent 或发言于全量接收范围时可以产生推断候选。

强度分三档：explicit（显式）、inferred（推断）、not admitted（不接纳）。显式请求在任何接单模式下都工作；推断候选受接单模式管（src/policy.ts 的 EvalConfigSchema，`mode` 默认 observe）：

- `off`：一切推断候选不进评估。
- `observe`（默认）：推断候选照常评估，评估通过也只记录为带"would accept"（本来会接）标记的忽略决定，什么都不发生。
- `auto`：评估通过就真的接单。

项目对主动接单的谨慎全在这个默认值里：先让 agent 在 observe 模式下运行一段时间，人审阅它"本来会接什么"的记录，确认它的判断合理后再开启 auto（docs/002 第 "Accept mode and rules" 节明确写了这个推进路径）。

模型研判有硬约束（src/policy.ts:40 的 `assessmentOutcome`）：每条启用的规则必须恰好一条判定，多一条少一条都不行；接受需要方向已定、至少一条规则匹配、还要 `intent_evidence`（意图证据）。评估指令（prompts/admission.md）要求接受前确立三个独立事实：讨论针对本项目、参与者表达了让某个具体改动被实现的意图、方向足够确定到可以做一个小的本地修改；并给了正反例——"或许我们也该像他们那样显示未读数"是偏好表达，接；"这个按钮的文字怪怪的，改成 Save 就行"是已确立方向的实现请求，接。意图不确定时安静忽略，让后续消息继续积累，不拿日常闲聊去烦人。有一条捷径：候选卡片明显不碰任何启用规则（纯闲聊），主 Session 可以直接忽略，记录 `ignoredFromCard` 标记，避免一次完整评估（docs/002 第 "Routing candidates" 节）。

**订阅路径**——延续既有工作。订阅线程上的每条消息（包括 bot 和 CI 的）扇出给所有订阅中的工单，绕过准入、不授予任何新权限，每个工单仍然被自己的授权约束着。关键分工是：**人发到工单自己线程上的后续消息，由执行器决定**，不进评估；主 Session 只收到一条通知，而且此时只被允许停工，接单、附加、忽略、重排队都被拒绝。执行器要么在工单范围内处理请求，要么把它交还（handback，附一句理由）；交还的消息在没有任何工单拥有它之后，带着各执行器的理由作为候选进入新的评估。工单结束后授权还在：人在它线程上说一句话就能在同一个授权下恢复同一份工作，不需要新的评估或决定——除非是人亲手停的工单，那种收到任何东西。

授权（Mandate）的变更操作只有三个：评估接受时创建、人的停止撤回、恢复前重验失败时撤销（docs/002 第 "Resume and stop" 节）。重验（revalidate，src/policy.ts:213）在已结束工单恢复前进行：Source 还得在听原线程；推断授权要求现在仍是 auto 模式且匹配规则仍启用；靠准入表进来的授权要求今天的表对今天的发送者还能给出至少原有强度——把某人从名单移除，可以让一份靠名单格接的授权失效。

策略是版本化的（src/policy.ts:116 `policyVersion`，对规则、接单模式和各 Source 部分求哈希）。版本变化丢弃运行中的评估、把它们的 Trigger 重新排队，并给受影响的活工单发一条策略变化输入，说明匹配的规则改了什么、请求者是否还有资格、主动接单是否已关闭；不受影响的工单收不到任何通知；活工单的授权不立即撤销（src/policy.ts:144 `policyEffects` 算出哪些工单受影响）。这里能看到和很多系统不一样的一个取舍：改规则不终止运行中的工作——终止会留下半成品，改动被记录并送达就够了。

## 评估：判断要不要接活

评估（Eval）是一个线程上对一批 Trigger 的判断，输入是 Trigger 批、线程快照、线程上全部工单（包括已结束的——评估靠这个防止重复接单）和当前策略，输出一个决定（accept 接单、stop 停止、ignore 忽略、unavailable 未完成）。评估自身不持有状态（docs/001 领域模型表）。

实现是 src/core/evals.ts:27 的 `Evals` 类，它是引擎五个内部部件之一。调度上，评估由一个 2 秒一轮的调度器驱动（src/app/passes.ts:28，`setInterval` 2000 毫秒，同时任何命令可以要求立即轮一次）：轮到某个线程时，把排队中的 Trigger 连同评估期间到达的合并成一批，一次评估处理。

超时语义刻意对评估友好：计时从候选送达主 Session 才开始（`candidateDelivered` 记录送达时刻），等待投递的时间不算，没送达的候选永不过期。过期的评估把 Trigger 重新排队再试，连续两次过期后第三次记 `unavailable`（src/core/evals.ts:19 的 `REQUEUES = 2`）；评估失败也记 unavailable。unavailable 的决定只在满足四个条件时才上面板求人看：24 小时内、仍是线程上最新决定、没被 dismissed（人可以选择"再评估一次"或"忽略这个问题"）、线程既没排队也没在评估中。

评估时模型看到的上下文是有界的（docs/007 "Result shapes and assessment context" 节）：Trigger 文本最多 4000 字符；相关工单最多 8 个（活着的排前面）；线程窗口是前 5 条消息加触发消息两侧各 5 条（每条截到 400 字符，紧邻的两条 1200）；窗口外的消息只给 50 字符的存根加 id，评估工具 `orchestrator_eval_read` 按需展开。评估会话同时可以读仓库文件。窗口构造在 src/sources/admission-context.ts，GitHub 侧的线程上下文读取在 src/sources/github-read.ts:159。

## 执行：worker Session 与工单目录

一次接单创建的东西：工单、授权、订阅、第一次派工、一条确认回复——在一个事务里原子完成（docs/007 对 `decide` 命令的描述）。每个工单得到一个名为 `worker-<工单id>` 的执行器 Session 和一个以工单短名命名的目录（默认在 `<stateDir>/work` 下，docs/003-execution.md）。

**目录准备**：首次派工前，如果目录不存在，prepare 命令以 `sh` 在执行根目录执行一次，限时 10 分钟；失败则工单失败、记录输出，重试或人的消息会再试。文档给的典型命令用 `git worktree`（worktree，git 的多工作树功能，一个仓库同时检出多个分支到不同目录）从本地克隆建检出。PR 与工单的归属判定很简单：PR 分支名的最后一段等于工单短名（docs/003 第 "Preparing a Ticket directory" 节）。

**并发与 slot**：工单从启动（含准备）或唤醒闲置执行器的投递开始持有 worker slot，活跃回合期间一直持有。并发上限是 `maxWorkers`，默认 3（src/policy.ts:93）。关键细节是留了一个额外 slot 给人的消息或状态请求：普通 slot 满的时候，人的唤醒可以借用这个额外 slot——**新工作排队等待时，人继续既有工单的请求仍然能被处理**（docs/003 第 "Concurrency" 节）。WorkerSlots 类（src/executor/dsh.ts:171）负责在启动或唤醒前预留容量，唤醒优先于新启动。

**后台工作规则**（docs/003 "Background work and worker slots" 节，实现 src/executor/background.ts）：一个回合结束时如果还有 shell job 或 subagent 在运行，工单保留 slot、状态仍是 working，主 Session 收不到等待报告；job 完成带着结果在原 slot 唤醒执行器。回合的后台工作最多 30 分钟，到点 shell job 被终止、工单报 waiting，subagent 允许继续运行。把工作交给人之后（ready 报告、提问、blocked、failed）：subagent 立即停止；shell job——比如一个为人工验证而运行的服务——可以保留到派工结束，不占 slot、不受 30 分钟限制、完成也不唤醒，执行器下一回合自己读结果。

**失败与恢复**：执行器报 blocked 或 failed、或启动失败，工单不再自动接收输入——但工具都还在，人可以直接进入 Session 自己继续工作（docs/003 明确说这正是当初拒绝"失败时锁全部工具"这个设计的原因）。人的消息、一条非 blocked/failed 的后续报告、或面板上的重试按钮解除这个状态。模型提供方或网络的瞬态故障（HTTP 408/429/5xx、连接被拒/重置/超时）先重试三次、退避递增；prepare 命令失败不自动重试。重试（retry）结束当前派工、在同一个 Session、同一个目录、同一个分支、同一个 PR 上启动新派工。

**重启语义**：重启让运行中的派工以"host restarted"结束，新派工带恢复说明启动——告诉执行器先检查目录、git 历史和 GitHub 再重复任何外部动作，最老的工单先恢复。Session、目录、订阅、待处理消息、以及"哪些消息执行器 Session 已经读进历史"的记录全部跨重启保留。

"已读"的判定值得细看，因为它决定哪些未读消息在工单结束时回到评估（docs/003 重启节与 src/core/engine.ts 对 `inputsRead` 的注释）：一条输入算已读需要两步——Session 在某个步骤里认领它（写进历史），**并且**此后有一条报告或一次回合结束跟随。只认领了、步骤被取消或出错，不算已读。重派工时，上一份派工没被读走的输入重新投递，而 Session 里残留的旧副本被先取走，保证新投递是唯一一份。

**合并纪律**：默认执行器永远不启用 auto-merge（GitHub 会把合并记到开启者头上），合并要么由 Delivery requirements 指名的另一个账号的 CLI 完成，要么由人手动完成。内建默认指令允许 auto-merge 的条件很严格：为该工单开的 PR、已就绪、所需批准覆盖头提交、增删总行数小于 200；推下一版之前先撤回 auto-merge（docs/003 "Merging" 节）。文档同时诚实说明：这些指令约束 agent，GitHub 仓库侧的强制（分支保护、过期批准失效）要另外配置。

## 出站消息：先存储后执行

任何决定之后要做的事——转发候选给主 Session、启动派工、投递输入、发消息——**先存储，后执行**（docs/003 "Stored work" 节）。这个顺序换来的是崩溃安全：决定一旦写入数据库，后续动作丢失了也会被重试补上。

执行器是一个耐久的效果队列（Effects，src/app/effects.ts）：事务内 `enqueue`，提交后才执行；每种 kind 与 key 一行，同 key 的重排队替换载荷并立即到期、不改变队列顺序；失败指数退避；处理器抛 `Later`（src/app/effects.ts:5）表示"现在条件不具备"，延迟执行且不计失败次数（典型场景是没有空闲 worker slot）。六种效果：assessment（把候选送进主 Session 回合）、launch（启动派工）、delivery（把工单的待发输入送给运行中的派工）、relay（把 worker 报告或人的后续消息转进主 Session）、notice（注入通知但不唤醒）、reply（把渠道消息经 Source 发出去）。

渠道消息有专门的 Outbox（发件箱，src/app/outbox.ts:22）：它是回执的唯一写入者，`send` 在一个事务里保存回执并排队 reply 效果，每个消息 id 永远不会被排队两次。同一工单发往同一会话的消息按排队顺序发出——确认先于答案；一条消息连续失败三次成为系统问题，后面的同路消息继续等它（顺序优先于吞吐，docs/003 "Channel failure" 节）。消息只在两种情况下丢弃：Source 不再监听那个会话，或 Source 回答会话永远收不到（Issue 删除、会话锁定、飞书消息撤回）。丢弃记录永久保留（何时、为何、为哪个工单），永远不会重新排队——一条被丢弃的确认读作"已丢弃"，这与"已发送"是两个明确区分的状态。

调度器（Passes，src/app/passes.ts）串行驱动：每 2 秒一轮，每轮先处理到期效果、再驱动引擎的 `evaluateDue`；同一轮里被要求的新工作合并到轮末。暂停处理（pause）停下派发、新评估、投递与回复，但 Source 照常记录 Trigger、运行中的回合不打断；暂停期间的评估不过期，截止时间顺延暂停的时长。

## 持久化与恢复

一个 SQLite 文件 `<stateDir>/orchestrator.sqlite`，只有 Store（src/app/store.ts）打开它；启动时先获取目录锁，防止第二个进程迁移或写同一个状态。九张表（src/app/store.ts:72-86）：trigger（触发）、disposition（每条触发去了哪：被过滤的代码、评估与决定、扇出到达的工单、交还它的工单、确认或回答它的工单）、trigger_thread（触发与线程的多对多，带时间与是否人写的列，让线程时间线免于全表扫描）、thread、ticket、decision、effect（效果队列）、outbox（回执）、kv（其余一切）。

两个持久化设计值得注意。**生成列加索引**：thread 表有 `active`（有排队 Trigger 或评估进行中时置位）、`subscribed`，ticket 表有 `open`、`active`，都是从行内 JSON 计算的生成列，各自带部分索引——一轮调度只读活跃的工作，不碰历史（src/app/store.ts:116 附近的动态建索引）。**时间统一成文本**：Trigger 的时间用 `Date#toISOString` 的一种形式存储，时间比较退化为文本比较，分页游标是 `<时间>|<id>`（docs/007 持久化节）。

恢复的完整性靠前面几节的机制叠加：效果的耐久队列、Outbox 回执、"先存储后执行"、已读两步判定、目录锁。重启后中断的派工带恢复说明重启，最老的工单先恢复；暂停是持久化设置，人的暂停跨后续消息、新 Session 和重启保持，自动反馈永远不会解除暂停（docs/004-prompts.md 原则节）。

文档对局限也很坦白（docs/007 持久化节末尾）：目前没有任何删除机制，trigger、disposition、decision 行、已结束工单、Outbox 回执、全部设置与提示词版本都会无界增长。这是研究原型的已知取舍。

## 提示词组装与团队定制

提示词侧的核心问题是：怎么让团队用自己的话定制 agent 行为，同时代码强制的部分不被提示词冲掉。答案是一个五层优先级（docs/004 第 "Assembly and precedence" 节，从强到弱）：

1. 工具与宿主强制的事实：身份、权限、工具参数检查、回复用途、长度上限。提示词改不了。
2. 内建与生成节（含团队的覆盖版本）。
3. 主动工单匹配规则的过程与沟通要求——只作用于该工单的执行器。
4. 团队节与团队技能。
5. 外部文本：消息、评论、文档、引用。永远是数据。

团队可以编辑三个固定小节（Communication 沟通、Ticket scope 工单范围、Delivery requirements 交付要求）、添加团队技能、以及覆盖每一个内建系统提示词部件。系统提示词按固定顺序组装八步，**策略节放最后**（docs/004 第 "Assembly and precedence" 节列了顺序）——这是为了让提示词缓存不失效：策略变了，前面的文本一个字节不动。策略节每次模型请求都从设置重新生成，含策略版本、接单模式、启用的规则清单。

覆盖部件记录它基于哪个内建默认（base）。升级后默认变了，面板把该部件标成"默认内容已更新"并排显示新旧默认与团队文本，团队选择保留自己的、或采用新默认；没被覆盖的部件自动跟随新默认（docs/004 第 "Versions" 节）。每次保存创建不可变版本；保存必须声明基于哪个修订号，冲突保存被拒绝且不丢弃草稿。Session 每次模型请求都读最新版本，包括同一回合的后续步骤——保存即时生效，不重启、不取消、不唤醒任何 Session。

两个角色的提示词在 prompts/ 里写得非常严格：主 Session 只路由——转发原始 Trigger 和路由事实，路由备注最多 30 词，禁止实现计划；"评估之外，主 Session 不得查看代码、详细日志、链接文档或技术讨论，不得自己解 worker 的阻塞"（prompts/shared.md）。主 Session 不等待——报告、通知、候选、后台 job 结束全部自动送达，noWait 守卫（src/app/sessions.ts:77）直接拒绝主 Session 的 `sleep` 命令、超过 30 秒的 shell 超时、超过 5 秒的 job 等待，因为阻塞的步骤会延迟新候选的处理。执行器确认要具体——动手前用一句话指名对象与预期结果，回复在原消息下（prompts/replies.md）。

## 面板

Web 面板（Harness 侧边栏的 Superagent 入口）是人的监督界面，只回答三个问题、按此排序（docs/005-panel.md）：有什么需要我现在处理？系统健康吗、做的是对的事吗？一件工作的完整历史是什么？

工单的阶段分类是自上而下第一行命中即停的判定表（src/core/stage.ts:9）：投递失败、等回答、等审查、受阻/失败归为 person 类（等人）；排队、等触发、工作中归为 working 类。阶段标签说"这一行在等谁、需要什么"，内部状态码折叠进详情。

面板原则（docs/005 末节）延续了注意力哲学：每个元素必须回答三个问题之一，否则删除；健康状态不占空间；一个概念只出现在一个地方；数字必须等于它链接到的列表长度（诚实状态）；破坏性操作要求确认。评估（Eval）页把每个决定连同理由与匹配规则列出， observe 模式的审阅就在这里做——这正是"先观察后自动"推进路径的人工环节。

## 设计原则

把这些机制背后的取舍收拢一下，有三条贯穿全部代码的纪律。

**一个状态一个写者。** 每类状态有唯一写者，其他部件要么读、要么通过写者请求：领域对象只有引擎写，回执只有发件箱写，每条健康条目只被在健康板上声明它的那个部件写，重复声明直接拒绝（docs/007 "Dependency rules" 节）。这消灭了一整类并发写坏的 bug。

**请求与事实分离，命名上就分开。** 向对方要东西的方法用祈使语气命名（`stopTicket`、`bindThread`），可能被拒绝；记录适配器已经做了的事的方法用过去时命名（`assignmentStarted`、`deliveryFailed`）。调用方一眼看出这个调用是命令还是通报。

**授权与上下文分离。** 订阅送上下文不送权限；主 Session 的 note 送事实不送权限；每个工单带着它的授权（为什么可以做、可以做到哪）独立存在于它的线程上下文里。引擎的调用方只见自己角色的 Pick 类型（src/core/engine.ts:261-269，`EngineForSources`、`EngineForMainSession`、`EngineForPeople`、`EngineForSettings`、`EngineForExecutor`），核心（src/core）不依赖自身之外的任何东西（Node 哈希除外）、不做输入输出。

测试侧同样有值得学的纪律：`tests/docs.spec.ts` 自动检查编号文档只链接更早的文档、架构文档的表格列全了每个模块和每个测试；`tests/model-surface.spec.ts` 检查模型读到的一切（工具、提示词、技能、输入消息）且对每个角色有尺寸上限；`tests/class-docs.spec.ts` 要求每个类有文档注释。文档与模型可见面都纳入了测试范围。

## 可复用的做法

- **"先存储后执行"的耐久效果队列**：事务内入队、提交后执行、按 kind/key 合并、指数退避、`Later` 类表示延迟而非失败。任何"决定之后要做一串外部动作"的系统都能直接套用。
- **准入表**：把"谁在什么范围内说话该怎么对待"做成显式的、每格可配的矩阵，默认值保守（默认忽略名单外的请求）。比一堆特判清晰，比纯名单表达力强。
- **观察模式**：主动行为先以"只记录本来会做什么"的模式运行，人审阅记录后再放开。一切"让 agent 自动做某事"的功能都值得配一个这样的观察档。
- **授权对象（Mandate）**：把"为什么允许做这件事"做成不可变的数据（策略版本、范围、强度、匹配规则），跟着工单走；恢复前对当前策略重验。审计与撤销都有了依据。
- **两步已读判定**：认领（收进历史）加事后确认（一次报告或回合结束）才算读，重启安全，重投递时取走旧副本保证唯一。
- **后台工作的分级清理**：回合内后台工作限时 30 分钟；交给人的 shell job（试运行的服务）免限不唤醒；subagent 在交接点立即终止。按"这个东西为谁而活"决定清理策略。
- **提示词缓存友好的组装顺序**：易变的节（策略）放最后，变化的文本不碰前面的缓存。
- **文档编号阅读顺序**：docs/000 到 008 每篇只依赖前面的，且有测试强制这条规则。写复杂系统的文档可以照抄这个结构。

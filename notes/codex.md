# Codex

| 源仓库 | [openai/codex](https://github.com/openai/codex) |
|---|---|
| 协议 | Apache-2.0 |
| 主语言 | Rust |
| 笔记基准 | commit `431185b78b`（2026-10-20） |

Codex 是 OpenAI 开源的编码 agent（agent 指能自主多步行动、调用工具完成任务的 AI 程序，区别于只会一问一答的聊天机器人），主体用 Rust 编写，跑在用户自己的电脑上。你在终端里敲 `codex` 就能进入它的交互界面，让它读代码、改文件、跑命令、跑测试。代码规模不小：`codex-rs/` 目录下有一百多个 crate（Rust 的模块/零件单位），四千六百多个 Rust 源文件，近两百万行代码（含测试）。它解决的核心问题是"如何让模型安全地在本地真正干编码活"，而不是停在给你贴代码片段。在同类工具（Claude Code、opencode、Gemini CLI 这类终端编码 agent）里，Codex 的位置比较特殊：它是官方出品、生产级强度的参考实现，一套 Rust 核心同时支撑终端界面、IDE 插件、桌面应用和云上服务，安全机制和上下文管理都做得非常系统。

这份文档基于 2026-09-21 前后的仓库状态写成，目的是让没接触过这个项目的人能从头理解它"是什么、怎么转、为什么这样设计"。

## 它解决什么问题

把一个语言模型变成能干活的编程助手，中间隔着四个实际问题，Codex 的全部工程都是围绕它们展开的。

**第一，模型只会输出文字，不会动手。** 模型说"我帮你改一下 `main.rs`"，它自己改不了文件，也跑不了测试。需要一个程序替它执行：它说"读这个文件"，程序读了把内容喂回去；它说"跑这个命令"，程序跑了把输出喂回去。这个"模型出主意、程序跑腿、结果再喂回去"的循环就是 agent loop（智能体循环），是所有此类工具的心脏。

**第二，动手就有风险。** AI 执行的命令如果没有任何限制，一条 `rm -rf` 就可能闯祸。Codex 用沙箱（sandbox，把程序关进一个隔离房间，房间里能碰什么、能连什么网络都受系统级限制）加审批（approval，敏感动作先问用户）来解决。这是 Codex 投入工程量最大的部分之一。

**第三，模型的"工作记忆"有限。** 模型一次能"看到"的内容总量有上限，这个上限叫上下文窗口（context window），按 token（模型处理文本的最小单位，一个英文单词大约一两个 token）计费计量。编码任务动辄读几十个文件，对话一长窗口就满了。Codex 有一整套上下文管理：往窗口里放什么、放多大、什么时候把旧内容压缩成摘要。

**第四，用户出现在不同的地方。** 有人用终端，有人用 VS Code，有人用桌面应用。如果每端各写一套核心逻辑，成本和不一致都会失控。Codex 把核心做成一个独立的服务层（app-server），所有前端通过统一的协议跟它对话，一套逻辑处处复用。

一句话概括：Codex 是"模型的大脑"和"你的电脑"之间的那层完整的工程：让模型能动手、动手有围栏、干长活不失忆、在哪个界面都能用。

## 整体架构

整个仓库是一个 Rust workspace（把多个 crate 组成一个工程统一编译的机制），按职责分层。先看分层，再看关键 crate。

### 分层结构

从下往上大致是四层：

1. **协议层（protocol）**：定义前端和核心之间说什么"话"。两个核心类型：`Op`（用户/前端发给核心的请求，比如"开始一轮对话""打断当前任务""批准这条命令"）和 `Event`（核心发给前端的通知，比如"模型输出了一个字""命令执行完了"）。这层不干活，只定义数据形状，所有层共享。
2. **核心层（core 及其卫星 crate）**：真正干活的逻辑。agent 循环、工具调度、沙箱决策、上下文压缩、会话记录、审批把关都在这里。核心又拆出几十个专门的 crate，比如管压缩的 `compact` 系列、管会话记录的 `rollout`、管功能开关的 `features`、管 git 工作树的 `worktree`。
3. **服务层（app-server）**：把核心包装成一个 JSON-RPC 服务（JSON-RPC 是一种"用 JSON 格式一来一回调函数"的通信约定）。前端不直接调用核心的 Rust 函数，而是向 app-server 发请求、收事件。传输通道支持三种：stdio（标准输入输出管道）、Unix domain socket（同一台机器上进程间的本地通信插座，下文简称 UDS）、WebSocket（网络上保持长开的双向通道）。
4. **前端层**：`tui` 是终端交互界面；`exec` 是非交互模式（一条命令跑完任务，适合脚本和 CI）；IDE 插件和桌面应用是仓库外的官方前端，同样走 app-server 协议。`codex-cli` 目录是 npm 上的启动器，`sdk/` 里是给 JS 应用嵌入 Codex 用的 TypeScript SDK。

这个"一套核心、多个前端"的拆分是 Codex 架构上最重要的决定。代价是要维护一个严谨的协议（仓库里专门有工具从 Rust 类型自动生成 TypeScript 类型定义，保证两端不脱节）；好处是 IDE 插件、桌面端、终端的行为和功能完全同源。

### 依赖方向上的纪律

`AGENTS.md`（这个仓库给 AI 贡献者的开发守则，他们自己用 Codex 开发 Codex）里有一条很醒目的规矩："抵制往 codex-core 里加代码"。理由写在注释里：core 已经是最大的 crate，什么东西都往里放会越来越臃肿；新功能应该先找现有的合适 crate，实在没有就新开一个。这不是洁癖，是防止核心腐烂的手段：核心越小、越稳定，上层越敢改。

## 核心机制

下面按子系统逐个讲。每个机制都按"是什么、怎么实现、为什么这样设计"来说。

### Agent 循环：thread、turn、step

**是什么。** 三个层级概念撑起整个运行模型。thread（线程）是一次完整的协作会话，对应一份可恢复的记录；turn（回合）是用户说一句话到模型彻底处理完的过程；turn 内部每次"向模型发起采样请求、拿回结果"是一次 step（步）。用户的一次提问，通常经历多个 step。

**怎么实现。** 入口在 `core/src/session/turn.rs` 的 `run_turn` 函数（三千多行，是该仓库最大的文件之一）。主干是一个循环：

1. 前端通过 `Op::TurnInput` 提交用户输入，核心组装上下文，发起第一次采样请求。
2. 请求发往模型服务端（走 OpenAI 的 Responses API，由 `codex-api` crate 处理通信细节），返回一个事件流。流里可能出现：文字增量（`OutputTextDelta`，模型一个字一个字往外蹦）、推理摘要增量（模型"思考过程"的解说）、完整的工具调用（`OutputItemDone`）、回合结束标记（`Completed`）。
3. 如果模型请求了工具调用，核心执行工具，把输出追加进对话历史，发起下一次采样请求，回到第 2 步。
4. 如果模型只输出了一条给用户看的回复，说明活干完了，这一 turn 结束。

有两个实现细节值得展开。其一，工具调用可以并行：模型一次返回多个工具调用时，核心用 `FuturesOrdered`（一种保持完成顺序的并发容器）同时执行互不依赖的调用，全部完成后再一起喂回模型。其二，回合可以被"插话"（steer，直译"打方向"）：用户不必等模型跑完当前回合，可以中途追加输入，核心会把新输入排队或注入当前回合。这个能力早年在功能开关后面逐步放开，因为它改变的是"一问一答"的基本节奏。插话最近又进一步：新增 `instant_interrupt` 开关（默认关闭）后，新用户输入到达时可以**抢占**还在进行的模型响应——打断请求发起、响应流、连重试的退避等待也一并打断，然后把排队的输入接上继续回合；被抢占的请求重置连接和续写状态，下一请求带完整历史重发。配套地，code-mode（把工具调用折叠成代码执行的执行方式）里长时间运行的 `exec`/`wait` 调用会收到一个共享的抢占信号，**提前让出**：注意不是杀掉——正在跑的单元格继续跑，只是不再霸着回合，后续的 `wait` 调用还能照常收集它们的结果。插话解决"话能递进去"，抢占解决"话能马上被听进去"，代价是打断的响应作废重来——这个代价曾让团队把开关默认关着，2026-10-07 起 `instant_interrupt` 改为默认启用，code-mode 的中断也同日默认开，最初的保守默认被换了掉。

**为什么这样设计。** 把循环拆成 turn/step 两级，是为了让"可打断、可恢复、可计费"都有清晰的边界：打断发生在 turn 级（保留已完成的 step），上下文压缩发生在 step 之间（保证发给模型的每次请求都是完整一致的快照），限额统计也按 turn 结算。整个循环用 CancellationToken（Rust 里一个可以被多方触发的"取消信号"对象）贯穿，用户按 Esc 打断时，正在进行的请求和工具执行都能干净地停下来。

### 工具系统：内置工具与统一路由

**是什么。** 工具是模型能调用的具体动作，比如"执行这条 shell 命令"。Codex 的工具分三类：内置工具（核心自带）、MCP 工具（外部服务器提供）、动态工具（运行时注册）。

**怎么实现。** 每个工具在发给模型前要有一份规格（`ToolSpec`）：名字、参数的 JSON Schema（描述参数长什么样的规范）。规格分几种形态：普通函数式（Function）、自由格式（Freeform，比如 apply_patch 用自己的补丁文本格式而不是 JSON 参数）、命名空间式（Namespace，把 MCP 服务器的多个工具打包在一个前缀下）、工具搜索（ToolSearch，后述）。`core/src/tools/spec_plan.rs` 负责根据配置、模型能力和已启用的 MCP 服务，决定这一回合到底把哪些工具的规格放进请求。

内置工具中值得单独说的：

- `shell` / `unified_exec`：执行命令。统一执行器还支持长驻 shell（一次会话里保持一个 shell 进程，保留工作目录和环境变量）和 TTY 模式（模拟真实终端，能跑 vim 这类交互程序）。
- `apply_patch`：改代码不走"整文件覆写"，而是用一套自定义的补丁格式，明确写出增删改哪些行。补丁应用前后会算一遍 diff（文件差异），作为回合差异报告给用户。
- `update_plan`：让模型维护一张结构化的任务清单（每项是"待办/进行中/完成"），用户能实时看到它打算怎么干。
- `web_search`、`view_image`、`request_user_input`（向用户提问）、`sleep`、`current_time` 等，各管一摊小事。
- `tool_search`：当接入了大量 MCP 工具时，把所有工具规格塞进上下文会占掉大量空间。开了这个工具后，大部分工具规格不再随请求发送，模型先按需搜索"有没有能干 X 的工具"，再把找到的工具的详细规格临时加载进来。

工具的执行统一走 `ToolRouter`（路由器）：按名字找到对应的处理器，套上前置检查（审批判断、hook 回调）、超时控制、输出截断、事件上报，执行完再把输出包成统一格式。hook（钩子）是用户配置的回调，可以在工具执行前后、回合开始结束时插入自定义逻辑。

**执行层最近有一加一减。** 加法在并行度：不主动声明可并行的工具，执行时默认拿一把独占的调度锁，两个互不相干的读取也得排队。2026-10 上旬起，一批明确只读的工具改为可并行执行——技能与记忆的列出和读取、文件读取与搜索、历史搜索、插件与 agent 列表、当前时间、剩余上下文、`get_goal` 等；目标的创建和更新仍然串行。配套测试用屏障（barrier，一种让两个操作互相等齐、从而证明它们真的同时在跑的同步手段）验证并行确实发生。减法是移除：存在已久的一套补丁版 zsh 执行后端被整体拆除（连同配套的进程升级辅助运行时和包装器 crate），执行统一回标准 shell 执行器，旧配置开关被忽略并给出迁移提示。

另有一条实验性路线叫 code mode：让模型不再逐个"点菜式"调用工具，而是写一小段程序把多个工具调用编排起来执行，配套了独立的宿主运行时和预热机制。它还在功能开关的实验阶段，这里只记一笔，说明工具层在为"任务更复杂、调用更密集"的场景探路。

**为什么这样设计。** 工具规格是上下文的大户，"按需加载 + 命名空间合并 + tool_search"三板斧都是在同一个目标下：让接入一百个工具和接入三个工具的上下文开销差距尽量小。而统一的路由层让"审批、hook、遥测"这些横切关注点只写一遍。

**工具目录最近开始走向增量。** 2026-10-02/03 的提交给 Responses Lite 路径加了 `incremental_tools`（功能开关，默认关，尚在开发中）：工具定义改由 world state 和会话历史跟踪，初始目录只发一次，之后每个请求只追加新增或变更的定义，更早的请求历史原样保留；被移除的工具和命名空间指令的变化以 developer 通知发出；普通请求与远程压缩都改用历史提供的定义，目录哈希跨 JSON 键序保持稳定（同样的定义无论键怎么排都算同一个）。配套还有两处稳定化：Code Mode 的 `exec` 描述不再随目录变化而变（工具发现指导总是包含，哪怕当前没有延后工具），MCP 工具结果在分页历史里按上限截断并计入 JSON 序列化的开销。动机和别家是一致的：工具清单每个请求重发一遍，前缀缓存就永远断在清单那一处；清单稳定、变更增量，缓存才可能贯穿整个会话。这套路子随后还在打磨：模型目录可以按模型覆盖增量通知的行为；一批命名空间更新合并成一条 developer 通知发出，不再逐条刷屏；增量更新也开始记录自己的指标。2026-10-20 起 `incremental_tools` 转为稳定并默认启用（提交 c953dacb），Responses Lite 会话不再需要显式打开开关，工具目录的变更自动走增量追加。

**技能目录在走向体系化（2026-10-20）。** 一个技能可能同时来自云端目录和多个执行器环境（executor，实际代它跑文件的环境），围绕这个事实补了三块。其一，步骤工具的构建时序变了：技能工具此前依赖 World State 渲染来初始化目录，渲染没完成时会报"skill catalog is not ready for this step"；现在 `ToolContributor` 多出一个异步的 `prepare_for_step` 钩子，构建工具前先等所有贡献者就绪，不可变的技能目录、别名、插件策略、配置在每个步骤开始前准备好（提交 9b865ab3）。其二，安装位置可查了：discovery V2 下新增 `skills.installations`，列出某技能在哪些环境已启用（支持按来源过滤和分页，不读技能内容），`skills.read` 也能通过 `source` 参数指定从云端还是某个执行器环境读取；响应里带 `installations_truncated` 标记，被响应上限略去的安装位置可以分页取回（提交 03478b4b）。其三，别名稳定化：目录变化时，别名分配在活跃线程内保持有界、只追加（append-only，只增不改），每个步骤保留自己的别名快照，目录条目引用哪个根路径在整轮会话里不会漂移（提交 03478b4b）。

### 沙箱与审批：围栏和放行

这是 Codex 最厚实的子系统，分两半讲：沙箱管"物理上做不了"，审批管"做之前先问人"。

**沙箱策略。** 用户可选的沙箱强度是一个枚举（`SandboxPolicy`）：

- `read-only`：整个磁盘只读，默认断网。
- `workspace-write`：磁盘整体只读，但当前工作目录（workspace）和临时目录可写，可选开放网络。这是日常使用的主力档位。
- `external-sandbox`：声明"我已经在一个外部沙箱里了"（比如整个容器都是隔离的），Codex 不再自己加沙箱。
- `danger-full-access`：完全放开。

策略里有个精细设计：`workspace-write` 的可写根目录下，`.git`、`.codex` 这些路径仍然保持只读（代码里的说法是 read-only subpaths，只读子路径）。原因很直接：`.git/hooks` 里的脚本会在 git 操作时自动执行，如果 AI 能改它，就等于给了它一条绕过沙箱执行任意代码的暗道。可写目录里藏着的提权通道，被逐个堵死了。这份保护名单最近又添了 `.aws`（工作区根和额外的可写根都覆盖）：AWS 的配置文件可以指定凭据助手（credential helper，需要凭据时执行的外部程序），应用会真的去执行它——能写 `.aws` 就可能间接左右"执行什么程序"。用户显式写的放行规则仍然优先于默认保护。

**平台实现。** 同一套策略，三个平台三套实现（`SandboxType` 枚举）：macOS 用 Seatbelt（苹果系统自带的沙箱机制，通过 `/usr/bin/sandbox-exec` 命令加一份策略文件来启动）；Linux 用 Landlock（内核提供的文件访问控制）加 seccomp（内核提供的系统调用过滤），配合 `no_new_privs` 标志（禁止子进程提权）；Windows 用受限令牌或 MXC 沙箱。网络方向还有独立的 `network-proxy`（网络代理）：断网不是简单拔线，而是可选地"只允许访问这些域名"，由代理层执行白名单。有个细节能看出工程的偏执程度：调用 Seatbelt 时写死了 `/usr/bin/sandbox-exec` 这个绝对路径，而不是从 PATH 里找。注释解释了原因：万一有人往 PATH 里塞了一个恶意的同名程序，写死路径就让它无从下手。

Windows 这条线最近还在细化。一是本地执行可以**选择用哪种沙箱后端**：新增了一个默认关闭的偏好开关（`features.prefer_mxc`），开启后只要本机支持、网络设置允许，就用 MXC 沙箱做本地执行；显式指定 `windows.sandbox = "mxc"` 依然严格生效，命令失败也不会悄悄回退到别的后端。二是**共享文件系统能力不能顺手把"别人会话"的对象也放开**：Windows 沙箱的默认访问控制列表（DACL，声明"谁能碰这个对象"的权限表）只把完全访问权授予当前登录会话（logon session）自己的身份，不再授予"所有人"和各类能力标记——防止共享账户下，另一个登录会话顺藤摸瓜碰到本会话的进程、线程和进程间通信对象。

跟执行服务相关的还有一个跨传输的大小边界：exec-server（命令执行服务）收到的入站请求，无论走哪种传输（标准管道、WebSocket、中继等），编码后的消息都限制在 8 KiB 以内；进程输出、退出、关闭、HTTP 请求体这类"结果型"通知放宽到 2 MiB；携带链路追踪信息的请求头 `tracestate` 超过 512 字节就直接丢弃（保留主追踪标识）。给"进来的请求"和"回来的结果"划大小上限，是防止恶意或出错的对端把执行服务内存撑爆的第一道闸。

**沙箱的防线自己也会被写坏，于是有了对防线自己的检查。** 2026-10-07 的六连提交给 exec-server 加了沙箱完整性检查（sandbox integrity）：沙箱能起作用，依赖一批"包含依赖文件"（containment dependencies，构成防线的文件本身，比如沙箱执行器、策略配置）不被篡改；但如果文件系统策略恰好允许写这些文件所在的路径，防线就有被从内部架空的隐患。检查的问法很直接：按当前生效的策略，防线上每个关键文件是不是还写不进去？实现上按平台各配一个后端（macOS 用 Seatbelt，macOS 的 Seatbelt 把 deny 通配当原生模式处理、不需要额外扫描快照；Linux 用 bubblewrap；Windows 做 MXC 准备），目标、写根、只读豁免全部先解析符号链接再比对，deny 通配按解析后的真实内容匹配；macOS 后端把 Codex 自己的可执行文件和系统的 sandbox-exec 都列进关键依赖清单——防线的定义从"配置"扩大到了"执行沙箱的那几个程序本身"。检查跑在阻塞线程上、等待限五秒，结果只作观测（不影响命令执行），指标记录结果与耗时、标签里不含任何文件系统路径。

**审批策略。** 沙箱挡住的是"没权限的动作"，但有些动作合法又敏感（比如要在沙箱外跑一条命令），这时候轮到审批。`AskForApproval` 枚举定义了四档：`untrusted`（除明确允许的命令外都问）、`on-request`（默认档，模型自己判断什么时候该问）、`granular`（细粒度开关，命令审批、规则触发、MCP 询问等各管各的）、`never`（从不问，被挡就失败）。审批的判断逻辑在 `core/src/safety.rs`：每个动作先过一遍安全评估，结论有三种：自动批准、问用户、直接拒绝（比如只读沙箱下要写文件，问了也没用，直接拒绝并说明原因）。

实际执行时还有一条"升级"路径：命令先在沙箱里跑，如果因为权限不够失败了，可以生成一个"解除沙箱重跑"的审批请求，用户批准后才在沙箱外执行。用户看到的批准对话框会带具体的命令内容和请求原因，批准是针对这一次动作的，不是一次性放权。

**权限授予的时效与归属**也在这轮收紧了。此前"查权限"问的是当前活跃的回合，这带来一个隐蔽的坑：后台 code-mode 单元（一次回合里派生的并行执行单元）可以在新回合开始后继续跑，按"当前回合"查授权，它要么丢掉自己已获批的访问、要么误用别的回合的权限。现在权限授予明确绑定到**发起它的那个回合**：回合范围的授权与严格评审状态随回合上下文（TurnContext）保存，由捕获的步骤和后台单元持有；权限请求的答复记在发起请求的回合名下，哪怕答复到达时已经切换了回合；会话范围的授权照常跨回合共享，回合范围的彼此隔离。工具执行、补丁、MCP 调用、文件上传、终端输入，一律使用发起回合的权限与评审要求。配套地，扩展与技能读取的文件系统访问也收紧到**回调自己的权限**：扩展工具和回合输入贡献者拿到的是借出的环境访问对象（会话与发起回合的授权已经应用在内），技能读取必须用回调所在环境提供的文件系统访问，技能分页快照绑定到"源文件系统加回调权限"的组合键上——缓存的页面不再脱离产生它的权限而存在。权限体系还多出一个按用途扩容的方向：`/daybreak` 开关为网络安全工作开放更广的访问（cyber 访问程序从所连服务器的模型目录里选择），启用需要登录 ChatGPT 账户、OpenAI 提供方和确认模型支持，选择持久化在线程元数据里、恢复会话时还原，侧对话一律不启用。这轮默认值动了两处（2026-10 中旬）：`cli_daybreak` 转为稳定并默认启用（背景回合要做资格校验，API-key 账户在 cyber 访问程序开启时同样纳入），Cyber 访问程序对 API-key 会话默认开放。线程自有权限的恢复也补上了：冷恢复（进程重启后不带内存现场重新打开会话）不再让已保存的未命名权限配置被当前配置默认值顶掉——从该线程自己的设置快照还原合资格的权限配置，命名权限以自有快照为准，工作区权限按恢复后的工作区根重新应用。

### 上下文窗口管理与压缩

**是什么。** 上下文窗口是模型一次能"看到"的全部内容（系统指令、对话历史、工具输出的总和）的上限。任务一长，历史记录就会把窗口撑满，必须管理。

**怎么实现。** 分三件事：计量、注入、压缩。

计量在 `core/src/session/context_window.rs`：每个回合开始前算清楚当前用了多少 token、距离上限还有多少。上限有两个来源：模型的完整窗口乘以一个百分比（给输出留余量），以及配置项 `model_auto_compact_token_limit` 指定的自动压缩线（配了就优先用它）。

注入讲究纪律。`AGENTS.md` 里有一节专门审查"所有会被模型看见的内容"，规则包括：历史只能增量追加、不许重写；每一条注入的内容必须有大小上限；单条不得超过 1 万 token；超过 1 千 token 的新注入项要标记为最高优先级人工评审。每种注入内容（环境信息、当前时间提醒、用户指令、审批结果等）都是一个独立的类型，实现统一的 trait（Rust 的接口机制），在 `core/src/context/` 下有六十多个这样的类型。这套纪律的直接动机是提示词缓存（prompt caching，服务端对请求前缀的缓存，前缀不变就不重复计费、不重复计算）：历史被频繁改写，缓存就全作废。

压缩（compaction）在窗口逼近上限时触发，把旧历史浓缩成一份摘要，替换掉原始记录。实现上有三种时机：回合开始前的预压缩（`run_pre_sampling_compact`，发现这轮输入会把窗口顶爆就先压）、回合中途的压缩（压完必须把初始上下文重新注入，而且位置有讲究：要放在最后一条真实用户消息之前，因为模型受的训练是"压缩摘要是历史里的最后一项"）、以及用户手动敲 `/compact`。压缩本身也是一次模型调用：用一份固定的摘要提示词（`SUMMARIZATION_PROMPT`）让模型把旧对话写成摘要，单次压缩的输入上限是 2 万 token，超长部分先做分段截断。新一点的路径还支持服务端压缩（remote compaction v2，压缩这件事由模型服务端完成，客户端只拿结果），按模型能力自动选择走哪条。

**为什么这样设计。** 压缩是有损的，越晚压信息丢得越多，但压得太频繁又浪费请求和缓存。把触发点做成可配置的阈值，默认放在模型窗口的某个安全百分比上，是在"信息保真"和"请求成本"之间取的平衡。压缩完成后给替换历史编号（window number），保证后续的记录和恢复能对上账。

压缩的例外也出现了：2026-10 上旬起，客户端可以在 `turn/start` 时给某个工具输出打上 `retain` 标注（默认不打，行为照旧），请求核心把这个输出**保留在线程的模型历史里**；随后补上"带客户端标注的输出跨压缩保留"。模型压归压，客户明确说"这段要一直在"的，压缩不碰——保留什么由使用方逐条决定，而不是给压缩整体加开关。

**压缩还在往异步、服务端的方向走**（2026-10 中旬，均在功能开关后面）。新的 `async_compaction` 特性（默认关闭）允许压缩在回合之外异步进行，阈值由 `model_async_compact_threshold_percent` 配置（默认 65，即上下文用到 65% 就算到线；只配阈值不等于开启）。另一条是"推测性远程 V2 压缩"的地基：为后台压缩请求捕获历史、提示词元数据、路由状态、认证归属和上下文窗口身份，后台请求走 HTTP 且保持与前台相同的路由，会话内存里只留最新的候选结果；按历史版本、模型、压缩哈希和认证归属去重，会话关闭时取消并排空后台任务（已完成的用量统计保留）。提交里明说：后台启动的钩子还没接进回合循环——先立地基、后通水管。配套改了一处 budget 的算法：加密压缩载荷里可能带采样令牌的重放缓存，体积能涨到三倍，估算改为每 12 字节密文按 1 个 token 计，免得把装得下的检查点误判成超限。

编号在恢复场景里真的派上用场了：恢复一个压缩过的会话时，模型上下文的扫描会在**最新的压缩边界**停下——即从最新那次带替换历史（replacement_history）和窗口编号（window_number）的压缩开始，连同它之后的新记录一起恢复，**不会去翻压缩之前那些更老的回合上下文，也不会把压缩前的旧状态翻出来**。只有最新压缩缺了这两个字段（数据不完整）时才退回全量重放。这保证了"恢复"回到的是压缩发生后的世界，而不是压缩前的旧世界。

一处提示词层面的收拾（2026-10-20）：上下文成功压缩之后，界面不再发出"长线程与反复压缩可能影响准确性"的警告（提交 49df716b）——警告的适用前提（历史还是长的、还没压缩）已经不成立，继续显示只会让人对压缩后的状态产生多余的怀疑。

### 会话持久化：rollout

**是什么。** rollout 是 Codex 给会话记录起的内部名字：每一次对话的完整事件序列，按行追加写进 JSONL 文件（每行一个 JSON 对象的文本格式），存在 `$CODEX_HOME/sessions/` 目录下（`CODEX_HOME` 默认是 `~/.codex`）。

**怎么实现。** 核心里每发生一件要留档的事（用户输入、模型输出、工具调用、压缩事件），`rollout` crate 就往当天的文件里追加一行。文件头部有会话元数据（ID、工作目录、模型、指令来源）。读取方向做了不少优化：反向扫描器（从文件尾部往前找）、SQLite 状态库（`state_db`，存索引和派生状态）、可选的压缩存储（compression，旧会话文件用压缩格式归档，由功能开关控制）。恢复会话（`codex resume`）就是把 rollout 文件重放一遍，重建出内存里的对话历史；分叉（fork）则是从某个点复制出一份新会话。

**为什么这样设计。** 追加写（append-only）是最抗损坏的持久化形式：进程崩了最多丢最后半行，之前的内容都完好。而"记录的是事件而不是状态"意味着任何时候都能从零重放出当前状态，调试时也能精确回答"当时到底发生了什么"。

**恢复与并发正确性是这条线最近的工程主线。** 恢复会话的核心动作是把 rollout 文件重放成内存历史，这里藏着几道容易踩的坑，最近的提交逐个补上。

第一道是**快照与写入的竞态**（race，两个执行方因为时序不同而互相踩脚的错误）。恢复线程时，如果预加载的历史快照没有变化，直接复用能省一次重读，但"没变"必须在**拿到写者所有权之后**验证——从快照加载完到接管写入之间有时间窗，别的进程可能趁这个窗写入了新内容。存储历史现在带一个不序列化的版本号（只在恢复链路里传递），拿到写权后核对：一致就复用共享快照，缺了或变了就重载。配套的另一半是：就算快照真的旧了也不整体重读——恢复接口改为返回权威重放历史，把接管写权之前已提交的写入补进来，只补差额。

第二道是**数据库悄悄损坏**。SQLite 文件可能打开成功但内容已经坏了，此前的启动流程查不出来。现在打开可写数据库时会跑一遍快速完整性检查（PRAGMA quick_check，SQLite 自带的"体检"命令，带 100 毫秒的扫描时间上限，检查结果按文件身份共享、重复打开不再重查）。确认损坏的处理分两档：有恢复策略的运行时数据库先备份原文件（损坏现场保留，供事后分析）再重建；线程历史这类没有自动恢复策略的库只报告、不重建。检查的判定很克制：被中断或被锁住的检查记作"未完成"，不算"确认损坏"——宁可报不确定，不下错结论。判定方式本身也有讲究：不再靠匹配错误消息文本（换个措辞就失灵），而是按 SQLite 结果码（包括扩展结果码）分类，识别建立在数据库协议的保证上而不是措辞上。最后通过应用服务器的警告把恢复能力说清楚：已保存的对话能恢复线程列表和历史，只存在数据库里的部分元数据可能拿不回来。

第三道是**阻塞 I/O 不进异步运行时**。Rust 的异步运行时（tokio）把大量任务复用在少数线程上，哪个任务在异步函数里做了慢速磁盘读写，排在后面的所有任务都得干等。会话索引的追加、rollout 文件的打开/定位/读取/记录投影、压缩文件的片段搜索、目录枚举，这批操作全部挪进了 spawn_blocking（tokio 提供的"慢活专用线程池"）：压缩片段搜索从"每读一行调度一个阻塞任务"改成整个扫描在一个线程上跑完、命中第一个匹配就停；目录扫描在条目之间检查取消标志，调用方放弃等待就立刻收工；会话索引的锁在派发前获取、锁的持有权带进工作线程——即使排队中的更新被取消，已排队和进行中的写入依然保持串行，顺序不乱。

### MCP 与外部工具接入

**是什么。** MCP（Model Context Protocol，模型上下文协议）是一个开放标准，作用类似 USB 接口之于外设：不管工具是谁写的，只要按 MCP 实现一个服务器，Codex 就能发现并调用它的工具。数据库客户端、浏览器操作、内部 API 封装，都可以做成 MCP 服务器。

**怎么实现。** `codex-mcp` crate 管所有连接：启动子进程或连远端、握手、发现工具列表、转发调用、处理断线。每个 MCP 服务器的工具在暴露给模型时加上服务器名前缀，避免重名冲突。工具太多时配合上一节的 tool_search 按需加载。MCP 协议还有 elicitation（服务器向用户发起询问）和资源读取等能力，Codex 都做了对应的桥接。状态查询最近也变聪明了：`mcpServerStatus/list` 接受可选的服务器名，想看某台服务器的状态不再需要全量盘点——会话里已有连接的直接复用（连工具目录都是现成的，不重复发 `initialize` 和 `tools/list` 请求），没有的只为这一台单独建发现连接，只等它一个；名字写错返回空页，省略名字则维持原来的全量行为。

工具目录的**回合内刷新**也补上了（2026-10 中旬）。MCP 服务器可能在连接之后才暴露新工具，新增的 `mcp_tool_list_changed` 特性（默认关闭）让 Codex 收到服务器的工具清单变更通知时就地刷新目录：通知按传输到达顺序排队，并发刷新会合并，分页中途被通知作废的清单会重试；刷新失败保留旧目录并进入重试冷却，同时作废受影响的启动缓存，已受理的调用照常跑完（提交 0df4aa67）。配套两处：code mode 程序里的动态工具调用改为可并行，`DynamicToolHandler` 允许一个程序用 `Promise.all` 同时发起多个调用、互相等待客户端答复时不再彼此阻塞（提交 beae473b）；新增可选扩展工具 `multi_env_copy_file`，在两个已选环境之间直接拷贝文件、内容不进模型上下文，两端各自过沙箱策略与权限检查，完成后返回拷贝字节数，同环境拷贝直接拒绝（提交 e7de1f44）。

一个能体现"历史记录自包含"原则的细节：MCP 工具带有界面展示用的元数据（图标、显示样式等），这些元数据会被保留在工具调用事件和会话历史里。原因是一款工具今天在用、明天可能被卸载，但历史里那条调用记录必须永远能正确显示。展示所需的信息在事件发生时就完整存下来，而不是等显示时去找一个可能已经不在了的东西。

企业方向补了一块（2026-10-20）：MCP 连接支持企业托管授权（enterprise-managed authorization，连接的登录与授权由企业管理方统一决定，提交 1569abc5），企业 MCP 状态列表改走线程连接查询（提交 61fa059d）；跨配置重载时，企业授权的取消动作也能被跟踪（提交 cca40e57）。

安全上也有一个细节：本地的 MCP 服务器是通过 stdio（标准输入输出管道）跟 Codex 通信的。启动这类服务器时，Codex 会应用"只保留 stdio 描述符"的策略——**父进程手里那些跟 MCP 通信无关的文件描述符，不会跟着传进 MCP 服务器和它的子进程**。文件描述符（file descriptor，简称 FD）是操作系统给进程手里的每个打开文件/管道/套接字编的号；如果无关的 FD 泄漏进子进程，等于把一个"可以触摸宿主文件"的门把手交了出去。这个隔离动作把 MCP 服务器的"手"限制在它自己的通信管道上。

### Guardian：审批把关与独立评审

**是什么。** Guardian 是核心里的把关模块，职责写在模块注释的第一行："承载审批决策，以及一个隔离的同步评审者"。前一半是上面审批流程的执行者，后一半是独立的评审会话：像另请一位监理，用单独的模型会话对 Codex 的工作做评审，审批和评审互不干扰。

**怎么实现。** 模块注释里有一句凝练的设计声明：

> The extension chooses policy and evidence; core enforces permissions and mandatory review requirements.
> （扩展层负责选择策略和提供证据；核心层负责强制执行权限和强制评审要求。）

翻译成大白话：什么算敏感、什么时候要审、budget（给评审动作限定的用量上限）给多少，这些"政策"放在扩展层，可以随时调整；但"任何动作都必须过权限检查、该评审的必须评审"这条底线长在核心里，谁都绕不过去。Guardian 还管两种 budget：input budget（评审时喂给模型的内容量上限）和 request budget（评审可以用多少次模型请求），防止把关这个动作本身失控膨胀。配套的 `guardian-context` crate 负责把"给评审者看的材料"（对话节选、待审动作、用户此前的授权）按 budget 组装成上下文，超了就按优先级截断。

**为什么这样设计。** 安全系统里最怕两件事：政策太死板（什么都拦，用户烦了就全关掉）和底线太柔软（说变通就变通）。"策略灵活、底线强硬"的分工同时防住了这两个坑。

Guardian 的边界最近收得更紧，方向是"该审的都得审、按谁的动作审谁的"：评审用的上下文捕获从可配置改成了无条件——会话捕获和 subagent 历史分叉一律带上线程上下文，不再受配置开关影响，评审策略仍从保存的检查点选（不兼容的检查点保留旧式评审）；评审上下文绑定到**动作的目标环境**——动作打在哪个环境上，就用哪个环境的权限上下文来审，避免多环境共用一个 Guardian 会话时拿主环境的限制去审次环境的动作，目标环境不可用就拒绝评审；浏览器连接器（Browser connector）也纳入 computer-use 策略和审查，此前这套只覆盖两个 REPL 通道。

评审的**独立性**也在加码。此前评审材料依附父会话的压缩检查点，父会话一压缩、一回滚，评审手里的证据就可能跟着变。现在父会话压缩时可以为评审保留一份有界的独立转录（关闭 `guardian_reuse_parent_compaction` 时生效），同步评审与异步评分都不再依赖父检查点，评审会话照常接收父压缩后的转录增量；被回滚的动作，其证据按接受顺序清除，哪怕持久化的先后顺序不一样也清得干净。配合另外两条——评审材料里保留已确认的 Code Mode 消息（代码模式调用即使输出被截断，迟到的结果元数据也不丢）、熔断器（circuit breaker，错误率过高时自动暂停评审的保护机制）中断时可选用结构化错误上报——Guardian 正在从"能审"走向"审得可靠、证据经得起回看"。评审能看到的材料也在变全：加密的 agent 消息原样进评审（不是只看解密后的壳）、评审可选地检索会话历史（opt-in，不是默认翻历史）、评审的根上下文带上交接感知（agent 交接链上的前因后果不丢）。

Guardian 的两处默认在 2026-10 中旬也更新了：判定不再直接读 `OPENAI_API_KEY`（那会绕过 AuthManager 刚重载过的登录凭据），改用缓存里的登录凭据，`CODEX_GUARDIAN_DECISIONS_API_KEY` 保留为最高优先级覆盖；V2 异步分类在没有任何显式配置时默认走 conversation 模式（按整段对话分类），snapshot 模式保留为显式覆盖。

Guardian 的审批纪律随后补了一条（2026-10 中旬）：批准覆盖的是"被审的那个动作"的权限，一个 exec 重试若可以脱离沙箱运行，其审批动作改为 `RequireEscalated` 并清空额外权限声明，必须重新评审——旧批准不再预批越级重试，用户与钩子的既有批准行为不变（提交 4b9c24f9）。评审的簿记同步加严：跨失败的评审转录准入有记录可查（PR 54264），图像去重与检查点恢复两处共用一份实现（PR 54278），压缩摘要在 Guardian 转录里归因给助手角色（PR 54281），发往 Guardian Decisions 请求的证据消息结构原样保留（PR 54589）。

2026-10-20 的两笔补的是"评审被打断之后怎么办"和"评审本身可不可见"。其一，被取消或超时的 Guardian 评审此前可以留下未完成就半途接纳的转录证据，复用这个会话会让下一次评审缺证据；现在中断的评审标记为回滚到最近一次完成的评审，已提交的评审历史保留，待审证据在下次评审时重放，回归测试验证加密证据在下次评审中恰好出现一次（提交 affa861d）。其二，评审可观测：记录评审尝试次数与最终结果（带 `retried` 标签）、按失败原因测重试等待的时长与去向（重试、取消、到期限），必需的同步评审走 `required_sync` 路由单独计数；评审的遥测改用发起它的那个回合的模型归因——模型被覆盖后，指标仍算在真正请求评审的模型头上（提交 941b32bf）。

### TUI 与流式渲染

**是什么。** TUI（Text User Interface，文本用户界面）是在纯终端里画出来的交互界面，Codex 的主界面。基于 ratatui 库：程序把界面"画"成一帧帧字符网格，终端负责显示。

**怎么实现。** 界面主体是 `chatwidget`（对话部件），它监听核心发来的事件流并更新画面。模型输出是流式的（一个字一个字到，不是憋一整段），所以渲染要处理大量"内容还在变"的时刻。Codex 的做法有一条主线：区分"进行中"和"已定型"两种状态，分别用两套规则。

流式进行中：文字增量到达时只更新当前正在生长的那个单元格（cell，界面里一段独立排版的内容），不重排整体布局，避免画面跳动。流式结束：内容不再变了，才做一次收尾排版，比如列表项之间统一加间距（规则是"只要有任何一项跨了多行就统一加空行"，因为只有跨行项会让相邻项挤在一起难分辨）。收尾排版的策略还会进 Markdown 渲染缓存的 key（缓存键，用来说明"这份缓存是按什么规则算出来的"），因为同样的内容按不同间距策略渲染出的结果不同，缓存不记策略就会返回过期排版。

回看历史的"对话记录查看器"（transcript viewer）是另一个精心打磨的组件：历史太长不可能一次全加载，它分批加载，用户往下翻就读更老的记录。按 Home 跳到最开头时，如果老记录还没加载完，"跳转"会先记成挂起状态，等加载完再执行；但用户若在等待期间又做了别的滚动操作，挂起的跳转会被取消，同时已经加载到一半的数据不浪费（从"加载开头"模式转成"加载更老"模式继续用）。系统自己的重绘（比如终端窗口大小变了）不会触发取消，因为那不是用户的意图。

**为什么这样设计。** 终端环境的渲染既慢又容易闪，"进行中求稳、定型后求齐"是性能和观感之间的现实解法。而导航取消那套逻辑背后是一个通用的异步界面法则：凡是"用户操作之后才完成的旧动作"，都要给用户的新动作留出取消它的出口，否则晚到的旧结果会覆盖用户的最新意图。

小细节也照护到了：界面会检测操作系统"减少动态效果"的无障碍设置（有些人对动画敏感，系统提供了这个开关），开了就少放动画。用户能敲斜杠命令（slash command，以 `/` 开头的快捷指令，比如 `/compact` 手动触发压缩、`/experimental` 打开实验功能菜单），还能用"技能"（skill，把一段可复用的指令流程打包成文件，对话里提到它的名字就把它的内容注入上下文）。输入框的**提示建议**功能走过了一轮完整的生灭：2026-09-25 引入（回合顺利完成后，在完成回合的隐藏临时分叉里生成"下一步可以干什么"的建议，30 秒超时取消），两天后整个移除——建议生成、composer 渲染、Tab 接受与 Escape 关闭、`tui.prompt_suggestions` 配置项全部删掉。这本身是一条有用的工程信号：自动猜测"用户下一步想说什么"容易变成打扰，团队试了、不合适、干脆撤掉，配置项不留空壳。

预设（preset）这条线在 2026-10 中旬成型：`/presets` 提供十个编号槽位，把一段输入或当前的模型、思考力度、速度设置存成可复用条目，替换和删除都要确认，持久化在配置的 `tui.presets` 下并尊重配置层归属（提交 dcd9e954）。围绕它成了一组：当前权限设置可一键存为预设、`/permissions` 支持内联选择权限档位（PR 54385、54383），`/model` 支持内联切换模型、思考与速度（PR 54378），`/title` 和 `/statusline` 增加"仅本会话生效"的参数（PR 54387），预设还有专门的快捷键菜单（PR 54381）。

### 多会话与 git worktree

**是什么。** Codex 支持同时开多个会话并行干活，每个会话可以工作在独立的 git worktree（工作树，git 的功能：同一个仓库同时检出多个工作目录，就像同一个项目开了多张互不干扰的桌子，改完的东西最后还是汇总到同一个仓库）里。

**怎么实现。** `worktree` crate 的 `WorktreeManager` 负责创建：新工作树从仓库的默认分支起步，只绑定给这个新会话，不会把你改到一半的本地修改卷进去。善后也考虑到了：会话结束后，临时创建但没人认领的工作树会在销毁时自动删除；万一自动清理失败（比如有文件被占用），会明确提示用户手动执行 `git worktree remove <路径>`，而不是悄悄留下一堆垃圾目录。界面上有个 agents 总览页，列出所有活跃会话，可以在那里用工作树开新会话、切进去看进度。

### 多 agent 协作

**是什么。** Codex 不只支持"一个模型对着你说话"，还支持派生（spawn，从主会话拉起一个新的独立 agent）子 agent：每个子 agent 有自己的上下文、角色和任务，干完活把结果交回来。

**怎么实现。** 核心里有一套 agent 注册与生命周期管理（`core/src/agent/` 模块：注册表、角色定义、状态查询），配套 `spawn_agent` 一类工具让模型自己决定"这个活要不要拉个帮手"。agent 之间可以互发消息（协议里有专门的 `Op::InterAgentCommunication`，这类消息会记入会话历史），界面的 agents 总览页能看到每个 agent 的状态。仓库里同时存在新旧两代实现（`multi_agents` 和 `multi_agents_v2` 的工具处理器），正处于用功能开关控制的迁移期。消息板最近补了一个**内存后端**（`message_board_in_memory` 开关）：原本的消息板是 SQLite 写进磁盘的，临时会话（ephemeral session，用完即弃、不建持久存储的会话）用不了，内存版让这类会话里也能开消息板——同一棵派生树内的 agent 共享同一份板状态，最后一个句柄释放就整体回收，频道、帖子、订阅、通知、搜索、分页这些接口和写盘版一致，不因为是内存版就少功能。

**为什么这样设计。** 单上下文的窗口有限，一个会话里塞下"调研十个文件再汇总"既挤又乱；拆给子 agent 等于给每个任务一张独立桌子，主会话只收结论。而"派生权交给模型、管理权留给用户"的分工，让自动化和可控性各归其位。

消息板随后又补了三块：按模板初始化（新消息板搭好初始频道）、频道描述、以及权限与结构化拒绝——谁能读哪个频道有据可依，拒绝时返回结构化的原因，而不是一句干巴巴的报错。

**分叉这条线也在变细。** 新增实验性的预测分叉（prediction fork）：`thread/fork` 多出一种 `experimentalPredictionMode`，从一个已加载的父会话造**临时**分叉，此时拒绝覆盖配置、指定路径、回退旧回合这些选项，完整继承父会话生效中的配置、工具、环境、协作设置、被禁插件和持久历史。动机写在提交里：预测分叉要保住父会话的有效上下文与请求设置，让前缀缓存最大化命中——临时问一个"假如"，不该让服务端把同样的前缀重算一遍。响应里回报分叉实际生效的模型、服务档位和思考力度。预测分叉随后又补了一条纪律（2026-10 中旬）：给分叉挂上线程级的"禁用自动压缩"策略，回合前、中、后（包括上下文超限恢复）都跳过自动压缩、压下新的 token budget 提醒——继承来的父上下文哪怕超过了压缩阈值，也原样留给预测用，模型与技能的额度不受影响。subagent 侧还有几笔配套：subagent 能力改为独立于被分叉的历史保留、完整 agent 分叉可选保留历史前缀（opt-in）、subagent 模型上下文默认值做成可选特性。

根回合的挂起规则也放宽了（2026-10 中旬）：此前只要有活着的后代任务在跑，未完成的根回合就不许挂起，调用方得先停掉并卸载它们才能把根回合挪去别处恢复；现在 `suspend_turn_and_shutdown` 允许直接挂起根回合、发起所有共享本地 agent 运行时的会话关闭并拦住新启动，后代清理单独收尾，被中断的后代不会被自动恢复（提交 341de32c）。

**subagent 的环境继承改成了快照制（2026-10-20）。** 此前的设计是"subagent 继承已配置的线程环境"（带 `subagent_thread_environments` 开关，区分配置绑定与回合临时挂载），三天内被一个更简单的方案换掉：拉起 subagent 时，直接继承发起那个步骤的**环境快照**（step environment snapshot），临时挂载的环境不会变成 subagent 的持久环境；subagent 运行时被驱逐后重载，仍按父会话捕获的环境快照恢复，且要求环境 ID、工作目录、工作区根都匹配，权限校验照常（提交 fbb2f9db、d70c2c2c）。这个改法的走向值得注意：先是加了开关和单独的"配置绑定"概念，随后整个删掉——能靠"复制一份快照"解决的，不需要新的状态分类。

**临时分叉问一次模型：thread/sample（实验性，2026-10-20）。** app server 新增 `thread/sample` 请求：在一个继承已加载线程全部上下文与配置的临时分叉上收集一次模型回复，返回源回合 ID、响应 ID、助手文本和 token 用量，源会话不做任何修改。纪律也配齐了：要求源线程是空闲的持久根线程，并携带 `expectedTurnId` 与其最新完成回合核对；采样期间源历史变了就作废结果；分叉不出现在线程列表里，完成或超时后回收；响应在工具执行和 Stop 钩子之前拦截（工具调用与无文本响应返回 null）；思考力度的调整只在提供方和模型支持保缓存更新时才应用（提交 8f8e7a6e）。它和预测分叉是同一思路的两个入口：临时问一句，不付缓存和历史的代价。

### 语音与云端

仓库里还有两条支线。一条是实时语音会话（协议里的 `RealtimeConversationStart/Audio/Text` 等操作，配 `realtime-webrtc`、`voice-host` 等 crate）：用 WebRTC（浏览器和原生应用常用的实时音视频通信协议）建语音通道，说话就能指挥 Codex。另一条是云端任务的客户端能力（`cloud-tasks`、`cloud-config` 等 crate）：Codex Web 上的云端 agent 在远端容器里干活，本地 CLI 可以查看和管理这些任务。本地与云端共用同一套协议和数据形状，这是"一套核心多端复用"思路在产品形态上的延伸。

语音这一条线里有个容易被忽略但很实际的细节：实时语音用的 WebSocket（网络上保持长开的双向通道）连接，会**遵守配置里设置的代理（proxy）策略**——如果用户为 HTTP 请求配了代理，语音通道的连接也走同一个代理，而不是直连绕过。走代理还能带上自定义的证书信任配置（在 Windows 等平台上尤其重要），保证"出口流量怎么走、信任什么证书"全系统一致，不在语音这条侧路上留例外。

### 配置与功能开关

**配置系统。** 配置文件是 `$CODEX_HOME/config.toml`（TOML 是一种"键 = 值"分节书写的文本配置格式，比 JSON 更适合人手写）。支持 profile（配置档案，多套配置按名切换，比如"公司项目"和"个人项目"各一套模型和审批设置）、权限档位（permission profile，把沙箱强度和审批策略打包成预设）。配置类型变了，就跑一个命令重新生成 JSON Schema（描述配置文件合法结构的规范），编辑器靠它做补全和校验。

**功能开关。** `features` crate 维护一张集中式注册表：每个新功能都在这里登记，标注生命周期阶段（`Stage`）：开发中（用户不可见）、实验性（在 `/experimental` 菜单里可以手动开）、稳定（开关保留但默认开）、废弃、移除。用户在配置文件的 `[features]` 节里开关某个功能。老格式的开关名由 `legacy.rs` 负责迁移。开关不是只进不出的：功能稳定后，开关本身会被逐步移除，把行为固化下来。这套机制刚完成一次实景演示（2026-10 中旬）：worktree 与语音两个功能开关整体退役（提交 bb64b894），代码删除开关检查、配置里的覆盖值被忽略并给出警告、`/experimental` 菜单连同旧服务器目录里的条目一并隐藏，TUI 语音可用性改由平台支持决定。

**为什么这样设计。** 功能开关把"代码发布"和"用户用上"拆成两件事。改对话基本节奏的功能（比如回合中插话）、依赖外部条件的功能（比如网络代理），都先藏在开关后面灰度放量；出了问题按开关回退，不用重新发版。而阶段标记强制回答了每个开关的归宿问题，避免开关越积越多变成没人敢动的遗物。

### 可观测性

**是什么。** 可观测性指系统内部发生了什么、为什么发生，事后能查得清。

**怎么实现。** 三个层面。日志与追踪用 `tracing`（Rust 的结构化日志库），要求用 `#[tracing::instrument]` 标注在函数定义上（而不是在调用点手工包），异步任务的追踪信息才不会断链。指标走 OpenTelemetry（一套通用的遥测标准，简称 otel）：回合耗时、首字延迟、压缩次数、工具调用统计都有对应指标。业务层面，很多地方刻意记录"原因"而不只是"结果"：比如界面向后端发送一整段输入时，会记下发送的触发原因（回车、粘贴长文本、快捷键）和续传模式。出了"消息重复发送"之类的诡异行为，工程师能翻出记录，定位到具体是哪条触发路径。

**为什么这样设计。** 调试难，往往不是缺"发生了什么"的日志，而是缺"为什么发生"。记录动作时顺手把触发原因一起存下来，是最便宜的调试投资。

### 发布与安全流程

**发布。** 二进制从 GitHub Releases 和 `releases.openai.com` 两个渠道分发，安装脚本默认走后者、失败时回退前者。构建系统是 Cargo 和 Bazel（Google 的构建工具）双轨并用，CI 会检查依赖锁文件的一致性。

**签名。** macOS 的发布包要经过代码签名（code signing，用开发者的数字证书给程序盖防伪章，用户和系统据此验证程序确实出自官方且未被篡改；macOS 的 Gatekeeper 机制会拦截没有有效签名的程序）。签名流程在 `.github/scripts/macos-signing/` 里，有一条铁律：程序一旦签名，任何字节改动都会让签名作废，所以必须"全部改完再签"，签名身份（证书和私钥）在整个流程中要原样保留，弄丢了整个包就得从头再来。这类流程配有专门的测试，防止后续改动不小心破坏身份保留逻辑。

**其他安全面。** 仓库有 `SECURITY.md` 说明漏洞报告渠道；核心里有证明材料机制（attestation，向服务端证明客户端身份和运行环境的机制）；密钥优先存进系统钥匙串（keyring，操作系统提供的加密存储），退一步存文件时也放在受保护的路径里；依赖审计有 `deny.toml`（Rust 生态的依赖许可证和安全审计配置）。三大平台的沙箱实现、网络代理的域名白名单、可写目录里对 `.git/hooks` 的保护，都在前面各节说过。

远端 exec-server 的凭据面在这轮补齐（2026-10 中旬）：远端命令支持凭据掩码（PR 54309），执行器凭据有了按作用域的授权（PR 54346），stdin 凭据可轮换（PR 54434），大文件改走 exec-server 的 WebSocket 直连写入（PR 54135），Zsh shell 快照下的远端凭据掩码也支持了（PR 54432）。

2026-10-20 的几笔：Responses API 代理（本地客户端借道访问 Responses API 的转发层）补齐了认证封装与可续期的联邦认证原语，支持 GitHub Actions 的 OIDC 令牌获取（提交 f6e8ca3f、8cac6832、a91b0bf1、57560e9d），被拒绝的代理凭据会刷新并对失败的续期做退避（提交 54f99017）；账号令牌记录 OAuth 来源与登录身份（提交 896604a1）；Windows 沙箱的 MXC 实现迁移到独立的 `mxc-sdk`（提交 c6e29b4f）；审批规则支持按目录模板批准命令前缀（提交 d9a36f6e）；环境断连的通知不再立刻发出，等恢复尝试失败再报（提交 431185b7）。

## 设计哲学与取舍

把前面的机制放在一起看，有几个一以贯之的原则。

**安全是默认值，放权是显式动作。** 默认档位是沙箱加按需审批；想完全放开，用户必须主动选 `danger-full-access` 并承担后果。所有"放宽"都以一次具体的审批为单位，没有"批准一次、终身免疫"。反方向也一样：可写目录内的提权暗道（`.git/hooks`）被主动堵死。这个取向让 Codex 敢于把"自动执行"做成默认体验。

**上下文是被郑重对待的资产。** 往模型窗口里放东西有成文规则：增量追加、尺寸封顶、逐项评审、缓存友好。压缩是受控的有损操作，有明确的触发阈值和固定流程。这些规则写在贡献守则里，等于宣布"上下文质量是代码评审的一部分"。

**核心薄、周边厚。** `resist adding code to codex-core` 写进了贡献守则；模块有行数上限（新增代码原则上不超 500 行，超 800 行的文件要往新模块放）；单次提交原则上不超 800 行（复杂逻辑 500 行）。这些都是同一个判断：改动尺寸决定评审质量，评审质量决定系统寿命。

**一套核心，多端复用。** app-server 协议层前期投入大（要维护严格的类型同步和兼容性），换来的是终端、IDE、桌面、云四端行为同源。取舍是明确的：协议的严谨性成本是一次性的，多端不一致的成本是持续的。

**平台等价而不是平台偏好。** 三套沙箱实现、Windows 下的远程 daemon 连接、WSL 的适配，都是为了让"沙箱里的 AI"在哪个操作系统上都是同一种动物。代价是每个安全机制要实现三遍，但"安全性依赖操作系统"这件事没有捷径。

**用测试形态表达工程价值。** 界面改动必须带快照测试（预先记录渲染结果，改动后自动比对）；涉及 agent 逻辑的改动必须加集成测试（起一个完整的测试实例，用 mock 的模型服务端跑通整条链路）；测试里所有随机值（UUID、路径、缓存键）先归一化成稳定标签再比对。测试不是事后补的凭证，而是设计的一部分。

## 值得借鉴的工程实践

以下几条是从源码和提交历史里提炼的、可以直接搬到自己项目的做法。

**测试先归一化，再比对。** 任何包含随机值、时间戳、本机路径的输出，直接做快照对比永远失败。Codex 把这些值统一替换成 `<UUID 1>` 这类稳定标签后再比。写所有"对比文本"的测试都用得上这一招。

**临时资源必须有善后，善后失败必须有指引。** 工作树的例子：没人认领的临时工作树在销毁时自动删除（Rust 的 Drop 机制，对象离开作用域时自动执行的清理逻辑）；删不掉就提示手动清理命令。自己写任何"创建了就可能用不上"的资源（临时目录、锁文件、子进程）都适用：自动清理是第一选择，清理不了就把手动办法明确告诉用户。

**给"晚到的旧结果"留取消出口。** 界面上用户的新操作应该能取消尚未完成的旧操作，否则旧结果晚到会覆盖新状态。判断时要区分"用户主动"和"系统被动"：被动重绘不该打断用户既定意图。

**"正在变"和"已定型"分开管理。** 流式渲染、进度条、实时列表都有中间态和终态。中间态求稳（少动、不跳），终态求齐（统一、收尾）。影响最终结果的决策（比如间距策略）要进缓存键，否则缓存会返回过期样式。

**记录"为什么"，不只记录"什么"。** 日志里多存一个触发原因字段，排查问题时就能从"哪行代码执行了"推进到"哪条路径触发的"。这是成本最低的可观测性投资。

**改运行中的状态，等自然边界。** 对话进行中切换环境这类请求，推迟到当前回合结束再生效。干到一半换房间，上下文必然前后不一致；回合边界就是那个"把桌子收拾干净"的自然时机。

**历史要自包含。** 需要事后展示的信息（UI 元数据、触发原因、当时的配置快照），在事件发生时就完整存进记录里。展示时刻再去外部找，早晚找到一场空。

**文档化的红线。** 把"上下文注入规则""单次改动行数上限""必须带哪种测试"写成贡献守则里的明确条款，而不是靠老成员口口相传。规则成文，机器和新人才能一起执行。

**用自己的工具养自己的工具。** 这个仓库的 `AGENTS.md` 就是给 Codex 自己看的行为守则：格式化命令、测试命令、行数纪律、上下文规则，全按"AI 会照着执行"来写。项目吃自己的狗粮，文档的措辞会自然变得可执行。
